## Top Strengths

The codebase excels at **Vertical Slice Architecture** (Guidelines 6, 7, 8) — each project is independent, each file tells its own complete story, and configuration is always explicit at call sites. The **Toolbox Pattern** is well-executed with static helpers like `PlotToolbox`, `ProgressToolbox`, `StatisticsCalculator`, and `ProcessNameExtractor`. **Descriptive naming** is strong throughout — `ExtractTimestamps`, `AddScatterWithFill`, `FindServiceProcessIdAsync`, `PublishEventsAsync`.

## Guideline 1: Static Classes for Pure Logic

*"If a class has no instance state, make it static."*

**Score: Needs Attention (3 violations)**

The codebase has many excellent examples of proper static class usage (`PlotToolbox`, `StatisticsCalculator`, `K6ScriptGenerator`, `ProcessNameExtractor`, `LegendFormatters`, `DurationParser`, `PhaseInfoConverter`, `ProgressLineRenderer`, `ContainerDetector`, `Wsl2Detector`, `PowerShellHelper`, `PowerShellExecutor`, `ConsoleCoordinator`, etc.). However, three classes should be converted.

### Violation 1.1 — `PhaseOverlayRenderer`

**File:** `PerformanceTester.Reporting/ChartGeneration/PlotConfiguration/PhaseOverlayRenderer.cs`
**Severity:** High — clearest violation, config is pure data.

Stores `ChartConfig _config` as its sole field. All three methods (`AddPhaseBoundaries`, `AddPhaseLabels`, `AddTitle`) could accept `config` as a parameter instead, making the class static.

```csharp
// ❌ Current: instance class with config field
internal sealed class PhaseOverlayRenderer
{
    private readonly ChartConfig _config;
    public PhaseOverlayRenderer(ChartConfig config) => _config = config;
    public void AddPhaseBoundaries(Plot plot, TestReport testReport) { /* uses _config */ }
}

// ✅ Should be: static class with explicit parameter
internal static class PhaseOverlayRenderer
{
    public static void AddPhaseBoundaries(Plot plot, TestReport testReport, ChartConfig config) { ... }
}
```

### Violation 1.2 — `CloudEventFactory`

**File:** `PerformanceTester.EventPublishing/CloudEventFactory.cs`
**Severity:** Medium.

Only instance field is `private readonly Random _random = new()`. In .NET 9, `Random.Shared` is thread-safe and could replace this field entirely, allowing the class to become static.

### Violation 1.3 — `OSPlatformDetector`

**File:** `PerformanceTester.Common/OSPlatformDetector.cs`
**Severity:** Low — tradeoff for interface-based DI.

Has zero instance fields. Exists only to implement `IOSPlatformDetector` for DI. All logic uses static BCL APIs (`RuntimeInformation.IsOSPlatform()`). This is an acceptable design tradeoff if DI-based platform injection is needed.

## Guideline 2: Explicit Parameters Over Hidden State

*"Pass all dependencies as method parameters, not constructor injection. Makes data flow visible at the call site."*

**Score: Needs Attention (8 violations)**

A cluster of violations exists in the **Reporting** project where configuration objects are stored as constructor-injected fields instead of being passed to methods explicitly.

### Violation 2.1 — `ChartGenerator`

**File:** `PerformanceTester.Reporting/ChartGeneration/ChartGenerator.cs`
**Fields:** `_config`, `_dataLoader`, `_phaseRenderer`, `_imageComposer` — all stored from constructor, used in `GenerateChartAsync`. The `ChartConfig` is pure data; the other three are stateless helpers wrapping that same config.

```csharp
// ❌ Current: 4 hidden dependencies
public async Task GenerateChartAsync(string outputPath, TestReport testReport, CancellationToken ct)

// ✅ Better: explicit at call site
public static async Task GenerateChartAsync(
    string outputPath, TestReport testReport, ChartConfig config, CancellationToken ct)
```

### Violation 2.2 — `ChartDataLoader`

**File:** `PerformanceTester.Reporting/ChartGeneration/DataLoading/ChartDataLoader.cs`
**Fields:** `_logger` — used only for occasional warnings during data loading. Methods could be static with an optional logger parameter.

### Violation 2.3 — `PhaseOverlayRenderer`

**File:** `PerformanceTester.Reporting/ChartGeneration/PlotConfiguration/PhaseOverlayRenderer.cs`
**Fields:** `_config` — pure configuration data for font sizes and line widths. (Overlaps with Violation 1.1.)

### Violation 2.4 — `ChartImageComposer`

**File:** `PerformanceTester.Reporting/ChartGeneration/ImageComposition/ChartImageComposer.cs`
**Fields:** `_dimensions` — pure `PlotDimensions` data (width/height). Could be a parameter to `RenderPlotToBitmap`.

### Violation 2.5 — `K6Executor`

**File:** `PerformanceTester.ApiLoadTesting/K6Executor.cs`
**Fields:** `_metricsParser`, `_k6Path` — parser and binary path stored from constructor but could be explicit parameters to `ExecuteAsync`.

### Violation 2.6 — `LinuxSystemInfoDetector` / `WindowsSystemInfoDetector`

**Files:** `PerformanceTester.Reporting/SystemInfoDetection/`
**Fields:** `_systemInfoCache` — lazy cache initialized in constructor. The detection logic is pure computation that could be static methods with caching handled externally.

### Violation 2.7 — `OrchestratorProgressAdapter`

**File:** `PerformanceTester.Cli/Output/OrchestratorProgressAdapter.cs`
**Fields:** `_totalEventCount`, `_apiDuration` — immutable configuration values. Note: this class also has legitimate mutable state (`_currentEventCount`, `_apiStartTime`), so it can't be fully static, but these config values could be method parameters.

### Violation 2.8 — `SynchronousProgress<T>`

**File:** `PerformanceTester.Orchestration/SynchronousProgress.cs`
**Fields:** `_handler` — callback stored from constructor. Implements `IProgress<T>` interface so the field is needed for contract compliance. This is the weakest violation.

## Guideline 3: Inline Single-Use Code

*"If something is only used once, inline it with a descriptive comment."*

**Score: Minor Issues (5 violations)**

### Violation 3.1 — `TestOrchestrator.FormatDuration`

**File:** `PerformanceTester.Orchestration/TestOrchestrator.cs` (lines 809-820)
Called only once (line 767). Simple 3-conditional formatting logic that should be inlined with a comment like `// Format duration as "1h" / "30m" / "45s"`.

### Violation 3.2 — `DatabaseCleaner.BuildConnectionString`

**File:** `PerformanceTester.Infrastructure/Database/DatabaseCleaner.cs` (lines 121-128)
Called once. Wraps 3 lines of `NpgsqlConnectionStringBuilder` creation. Should be inlined with comment: `// Build connection string for target database`.

### Violation 3.3 — `ChartGenerator` helper methods

**File:** `PerformanceTester.Reporting/ChartGeneration/ChartGenerator.cs`
Three methods each called exactly once: `EnsureOutputDirectoryExists`, `DeriveDataFilePaths`, `ValidateDataFilesExist`. Each is 4-8 lines. Should be inlined in `GenerateChartAsync` with descriptive comments.

### Violation 3.4 — `ProgressReporter.ClearCurrentLine`

**File:** `PerformanceTester.Cli/Output/ProgressReporter.cs` (lines 126-133)
Wraps a 2-line operation (flag check + `ProgressToolbox.ClearPreviousLines(1)`). Called 4 times but trivial enough to inline with comment: `// Clear progress line if rendered`.

### Violation 3.5 — `ProgressReporter.RenderCurrentProgress`

**File:** `PerformanceTester.Cli/Output/ProgressReporter.cs` (lines 110-124)
Called only twice. Simple 4-line logic: null check → clear → render → set flag.

## Guideline 4: Descriptive Function Names

*"Functions that configure should say what they configure. Avoid generic names."*

**Score: Good (1 violation)**

### Violation 4.1 — `MetricsAggregator.ProcessMetric`

**File:** `PerformanceTester.ApiLoadTesting/MetricsAggregator.cs`
"Process" is vague. The method accumulates k6 metrics (requests, failures, durations) into internal aggregation state.
**Better name:** `AccumulateK6Metric` or `AddMetricToAggregation`.

**Positive examples:** The codebase generally excels here — `ExtractTimestamps`, `AddScatterWithFill`, `ConfigureLeftAxisLabel`, `FindServiceProcessIdAsync`, `PublishEventsAsync` are all descriptive and self-documenting.

## Guideline 5: Toolbox Pattern

*"Extract small, pure, single-purpose functions into a shared toolbox."*

**Score: Minor Issues (2 violations)**

### Violation 5.1 — `CompareCommand` JSON loading duplication

**File:** `PerformanceTester.Cli/Commands/CompareCommand.cs` (lines 220-377)
Three nearly identical methods follow the same pattern:
- `LoadThroughputSamplesAsync`
- `LoadProcessResourceSamplesAsync`
- `LoadSystemResourceSamplesAsync`

Each does: `File.Exists` → `ReadAllText` → `JsonDocument.Parse` → `EnumerateArray` → Map to model. Should be extracted to a generic toolbox function like `JsonFileToolbox.LoadSamples<T>(filePath, mapFunc, ct)`.

### Violation 5.2 — `RabbitMqCleaner.CreateRequest`

**File:** `PerformanceTester.Infrastructure/RabbitMQ/RabbitMqCleaner.cs` (lines 82-87)
Pure function creating an `HttpRequestMessage` with an auth header. Used twice within the class. Could be extracted to a reusable toolbox function for authenticated HTTP requests.

## Guideline 10: Composition Over Interfaces

*"Don't create interfaces just for the sake of abstraction."*

**Score: Needs Attention (5 violations)**

All five interfaces below have exactly one implementation with no test substitution or polymorphism benefit:

| Interface | Implementation | Project |
|-----------|---------------|---------|
| `IChartGenerator` | `ChartGenerator` | Reporting |
| `IComparisonReportGenerator` | `ComparisonReportGenerator` | Reporting |
| `IReportGenerator` | `ReportGenerator` | Reporting |
| `IProgressReporter` | `ProgressReporter` | Cli |
| `IConsoleWriter` | `ConsoleWriter` | Cli |

**Not violations (correctly use interfaces):**
- `ISystemInfoDetector` — 2 implementations (Linux/Windows)
- `IProcessFinder` — 2 implementations (Linux/Windows)
- `IOSPlatformDetector` — Platform abstraction boundary
- `IEventPublisher`, `IEventConsumer`, `ITestOrchestrator` — Cross-slice VSA contracts

**Nuance:** Some of the flagged interfaces could be argued as valid if they serve as a consumer contract between slices. However, `IChartGenerator`, `IReportGenerator`, and `IComparisonReportGenerator` are consumed only within the same project (Reporting) or by a single consumer (Orchestration/Cli), making the abstraction layer unnecessary overhead.

## Guideline 11: Return Early to Avoid Nesting

*"Use guard clauses and early returns. Keep main logic at base indentation."*

**Score: Needs Attention (7 deeply nested methods)**

### Nesting 11.1 — `DockerMonitorService.RunStreamingLoopWithReconnectionAsync`

**File:** `PerformanceTester.DockerMonitoring/DockerMonitorService.cs` (lines 215-372)
**Depth:** 5+ levels  |  **Length:** 158 lines
**Pattern:** `while` → `try` → `Task.WhenAny` → `if` → `try` → `catch`
**Priority:** High — most complex method in the codebase. The reconnection logic with backoff calculation is deeply buried inside exception handlers.

**Improvement:** Extract inner loops to named methods (`TryConnectAsync`, `CalculateBackoffDelay`), use guard clauses for cancellation checks.

### Nesting 11.2 — `ProcessMonitorService.ExecuteAsync`

**File:** `PerformanceTester.ProcessMonitoring/ProcessMonitorService.cs` (lines 80-263)
**Depth:** 4+ levels  |  **Length:** 184 lines
**Pattern:** `try` → `try` → `while` → `try` → `if`
**Priority:** High — lifecycle management with deeply nested sampling loop.

**Improvement:** Extract process initialization (lines 106-129) to `InitializeProcessAsync()` and sampling loop (lines 138-225) to `RunSamplingLoopAsync()`.

### Nesting 11.3 — `TestOrchestrator.ExecuteEventTestPhaseAsync`

**File:** `PerformanceTester.Orchestration/TestOrchestrator.cs` (lines 395-510)
**Depth:** 5 levels  |  **Length:** 116 lines
**Pattern:** `if` → lambda → `if` → `lock` → `if` (progress throttling)
**Priority:** Medium.

**Improvement:** Extract progress callback creation to a named method. Consider `SemaphoreSlim` instead of `lock` for async-friendly code.

### Nesting 11.4 — `TestOrchestrator.ExecuteWarmupPhaseAsync`

**File:** `PerformanceTester.Orchestration/TestOrchestrator.cs` (lines 296-393)
**Depth:** 4 levels  |  **Length:** 98 lines
**Pattern:** `try` → `for` → `try` → `if-else`
**Priority:** Medium.

### Nesting 11.5 — `EventConsumerService.OnMessageReceivedAsync`

**File:** `PerformanceTester.EventConsuming/EventConsumerService.cs` (lines 357-448)
**Depth:** 3-4 levels  |  **Length:** 92 lines
**Pattern:** `try` → `if (tracking)` → `if (sample)` with nested `try-catch` for NACK
**Priority:** Medium.

**Improvement:** Extract target completion check (lines 396-419) to `CheckTargetReachedAsync()`. Use early return after ACK for the non-tracking path.

### Nesting 11.6 — `TestCommand.ExecuteAsync`

**File:** `PerformanceTester.Cli/Commands/TestCommand.cs` (lines 129-233)
**Depth:** 3 levels  |  **Length:** 105 lines
**Pattern:** Repetitive `catch` blocks each duplicating 3-4 statements (progress report + console output + logging + return code)
**Priority:** Low.

**Improvement:** Extract common error handling to `HandleTestError(exception, progressReporter, consoleWriter, logger)`.

### Nesting 11.7 — `ComparisonReportGenerator.WriteTestEnvironment`

**File:** `PerformanceTester.Reporting/ComparisonGeneration/ComparisonReportGenerator.cs` (lines 81-158)
**Depth:** 3 levels  |  **Length:** 78 lines
**Pattern:** `if` → `for` → `if` (disk formatting)
**Priority:** Low.

## Recommendations

### High Priority

1. **Flatten deep nesting** in `DockerMonitorService.RunStreamingLoopWithReconnectionAsync` and `ProcessMonitorService.ExecuteAsync` — extract inner loops and connection logic to named methods, use guard clauses for early exits.
2. **Make `PhaseOverlayRenderer` static** — pass `ChartConfig` as a parameter to all three methods.

### Medium Priority

3. **Remove 5 single-implementation interfaces** in Reporting and Cli projects — inject concrete classes directly via DI.
4. **Extract JSON loading toolbox** from `CompareCommand` — eliminate 3-way duplication with a generic `LoadSamples<T>()`.
5. **Make `ChartDataLoader` and `ChartImageComposer` static** — pass dependencies as explicit method parameters.
6. **Flatten progress callback nesting** in `TestOrchestrator.ExecuteEventTestPhaseAsync` — extract callback creation to a named method.

### Low Priority

7. **Inline single-use private methods** — `FormatDuration`, `BuildConnectionString`, `EnsureOutputDirectoryExists`, `DeriveDataFilePaths`, `ValidateDataFilesExist`.
8. **Rename `ProcessMetric`** to `AccumulateK6Metric` for clarity.
9. **Use `Random.Shared`** in `CloudEventFactory` and make the class static.
10. **Extract common error handling** in `TestCommand.ExecuteAsync` to reduce catch block duplication.
