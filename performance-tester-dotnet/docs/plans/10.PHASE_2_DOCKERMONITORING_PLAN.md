## Overview

### Purpose

Implement `PerformanceTester.DockerMonitoring` as an independent slice that monitors Docker container resource usage (CPU, memory) using the Docker.DotNet client library. This slice runs as a BackgroundService during performance tests to track RabbitMQ and PostgreSQL container metrics.

### Scope

**What's Included:**
- ✅ `DockerMetrics` model (slice-owned)
- ✅ `IDockerMonitor` public interface
- ✅ `DockerMonitorService` BackgroundService with PeriodicTimer
- ✅ Docker.DotNet client wrapper (`DockerClient`)
- ✅ CPU/memory calculation from Docker stats API
- ✅ Channel-based metrics collection
- ✅ `AddDockerMonitoring()` extension method
- ✅ Integration test project with real Docker containers

**What's NOT Included:**
- ❌ Container lifecycle management (Testcontainers handles this)
- ❌ Docker Compose integration
- ❌ Reporting/aggregation (handled by Reporting slice in Phase 3)

### Key Design Principles

**VSA Principles:**
- Producer-owned contracts (DockerMonitoring owns DockerMetrics)
- No dependencies on other Phase 2 slices
- Self-contained capability
- Interface-based public API

**BackgroundService Pattern:**
- PeriodicTimer for sampling (3000ms interval per Python)
- Channel-based producer-consumer for metrics
- Graceful shutdown via CancellationToken
- Complete channel in finally block

**Docker Integration:**
- Uses Docker.DotNet (official Docker SDK)
- No subprocess spawning (`docker stats`)
- Direct access to Docker API
- Cross-platform (Unix socket on Linux, named pipe on Windows)

## Python Source Analysis

### File: `container_monitor.py` (198 lines)

**Key Findings:**

#### 1. Container Stats Structure (lines 45-80)

```python
def get_container_stats(container_name: str) -> Optional[Dict]:
    """Get real-time stats for a specific container"""
    try:
        client = docker.from_env()
        container = client.containers.get(container_name)
        stats = container.stats(stream=False)

        return {
            'cpu_percent': calculate_cpu_percent(stats),
            'memory_mb': stats['memory_stats']['usage'] / (1024 * 1024),
            'container_id': container.id,
            'container_name': container.name
        }
    except docker.errors.NotFound:
        return None
```

**Implications:**
- Stream=False means single snapshot (not streaming)
- Memory calculation: `usage / (1024 * 1024)` converts bytes to MB
- Returns None if container not found (graceful degradation)

#### 2. CPU Calculation (lines 85-120)

```python
def calculate_cpu_percent(stats: Dict) -> float:
    """Calculate CPU percentage from Docker stats"""
    cpu_delta = stats['cpu_stats']['cpu_usage']['total_usage'] - \
                stats['precpu_stats']['cpu_usage']['total_usage']

    system_delta = stats['cpu_stats']['system_cpu_usage'] - \
                   stats['precpu_stats']['system_cpu_usage']

    cpu_count = stats['cpu_stats']['online_cpus']

    if system_delta > 0 and cpu_delta > 0:
        cpu_percent = (cpu_delta / system_delta) * cpu_count * 100.0
    else:
        cpu_percent = 0.0

    return round(cpu_percent, 2)
```

**Key Formula:**
```
CPU% = (cpu_delta / system_delta) * cpu_count * 100
```

**Implications:**
- Requires two snapshots (current and previous)
- Must store previous stats for delta calculation
- Division by zero handling required
- Result rounded to 2 decimal places

#### 3. Monitoring Loop (lines 125-165)

```python
def monitor_container(container_name: str, interval: float = 3.0):
    """Monitor container continuously"""
    logger.info(f"Starting container monitoring: {container_name}")

    while True:
        stats = get_container_stats(container_name)

        if stats:

                'timestamp': datetime.utcnow(),

                'container_name': stats['container_name']

        time.sleep(interval)  # 3 seconds
```

**Implications:**
- Sampling interval: 3 seconds (matches ProcessMonitoring)
- Infinite loop (runs until process killed)
- Graceful handling if container not found
- Metrics stored in memory (list)

## Architecture Design

### Project Structure

```
PerformanceTester.DockerMonitoring/
├── DockerMetrics.cs                   # Model (record)
├── IDockerMonitor.cs                  # Public interface
├── DockerMonitorService.cs            # BackgroundService + IDockerMonitor implementation
├── DockerClientWrapper.cs             # Docker.DotNet wrapper
├── ServiceCollectionExtensions.cs     # AddDockerMonitoring()
├── README.md
└── PerformanceTester.DockerMonitoring.csproj
```

**Note:** Flat structure (no folders) following the pattern established in Phase 1 and Phase 2a/2b.

**Design Decision:** Uses **single-class pattern** where `DockerMonitorService` implements both `BackgroundService` and `IDockerMonitor`. No separate channel/consumer classes needed since:
- Sampling interval is slow (3000ms) - no performance benefit from fire-and-forget
- Writing to in-memory `ConcurrentBag<T>` is negligible overhead (~nanoseconds)
- Simpler design: one class, clear naming (MonitorService implements IMonitor)
- Avoids naming confusion of having MonitorService NOT implement IMonitor interface

### NuGet Dependencies

```xml
<PackageReference Include="Docker.DotNet" Version="3.125.15" />
<PackageReference Include="Microsoft.Extensions.Hosting.Abstractions" Version="9.0.0" />
<PackageReference Include="Microsoft.Extensions.Logging.Abstractions" Version="9.0.0" />
```

**Why Docker.DotNet:**
- Official Docker SDK for .NET
- No subprocess spawning required
- Cross-platform (Unix socket + named pipe)
- Strongly-typed stats API
- Maintained by Docker, Inc.

### Component Relationships

```
DockerMonitorService (BackgroundService + IDockerMonitor)
    ↓ uses
DockerClientWrapper
    ↓ wraps
Docker.DotNet.DockerClient
    ↓ produces
DockerMetrics
    ↓ stores in
ConcurrentBag<DockerMetrics> (in-memory)
    ↓ retrieved via
IDockerMonitor.GetCollectedMetrics()
```

**Simplified Design:** No channel/consumer pattern. DockerMonitorService samples metrics and stores them directly in a thread-safe collection.

**Synchronous Metrics Retrieval:** `GetCollectedMetrics()` is synchronous (not async) because it only performs in-memory operations (LINQ sorting of `ConcurrentBag<T>`). No I/O operations are involved.

## Docker Client Integration

### DockerClientWrapper.cs

**Location:** `PerformanceTester.DockerMonitoring/DockerClientWrapper.cs`

**Purpose:** Encapsulate Docker.DotNet client and provide typed stats access.

```csharp
using Docker.DotNet;
using Docker.DotNet.Models;

namespace PerformanceTester.DockerMonitoring;

/// <summary>
/// Wrapper around Docker.DotNet client for container stats retrieval.
/// </summary>
internal sealed class DockerClientWrapper : IDisposable
{
    private readonly DockerClient _client;
    private readonly ILogger<DockerClientWrapper> _logger;

    public DockerClientWrapper(ILogger<DockerClientWrapper> logger)
    {
        _logger = logger;

        // Auto-detect Docker endpoint (Unix socket on Linux, named pipe on Windows)
        var dockerUri = RuntimeInformation.IsOSPlatform(OSPlatform.Windows)
            ? new Uri("npipe://./pipe/docker_engine")
            : new Uri("unix:///var/run/docker.sock");

        _client = new DockerClientConfiguration(dockerUri).CreateClient();

        _logger.LogDebug("Docker client initialized with endpoint: {Endpoint}", dockerUri);
    }

    /// <summary>
    /// Gets container stats snapshot (non-streaming).
    /// Returns null if container not found.
    /// </summary>
    public async Task<ContainerStatsResponse?> GetContainerStatsAsync(
        string containerName,
        CancellationToken cancellationToken = default)
    {
        try
        {
            // Get container by name (matches Python behavior)
            var containers = await _client.Containers.ListContainersAsync(
                new ContainersListParameters
                {
                    All = false, // Only running containers
                    Filters = new Dictionary<string, IDictionary<string, bool>>
                    {
                        ["name"] = new Dictionary<string, bool> { [containerName] = true }
                    }
                },
                cancellationToken);

            if (containers.Count == 0)
            {
                _logger.LogWarning("Container {ContainerName} not found", containerName);
                return null;
            }

            var containerId = containers[0].ID;

            // Get stats (stream=false for single snapshot)
            var statsProgress = new Progress<ContainerStatsResponse>();
            ContainerStatsResponse? result = null;

            statsProgress.ProgressChanged += (_, stats) => result = stats;

            await _client.Containers.GetContainerStatsAsync(
                containerId,
                new ContainerStatsParameters { Stream = false }, // Single snapshot
                statsProgress,
                cancellationToken);

            // Docker.DotNet invokes ProgressChanged asynchronously
            // Give it a moment to populate result
            await Task.Delay(100, cancellationToken);

            if (result == null)
            {
                _logger.LogWarning("Failed to get stats for container {ContainerName}", containerName);
            }

            return result;
        }
        catch (DockerContainerNotFoundException)
        {
            _logger.LogWarning("Container {ContainerName} not found (DockerContainerNotFoundException)",
                containerName);
            return null;
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Error getting stats for container {ContainerName}", containerName);
            throw;
        }
    }

    /// <summary>
    /// Calculates CPU percentage from Docker stats.
    /// Formula: (cpu_delta / system_delta) * cpu_count * 100
    /// </summary>
    /// <remarks>
    /// <para><strong>Container-Level CPU Calculation</strong></para>
    /// <para>
    /// This method matches Docker's native stats API and Python reference implementation.
    /// It measures container CPU usage by comparing container CPU time against system-wide
    /// CPU time progression, scaled by available cores to show total capacity used.
    /// </para>
    /// <para><strong>Why This Differs from Process-Level CPU:</strong></para>
    /// <para>
    /// Container monitoring scales by multiplying by core count (total capacity).
    /// Process monitoring normalizes by dividing by core count (per-core average).
    /// See <c>ProcessCpuCalculator.Sample</c> in PerformanceTester.ProcessMonitoring
    /// for process-level CPU calculation. The formulas differ because containers use
    /// cgroup accounting (system CPU time) while processes use wall-clock time.
    /// </para>
    /// <para><strong>Stateless Design:</strong></para>
    /// <para>
    /// Unlike ProcessCpuCalculator, this method is stateless because Docker API provides
    /// both current stats (cpu_stats) and previous stats (precpu_stats) in a single response.
    /// No need to maintain state between calls.
    /// </para>
    /// </remarks>
    public static double CalculateCpuPercent(ContainerStatsResponse stats)
    {
        var cpuDelta = stats.CPUStats.CPUUsage.TotalUsage -
                       stats.PreCPUStats.CPUUsage.TotalUsage;

        var systemDelta = stats.CPUStats.SystemUsage -
                          stats.PreCPUStats.SystemUsage;

        var cpuCount = stats.CPUStats.OnlineCPUs;

        if (systemDelta > 0 && cpuDelta > 0)
        {
            var cpuPercent = (double)cpuDelta / systemDelta * cpuCount * 100.0;
            return Math.Round(cpuPercent, 2);
        }

        return 0.0;
    }

    public void Dispose()
    {
        _client?.Dispose();
    }
}
```

**Key Design Decisions:**

**Platform Detection:**
- Uses `RuntimeInformation.IsOSPlatform()` for cross-platform support
- Windows: Named pipe (`npipe://./pipe/docker_engine`)
- Linux/macOS: Unix socket (`unix:///var/run/docker.sock`)

**Container Lookup:**
- Uses container name filter (matches Python)
- Only searches running containers (`All = false`)
- Returns null if not found (graceful degradation)

**Stats Retrieval:**
- `Stream = false` for single snapshot (not continuous streaming)
- Uses `IProgress<T>` pattern (Docker.DotNet requirement)
- Small delay (100ms) to allow async callback to populate result

**CPU Calculation:**
- Static method (no state required)
- Matches Python formula exactly
- Handles division by zero
- Rounds to 2 decimal places
- **Important:** Uses different formula than ProcessCpuCalculator (see below)

**Error Handling:**
- Returns null for not found (non-fatal)
- Logs warnings for missing containers
- Re-throws unexpected exceptions

### CPU Calculation: Why Docker Differs from Process Monitoring

**Important Design Note:** Docker container CPU calculation uses a **different formula** than process-level CPU calculation (`ProcessCpuCalculator` in Phase 2c). This is **intentional and correct**.

#### Process-Level CPU (Phase 2c: ProcessMonitoring)

```csharp
// Formula: (CPUTimeDelta / ElapsedTimeDelta / CoreCount) * 100
var cpuPercent = (cpuDelta / timeDelta / Environment.ProcessorCount) * 100.0;
```

**Characteristics:**
- Compares CPU time against **wall-clock time** (real elapsed time)
- **Normalizes** by dividing by core count (shows per-core average)
- Maintains state between calls (stores previous timestamp and CPU time)
- Returns 0.0 on first call (initialization)

**Example:** If 200ms CPU time used in 1000ms elapsed on 4-core system:
```
(200ms / 1000ms / 4) * 100 = 5% per-core average
```

#### Container-Level CPU (Phase 2e: DockerMonitoring)

```csharp
// Formula: (cpu_delta / system_delta) * cpu_count * 100
var cpuPercent = (double)cpuDelta / systemDelta * cpuCount * 100.0;
```

**Characteristics:**
- Compares container CPU time against **system-wide CPU time** (cgroup accounting)
- **Scales** by multiplying by core count (shows total capacity used)
- Stateless (Docker API provides both current and previous stats in single response)
- Matches Docker CLI (`docker stats`) output exactly

**Example:** If container used 100ms of 1000ms system CPU on 4-core system:
```
(100ms / 1000ms) * 4 * 100 = 40% total capacity
```

#### Why the Formulas Differ

| Aspect | Process Monitoring | Docker Monitoring |
|--------|-------------------|-------------------|
| **Data Source** | `Process.TotalProcessorTime` | Docker Stats API (cgroups) |
| **Comparison** | CPU time vs wall-clock time | Container CPU vs system CPU |
| **Core Count** | Divide (normalize) | Multiply (scale) |
| **State** | Stateful (maintains previous sample) | Stateless (Docker provides precpu_stats) |
| **Use Case** | Track individual process usage | Track container resource limits |
| **Matches** | .NET Process API conventions | Docker CLI conventions |

#### VSA Implications

Per Vertical Slice Architecture principles, these implementations should **remain separate**:
- ✅ Each slice owns its CPU calculation (no shared abstraction)
- ✅ Different domains require different formulas
- ✅ No coupling between ProcessMonitoring and DockerMonitoring slices
- ❌ Attempting to share logic would be premature abstraction

**Cross-References:**
- See `ProcessCpuCalculator.cs` in PerformanceTester.ProcessMonitoring for process-level calculation
- Both implementations include XML documentation explaining the differences

## BackgroundService Implementation

### DockerMonitorService.cs

**Location:** `PerformanceTester.DockerMonitoring/DockerMonitorService.cs`

**Purpose:** BackgroundService that samples container stats at regular intervals and implements IDockerMonitor.

```csharp
using System.Collections.Concurrent;

namespace PerformanceTester.DockerMonitoring;

/// <summary>
/// BackgroundService that monitors Docker container resource usage.
/// Samples CPU and memory metrics at regular intervals and stores them in memory.
/// Implements IDockerMonitor to provide access to collected metrics.
/// </summary>
internal sealed class DockerMonitorService : BackgroundService, IDockerMonitor
{
    private readonly string _containerName;
    private readonly TimeSpan _samplingInterval;
    private readonly DockerClientWrapper _dockerClient;
    private readonly ILogger<DockerMonitorService> _logger;
    private readonly ConcurrentBag<DockerMetrics> _collectedMetrics = new();

    public string ContainerName => _containerName;

    public DockerMonitorService(
        string containerName,
        TimeSpan samplingInterval,
        DockerClientWrapper dockerClient,
        ILogger<DockerMonitorService> logger)
    {
        _containerName = containerName;
        _samplingInterval = samplingInterval;
        _dockerClient = dockerClient;
        _logger = logger;
    }

    /// <inheritdoc />
    public IReadOnlyCollection<DockerMetrics> GetCollectedMetrics()
    {
        // Return metrics sorted by timestamp (chronological order)
        return _collectedMetrics
            .OrderBy(m => m.Timestamp)
            .ToList()
            .AsReadOnly();
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        _logger.LogInformation(
            "Docker monitor started for container: {ContainerName}, interval: {Interval}ms",
            _containerName, _samplingInterval.TotalMilliseconds);

        // Use PeriodicTimer for accurate intervals (preferred over Task.Delay loop)
        using var timer = new PeriodicTimer(_samplingInterval);

        try
        {
            while (!stoppingToken.IsCancellationRequested)
            {
                // Wait for next tick
                await timer.WaitForNextTickAsync(stoppingToken);

                // Sample container stats
                var stats = await _dockerClient.GetContainerStatsAsync(
                    _containerName,
                    stoppingToken);

                if (stats == null)
                {
                    // Container not found - log and continue
                    // This allows container to start after monitor
                    _logger.LogDebug("Container {ContainerName} not found, skipping sample",
                        _containerName);
                    continue;
                }

                // Calculate metrics
                var metrics = new DockerMetrics
                {
                    Timestamp = DateTime.UtcNow,
                    ContainerId = stats.ID,
                    ContainerName = _containerName,
                    CpuPercent = DockerClientWrapper.CalculateCpuPercent(stats),
                    MemoryMB = Math.Round(stats.MemoryStats.Usage / 1024.0 / 1024.0, 2)
                };

                // Store metrics directly (thread-safe)
                _collectedMetrics.Add(metrics);

                _logger.LogTrace(
                    "Container {ContainerName} - CPU: {Cpu}%, Memory: {Memory}MB",
                    _containerName, metrics.CpuPercent, metrics.MemoryMB);
            }
        }
        catch (OperationCanceledException)
        {
            _logger.LogInformation(
                "Docker monitor stopped for container: {ContainerName}",
                _containerName);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Docker monitor failed for container: {ContainerName}",
                _containerName);
            throw;
        }
        finally
        {
            _logger.LogInformation(
                "Docker monitor completed for container: {ContainerName}, collected {Count} samples",
                _containerName, _collectedMetrics.Count);
        }
    }
}
```

**Key Design Decisions:**

**Implements Both BackgroundService and IDockerMonitor:**
- Single class handles both sampling and data retrieval
- Simpler than channel/consumer pattern
- Clear naming: MonitorService implements IMonitor interface
- No performance penalty (sampling interval is slow: 3000ms)

**Constructor Injection:**
- `containerName` - Which container to monitor
- `samplingInterval` - How often to sample (3000ms default)
- `dockerClient` - Docker.DotNet wrapper
- `logger` - Structured logging

**Thread-Safe Storage:**
- Uses `ConcurrentBag<DockerMetrics>` for in-memory storage
- Thread-safe without explicit locking
- Negligible overhead for 3-second sampling intervals

**PeriodicTimer:**
- More accurate than `Task.Delay` loop
- Automatically adjusts for drift
- Cancellation-aware
- .NET 6+ best practice

**Graceful Container Not Found:**
- Returns null from wrapper
- Logs debug message (not warning, too noisy)
- Continues monitoring (allows late container start)
- Non-fatal error

**Memory Calculation:**
- `stats.MemoryStats.Usage` is in bytes
- Divide by 1024 twice for MB
- Round to 2 decimal places
- Matches Python calculation

**GetCollectedMetrics:**
- Returns metrics sorted by timestamp (chronological order)
- Thread-safe read (ConcurrentBag enumeration is safe)
- Returns read-only collection
- Synchronous (no I/O operations, only in-memory LINQ)

**Logging Levels:**
- Information: Start/stop lifecycle events, final sample count
- Debug: Container not found (non-fatal)
- Trace: Per-sample metrics (verbose)
- Error: Unexpected exceptions

## Dependency Injection

### ServiceCollectionExtensions.cs

**Location:** `PerformanceTester.DockerMonitoring/ServiceCollectionExtensions.cs`

**Purpose:** Provide `AddDockerMonitoring()` extension method following established patterns.

```csharp
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

namespace PerformanceTester.DockerMonitoring;

/// <summary>
/// Extension methods for registering Docker monitoring services.
/// </summary>
public static class ServiceCollectionExtensions
{
    /// <summary>
    /// Adds Docker container monitoring for a specific container.
    /// Registers a BackgroundService that samples container stats at regular intervals.
    /// </summary>
    /// <param name="services">Service collection.</param>
    /// <param name="containerName">Name of container to monitor (e.g., "performancetest-rabbitmq").</param>
    /// <param name="samplingInterval">How often to sample metrics (default: 3000ms).</param>
    /// <returns>Service collection for chaining.</returns>
    public static IServiceCollection AddDockerMonitoring(
        this IServiceCollection services,
        string containerName,
        TimeSpan? samplingInterval = null)
    {
        var interval = samplingInterval ?? TimeSpan.FromMilliseconds(3000);

        // Register Docker client wrapper (shared across all container monitors)
        services.AddSingleton<DockerClientWrapper>();

        // Register DockerMonitorService as both BackgroundService and IDockerMonitor
        services.AddSingleton<DockerMonitorService>(sp =>
        {
            var dockerClient = sp.GetRequiredService<DockerClientWrapper>();
            var logger = sp.GetRequiredService<ILogger<DockerMonitorService>>();

            return new DockerMonitorService(
                containerName,
                interval,
                dockerClient,
                logger);
        });

        // Register as IHostedService (starts BackgroundService)
        services.AddHostedService<DockerMonitorService>(sp =>
            sp.GetRequiredService<DockerMonitorService>());

        // Register as IDockerMonitor (provides public API)
        services.AddSingleton<IDockerMonitor>(sp =>
            sp.GetRequiredService<DockerMonitorService>());

        return services;
    }
}
```

**Key Design Decisions:**

**Single Class, Multiple Registrations:**
- DockerMonitorService registered as singleton (concrete type)
- Same instance registered as IHostedService (BackgroundService lifecycle)
- Same instance registered as IDockerMonitor (public API)
- Triple registration pattern ensures all consumers get the same instance

**Per-Container Registration:**
- Each call to `AddDockerMonitoring()` registers monitoring for one container
- Orchestrator calls twice: once for RabbitMQ, once for PostgreSQL
- Each gets its own DockerMonitorService instance

**Shared Docker Client:**
- One DockerClientWrapper shared across all monitors
- More efficient than creating multiple connections
- Thread-safe (Docker.DotNet handles this)

**Why Triple Registration:**
- Singleton: DI container creates and manages instance
- IHostedService: IHost calls Start/StopAsync lifecycle methods
- IDockerMonitor: Orchestrator retrieves via GetServices<IDockerMonitor>()

**No Keyed Services:**
- Could use keyed services (.NET 8+) to distinguish containers
- Current approach simpler: orchestrator gets all IDockerMonitor instances
- ContainerName property identifies which container each monitor tracks

**Usage Example:**

```csharp
// In Orchestration project's DI setup
var builder = Host.CreateApplicationBuilder();

// Register Docker monitoring for both containers
builder.Services.AddDockerMonitoring(
    containerName: "performancetest-rabbitmq",
    samplingInterval: TimeSpan.FromSeconds(3));

builder.Services.AddDockerMonitoring(
    containerName: "performancetest-postgres",
    samplingInterval: TimeSpan.FromSeconds(3));
```

### DockerMonitoringSystem.cs

**Purpose:** Custom System class providing access to DockerMonitoring services. Exposes individual monitor properties for PostgreSQL and RabbitMQ containers, following the pattern of exposing infrastructure components directly (like PostgresConnection, RabbitMqConnection in base System).

```csharp
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using PerformanceTester.IntegrationTesting;

namespace PerformanceTester.DockerMonitoring.IntegrationTests.Infrastructure;

/// <summary>
/// System under test for Docker monitoring integration tests.
/// Extends base System with DockerMonitoring-specific components.
/// </summary>
public sealed class DockerMonitoringSystem : System
{
    private IHost? _host;

    public IDockerMonitor PostgresMonitor { get; private set; } = null!;
    public IDockerMonitor RabbitMqMonitor { get; private set; } = null!;

    /// <summary>
    /// Initializes Docker monitoring services for PostgreSQL and RabbitMQ containers.
    /// </summary>
    internal new void Initialize(string postgresConnectionString, string rabbitMqConnectionString)
    {
        base.Initialize(postgresConnectionString, rabbitMqConnectionString);

        var builder = Host.CreateApplicationBuilder();

        builder.Logging.ClearProviders();
        builder.Logging.AddXunitOutput(base.Output);

        builder.Services.AddDockerMonitoring(
            containerName: "performancetest-postgres",
            samplingInterval: TimeSpan.FromMilliseconds(500));

        builder.Services.AddDockerMonitoring(
            containerName: "performancetest-rabbitmq",
            samplingInterval: TimeSpan.FromMilliseconds(500));

        builder.Services.Configure<HostOptions>(options =>
        {
            options.ShutdownTimeout = TimeSpan.FromSeconds(30);
        });

        _host = builder.Build();

        // Resolve monitors individually by container name
        var monitors = _host.Services.GetServices<IDockerMonitor>().ToList();
        PostgresMonitor = monitors.First(m => m.ContainerName == "performancetest-postgres");
        RabbitMqMonitor = monitors.First(m => m.ContainerName == "performancetest-rabbitmq");
    }

    /// <summary>
    /// Starts all BackgroundServices (begins monitoring).
    /// </summary>
    public async Task StartMonitoringAsync(CancellationToken cancellationToken = default)
    {
        if (_host == null)
            throw new InvalidOperationException("System not initialized");

        await _host.StartAsync(cancellationToken);
    }

    /// <summary>
    /// Stops all BackgroundServices (ends monitoring).
    /// Safe to call multiple times (idempotent).
    /// </summary>
    public async Task StopMonitoringAsync(CancellationToken cancellationToken = default)
    {
        if (_host == null)
            return; // Already stopped or never started

        await _host.StopAsync(cancellationToken);
    }

    /// <summary>
    /// Disposes host and all services.
    /// Defensively stops monitoring if still running (tests may forget to call StopMonitoringAsync).
    /// </summary>
    public override void Dispose()
    {
        if (_host != null)
        {
            try
            {
                // Defensive cleanup: stop monitoring if still running
                // Synchronous wait is acceptable in Dispose() context
                StopMonitoringAsync().GetAwaiter().GetResult();
            }
            catch
            {
                // Ignore errors (already stopped or never started)
            }

            _host.Dispose();
            _host = null;
        }

        base.Dispose();
    }
}
```

**Key Patterns:**

**Individual Monitor Properties:**
- Exposes `PostgresMonitor` and `RabbitMqMonitor` as separate properties
- Tests access monitors explicitly (not via iteration)
- Consistent with base System pattern (PostgresConnection, RabbitMqConnection)

**IHost Lifecycle:**
- `StartAsync()` begins monitoring (BackgroundServices start)
- `StopAsync()` ends monitoring (BackgroundServices stop gracefully)
- `Dispose()` cleans up resources (defensively stops if still running)

**Defensive Cleanup:**
- `Dispose()` calls `StopMonitoringAsync()` if host is still running
- Idempotent: safe to stop multiple times

**Test-Friendly Sampling:**
- Uses 500ms interval (faster than production 3000ms)
- Generates more samples in shorter test duration

```csharp
using JoanComasFdz.AssertingThat;
using Xunit;

namespace PerformanceTester.DockerMonitoring.IntegrationTests.Infrastructure;

public static class DockerMonitoringAssertions
{
    public static AssertingThat<IDockerMonitor> HasCollectedMetrics(
        this AssertingThat<IDockerMonitor> assertingThat)
    {
        var monitor = assertingThat.InstanceToAssert;
        var metrics = monitor.GetCollectedMetrics();

        Assert.NotEmpty(metrics);

        return assertingThat;
    }

    public static AssertingThat<IDockerMonitor> HasMinimumSampleCount(
        this AssertingThat<IDockerMonitor> assertingThat,
        int expectedMinimum)
    {
        var monitor = assertingThat.InstanceToAssert;
        var metrics = monitor.GetCollectedMetrics();

        Assert.True(metrics.Count >= expectedMinimum,
            $"{monitor.ContainerName} expected >= {expectedMinimum} samples, got {metrics.Count}");

        return assertingThat;
    }

    public static AssertingThat<IDockerMonitor> HasValidCpuPercentages(
        this AssertingThat<IDockerMonitor> assertingThat)
    {
        var monitor = assertingThat.InstanceToAssert;
        var metrics = monitor.GetCollectedMetrics();

        foreach (var metric in metrics)
        {
            Assert.True(metric.CpuPercent >= 0,
                $"{monitor.ContainerName} CPU% must be >= 0, got {metric.CpuPercent}");
            Assert.True(metric.CpuPercent <= 1000,
                $"{monitor.ContainerName} CPU% exceeds reasonable bound, got {metric.CpuPercent}");
        }

        return assertingThat;
    }

    public static AssertingThat<IDockerMonitor> HasValidMemoryMeasurements(
        this AssertingThat<IDockerMonitor> assertingThat)
    {
        var monitor = assertingThat.InstanceToAssert;
        var metrics = monitor.GetCollectedMetrics();

        foreach (var metric in metrics)
        {
            Assert.True(metric.MemoryMB > 0,
                $"{monitor.ContainerName} Memory must be > 0 MB, got {metric.MemoryMB}");
            Assert.True(metric.MemoryMB <= 100_000,
                $"{monitor.ContainerName} Memory exceeds reasonable bound, got {metric.MemoryMB} MB");
        }

        return assertingThat;
    }

    public static AssertingThat<IDockerMonitor> HasMetricsInChronologicalOrder(
        this AssertingThat<IDockerMonitor> assertingThat)
    {
        var monitor = assertingThat.InstanceToAssert;
        var metrics = monitor.GetCollectedMetrics();
        var timestamps = metrics.Select(m => m.Timestamp).ToList();

        Assert.Equal(timestamps.OrderBy(t => t).ToList(), timestamps);

        return assertingThat;
    }
```

## Notes and Considerations

### Performance Expectations

- **First sample:** ~100-200ms (Docker API call overhead)
- **Subsequent samples:** ~50-100ms (steady state)
- **Memory overhead:** ~10-20 MB per monitor instance
- **Channel overhead:** Negligible (unbounded, in-memory)

### Cross-Platform Considerations

- **Linux:** Uses Unix socket (`/var/run/docker.sock`)
- **Windows:** Uses named pipe (`npipe://./pipe/docker_engine`)
- **macOS:** Uses Unix socket (same as Linux)
- **Docker Desktop:** Works with all platforms
- **Docker Engine:** Linux only (no Docker Desktop)

### Known Limitations

- **Container name matching:** Exact match required (no wildcards)
- **Container not found:** Debug logging only (not warning, too noisy)
- **Multi-host:** Not supported (single Docker daemon only)
- **Swarm mode:** Not tested (single node only)

### Future Enhancements (Out of Scope)

- Support for container name wildcards
- Support for multiple Docker hosts
- Network I/O metrics
- Disk I/O metrics
- Container event stream monitoring
