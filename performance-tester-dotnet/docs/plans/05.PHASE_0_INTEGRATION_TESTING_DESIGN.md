## Overview

### Purpose

Create `PerformanceTester.IntegrationTesting` as a shared project that provides foundational infrastructure for all integration test projects. This eliminates duplication of container management and logging configuration across 6+ test projects while maintaining flexibility for each slice to implement its own testing patterns.

### Why Phase 0?

During design, we identified that all integration test projects will need:
- Container lifecycle management (PostgreSQL, RabbitMQ)
- Logging capture to test output
- Common test lifecycle patterns

Rather than duplicating this infrastructure across every test project, we create it once upfront as the foundation for all testing.

### Scope

**What's Included:**
- ✅ ContainerManager singleton (PostgreSQL + RabbitMQ)
- ✅ IntegrationTestBase abstract class with generic `<TSystem>` parameter (containers + logging + system initialization)
- ✅ Microsoft.Extensions.Logging integration for test output capture
- ✅ Default `System` class providing PostgreSQL and RabbitMQ connection wrappers
- ✅ `PostgreSQL` helper class (connection string wrapper for test configuration)
- ✅ `RabbitMQ` helper class (connection string wrapper for test configuration)

**What's NOT Included (Each Test Project Implements):**
- ❌ Custom System implementations (optional - test projects can extend the base System class for domain-specific needs)
- ❌ Custom assertions - each project implements as needed
- ❌ Data cleanup logic - each project implements its own

**Design Philosophy:**
The shared infrastructure provides a **default System class** that works for simple test scenarios. Test projects can choose between:
1. **Simple approach:** Use `IntegrationTestBase<System>` with the default System class
2. **Extended approach:** Create custom `MySystem : System` and use `IntegrationTestBase<MySystem>` for domain-specific functionality

This generic pattern provides both **convenience** (default implementation) and **flexibility** (extensible via inheritance).

## ContainerManager Design

### Responsibility

Manage PostgreSQL and RabbitMQ container lifecycle as a singleton across all tests in a test run.

### Implementation Pattern

```csharp
namespace PerformanceTester.IntegrationTesting;

/// <summary>
/// Manages container lifecycle as a singleton.
/// Ensures containers are started once and reused across all tests.
/// Thread-safe using double-check locking pattern.
/// Containers are NEVER stopped programmatically - they remain running for entire test session.
/// </summary>
public sealed class ContainerManager
{
    private static readonly Lazy<ContainerManager> s_instance =
        new(() => new ContainerManager());

    public static ContainerManager Instance => s_instance.Value;

    private PostgreSqlContainer? _postgresContainer;
    private RabbitMqContainer? _rabbitMqContainer;
    private readonly SemaphoreSlim _startLock = new(1, 1);
    private bool _started = false;

    // Connection strings populated after startup
    public string PostgresConnectionString { get; private set; } = string.Empty;
    public string RabbitMqConnectionString { get; private set; } = string.Empty;

    private ContainerManager() { } // Private constructor for singleton

    /// <summary>
    /// Ensures containers are started (idempotent).
    /// Thread-safe, only starts containers once.
    /// Includes health checks to verify containers are ready to accept connections.
    /// </summary>
    public async Task EnsureStartedAsync(CancellationToken ct = default)
    {
        if (_started) return;

        await _startLock.WaitAsync(ct);
        try
        {
            if (_started) return;

            await StartContainersAsync(ct);
            _started = true;
        }
        finally
        {
            _startLock.Release();
        }
    }

    private async Task StartContainersAsync(CancellationToken ct)
    {
        try
        {
            // Build PostgreSQL container
            _postgresContainer = new PostgreSqlBuilder()
                .WithImage("postgres:16-alpine")
                .WithDatabase("testdb")
                .WithUsername("testuser")
                .WithPassword("testpass")
                .WithPortBinding(5432, true) // Random host port
                .Build();

            // Build RabbitMQ container
            _rabbitMqContainer = new RabbitMqBuilder()
                .WithImage("rabbitmq:3.13-management-alpine")
                .WithUsername("testuser")
                .WithPassword("testpass")
                .WithPortBinding(5672, true)  // AMQP port
                .WithPortBinding(15672, true) // Management UI
                .Build();

            // Start both containers in parallel for faster initialization
            await Task.WhenAll(
                _postgresContainer.StartAsync(ct),
                _rabbitMqContainer.StartAsync(ct)
            );

            // Store connection strings
            PostgresConnectionString = _postgresContainer.GetConnectionString();
            RabbitMqConnectionString = _rabbitMqContainer.GetConnectionString();

            // Wait for containers to be ready to accept connections
            await Task.WhenAll(
                WaitForPostgresReadyAsync(ct),
                WaitForRabbitMQReadyAsync(ct)
            );
        }
        catch
        {
            // Clean up any partially-started containers
            if (_postgresContainer != null)
                await _postgresContainer.DisposeAsync();
            if (_rabbitMqContainer != null)
                await _rabbitMqContainer.DisposeAsync();

            _postgresContainer = null;
            _rabbitMqContainer = null;
            PostgresConnectionString = string.Empty;
            RabbitMqConnectionString = string.Empty;

            throw; // Re-throw to caller
        }
    }

    /// <summary>
    /// Waits for PostgreSQL to be ready to accept connections.
    /// Polls connection until successful or timeout (30 seconds).
    /// </summary>
    private async Task WaitForPostgresReadyAsync(CancellationToken ct)
    {
        var timeout = TimeSpan.FromSeconds(30);
        var stopwatch = Stopwatch.StartNew();

        while (stopwatch.Elapsed < timeout)
        {
            try
            {
                using var connection = new NpgsqlConnection(PostgresConnectionString);
                await connection.OpenAsync(ct);
                return; // Success!
            }
            catch
            {
                await Task.Delay(100, ct); // Wait and retry
            }
        }

        throw new TimeoutException(
            "PostgreSQL container did not become ready within 30 seconds");
    }

    /// <summary>
    /// Waits for RabbitMQ to be ready to accept connections.
    /// Polls connection until successful or timeout (30 seconds).
    /// </summary>
    private async Task WaitForRabbitMQReadyAsync(CancellationToken ct)
    {
        var timeout = TimeSpan.FromSeconds(30);
        var stopwatch = Stopwatch.StartNew();

        while (stopwatch.Elapsed < timeout)
        {
            try
            {
                var factory = new ConnectionFactory
                {
                    Uri = new Uri(RabbitMqConnectionString)
                };
                using var connection = await factory.CreateConnectionAsync(ct);
                return; // Success!
            }
            catch
            {
                await Task.Delay(100, ct); // Wait and retry
            }
        }

        throw new TimeoutException(
            "RabbitMQ container did not become ready within 30 seconds");
    }
}
```

### Key Design Decisions

**Singleton Pattern:**
- One instance per test run
- Thread-safe using `Lazy<T>` + double-check locking
- Containers start once, reused across all tests

**Container Configuration:**
- Random host ports enable parallel test runs
- Lightweight Alpine images for faster startup
- Standard credentials for simplicity

**Lifecycle:**
- Containers start on first `EnsureStartedAsync()` call (~20-25 seconds including health checks)
- Subsequent calls are no-ops (idempotent)
- Health checks ensure containers are ready before returning (prevents "connection refused" errors)
- **Containers NEVER stopped programmatically** - remain running for entire test session
- Enables test parallelization (multiple test processes can share containers)

**Health Checks:**
- PostgreSQL: Polls connection until successful (up to 30 seconds)
- RabbitMQ: Polls connection until successful (up to 30 seconds)
- Prevents tests from failing with "connection refused" errors
- Adds ~2-5 seconds to startup time

**Error Handling:**
- Failed startup cleans up partially-started containers
- State reset on failure (can retry startup)
- Exceptions propagated to caller with context

**Container Cleanup (Manual Only):**
- Containers are NEVER disposed by ContainerManager
- **Why:** Stopping containers would kill parallel test execution across test processes
- **Local development**: Leave containers running indefinitely (fast for repeated test runs)
- **CI/CD**: Manually stop containers AFTER entire test suite completes
  - Example: `docker stop $(docker ps -q --filter ancestor=postgres:16-alpine)`
  - Example: `docker stop $(docker ps -q --filter ancestor=rabbitmq:3.13-management-alpine)`
- **Test isolation:** Achieved via per-test DI containers, not container restarts

## IntegrationTestBase Design

### Responsibility

Provide container initialization, logging capture, and system initialization using a generic pattern. Test projects can use the default `System` class or provide custom implementations.

### Implementation Pattern

```csharp
namespace PerformanceTester.IntegrationTesting;

/// <summary>
/// Base class for all integration tests.
/// Provides container initialization and logging capture.
/// Generic TSystem parameter allows test projects to use default or custom System implementations.
/// </summary>
public abstract class IntegrationTestBase<TSystem> : IAsyncLifetime where TSystem : System
{
    private static readonly ContainerManager s_containers = ContainerManager.Instance;

    /// <summary>
    /// xUnit test output helper for capturing logs and diagnostic messages.
    /// </summary>
    protected ITestOutputHelper Output { get; }

    /// <summary>
    /// System instance providing access to infrastructure components.
    /// Type is determined by TSystem generic parameter.
    /// </summary>
    protected TSystem System { get; private set; }

    protected IntegrationTestBase(ITestOutputHelper output)
    {
        Output = output;
        // Create instance of TSystem using Activator (allows default constructor)
        System = Activator.CreateInstance<TSystem>();
        // Note: Logging configuration is handled by each test project's SystemUnderTest class
        // using LoggingTestExtensions.AddXunitOutput(output)
    }

    /// <summary>
    /// Called before each test.
    /// Ensures containers are started and initializes System with connection strings.
    /// Override to add project-specific cleanup logic.
    /// </summary>
    public virtual async Task InitializeAsync()
    {
        Output.WriteLine("=== Ensuring containers started ===");
        await s_containers.EnsureStartedAsync();
        System.Initialize(s_containers.PostgresConnectionString, s_containers.RabbitMqConnectionString);
        Output.WriteLine("=== Containers ready ===");
    }

    /// <summary>
    /// Called after each test.
    /// Intentionally empty - data persists for debugging.
    /// Override to add project-specific cleanup (e.g., dispose System instance).
    /// </summary>
    public virtual async Task DisposeAsync()
    {
        await Task.CompletedTask;
    }
}
```

### Key Design Decisions

**Generic Pattern:**
- Uses `TSystem` generic parameter with `where TSystem : System` constraint
- Test projects can use default `System` or extend it for domain-specific needs
- Provides both convenience (default) and flexibility (extensible)

**Two-Phase Initialization:**
- **Phase 1 (Constructor):** Create TSystem instance using `Activator.CreateInstance<TSystem>()`
- **Phase 2 (InitializeAsync):** Call `System.Initialize()` with connection strings after containers are ready
- This pattern allows System subclasses to have parameterless constructors

**Activator Pattern:**
- Uses `Activator.CreateInstance<TSystem>()` to dynamically instantiate the generic type
- Requires TSystem to have a parameterless constructor
- Allows test projects to provide custom System implementations without changing base class

**Virtual Methods:**
- `InitializeAsync()` and `DisposeAsync()` are virtual
- Test projects override to add cleanup logic
- Must call `base.InitializeAsync()` to ensure containers start and System is initialized

**Shared Infrastructure:**
- Provides default `System` class with PostgreSQL and RabbitMQ properties
- Test projects can extend System for domain-specific functionality
- Balance between shared convenience and per-project flexibility

## Logging Infrastructure

### Responsibility

Capture all service logs from the code under test and write them to xUnit test output for debugging.

### Components

**1. XunitLogger** - ILogger implementation

```csharp
namespace PerformanceTester.IntegrationTesting.Logging;

/// <summary>
/// ILogger implementation that writes to xUnit ITestOutputHelper.
/// </summary>
internal sealed class XunitLogger : ILogger
{
    private readonly ITestOutputHelper _output;
    private readonly string _categoryName;

    public XunitLogger(ITestOutputHelper output, string categoryName)
    {
        _output = output;
        _categoryName = categoryName;
    }

    public IDisposable? BeginScope<TState>(TState state) where TState : notnull => null;

    public bool IsEnabled(LogLevel logLevel) => true;

    public void Log<TState>(
        LogLevel logLevel,
        EventId eventId,
        TState state,
        Exception? exception,
        Func<TState, Exception?, string> formatter)
    {
        var message = formatter(state, exception);
        _output.WriteLine($"[{DateTime.Now:HH:mm:ss} {logLevel}] {_categoryName}: {message}");

        if (exception != null)
        {
            _output.WriteLine($"Exception: {exception}");
        }
    }
}
```

**2. XunitLoggerProvider** - ILoggerProvider factory

```csharp
namespace PerformanceTester.IntegrationTesting.Logging;

/// <summary>
/// Logger provider that creates XunitLogger instances.
/// </summary>
public sealed class XunitLoggerProvider : ILoggerProvider
{
    private readonly ITestOutputHelper _output;

    public XunitLoggerProvider(ITestOutputHelper output)
    {
        _output = output;
    }

    public ILogger CreateLogger(string categoryName)
    {
        return new XunitLogger(_output, categoryName);
    }

    public void Dispose() { }
}
```

**3. LoggingTestExtensions** - Extension methods

```csharp
namespace PerformanceTester.IntegrationTesting.Logging;

/// <summary>
/// Extension methods for configuring Microsoft.Extensions.Logging with xUnit output.
/// </summary>
public static class LoggingTestExtensions
{
    /// <summary>
    /// Adds xUnit test output as a logging destination.
    /// All service logs will appear in test output.
    /// </summary>
    public static ILoggingBuilder AddXunitOutput(
        this ILoggingBuilder builder,
        ITestOutputHelper output)
    {
        builder.AddProvider(new XunitLoggerProvider(output));
        return builder;
    }
}
```

### Usage in Test Projects

```csharp
// In SystemUnderTest class (each test project implements its own)
private SystemUnderTest(ITestOutputHelper output)
{
    var builder = Host.CreateApplicationBuilder();

    // Configure logging to write to test output
    builder.Logging.ClearProviders();
    builder.Logging.AddXunitOutput(output);

    // Register production services
    builder.Services.AddInfrastructure(...);

    _host = builder.Build();
}
```

### Benefits

- All service logs automatically appear in test output
- No additional configuration per test
- Failed tests show complete logging context
- Debugging becomes significantly easier

## Usage Pattern

### How Test Projects Use This Infrastructure

Each integration test project has two options:

#### Option 1: Simple Approach (Default System)

Use the provided `System` class directly with `IntegrationTestBase<System>`:

```csharp
public class MyTests(ITestOutputHelper output) : IntegrationTestBase<System>(output)
{
    [Fact]
    public async Task Test()
    {
        // Use System.PostgreSQL and System.RabbitMQ directly
        var connectionString = System.PostgreSQL.ConnectionString;
    }
}
```

#### Option 2: Extended Approach (Custom System)

Extend the `System` class for domain-specific functionality:

```csharp
public class InfrastructureSystem : System
{
    public Infrastructure Infrastructure { get; private set; } = null!;

    internal new void Initialize(string postgresConnectionString, string rabbitMqConnectionString)
    {
        base.Initialize(postgresConnectionString, rabbitMqConnectionString);
        // Add domain-specific initialization
        Infrastructure = new Infrastructure(postgresConnectionString, rabbitMqConnectionString);
    }
}

public class InfrastructureTests(ITestOutputHelper output)
    : IntegrationTestBase<InfrastructureSystem>(output)
{
    [Fact]
    public async Task Test()
    {
        // Use System.Infrastructure, System.PostgreSQL, System.RabbitMQ
        await System.Infrastructure.SomeMethod();
    }
}
```

**Key Design Insight:**

Notice that `InfrastructureSystem` adds a **module property** (`Infrastructure`), not individual APIs. This is intentional:

- **System role:** Provide test helpers + modules
- **Module role:** Wrap DI container and expose production APIs
- **Production API role:** Actual functionality being tested

Pattern hierarchy:
```
System (base)
├── PostgreSQL (test helper)
├── RabbitMQ (test helper)
└── Infrastructure (module) ← Added by InfrastructureSystem
    ├── ServiceDiscovery (production API)
    ├── Database (production API)
    └── RabbitMQ (production API)
```

This separation ensures:
- Test helpers never pollute production code
- Modules encapsulate DI container lifecycle
- Production APIs remain testable and isolated

#### xUnit Test Class Lifecycle

**Critical Understanding:** xUnit creates a **new test class instance for each test method** by default.

```csharp
public class MyTests(ITestOutputHelper output) : IntegrationTestBase<System>(output)
{
    [Fact] public void Test1() { } // New MyTests instance created

    [Fact] public void Test2() { } // Another new MyTests instance created
}
```

**What This Means for Our Design:**

| Component | Lifecycle | Reason |
|-----------|-----------|--------|
| `ContainerManager` | **Singleton** (shared) | Expensive (~20s startup), reused across ALL tests |
| `IntegrationTestBase<TSystem>` subclass | **Per-test** (new instance) | xUnit default behavior |
| `TSystem` (System or custom) | **Per-test** (new instance) | Created via Activator in constructor, initialized in InitializeAsync |

**Result:** Maximum test isolation with acceptable overhead.

**Note:** If you want shared state across tests, you must explicitly use `IClassFixture<T>` (shared per test class) or `ICollectionFixture<T>` (shared across test classes). We don't use these patterns for System - only for expensive container infrastructure.


**Step 2: Write Tests (Simple Approach)**

**Step 2 (Alternative): Create Custom System (Extended Approach)**

For domain-specific functionality, extend the `System` class:

```csharp
// PerformanceTester.Infrastructure.IntegrationTests/InfrastructureSystem.cs
namespace PerformanceTester.Infrastructure.IntegrationTests;

/// <summary>
/// Custom system for Infrastructure integration tests.
/// Extends base System with Infrastructure-specific components.
/// </summary>
public class InfrastructureSystem : System
{
    public Infrastructure Infrastructure { get; private set; } = null!;

    internal new void Initialize(string postgresConnectionString, string rabbitMqConnectionString)
    {
        // Initialize base System (PostgreSQL, RabbitMQ wrappers)
        base.Initialize(postgresConnectionString, rabbitMqConnectionString);

        // Initialize Infrastructure-specific components
        var builder = Host.CreateApplicationBuilder();
        builder.Logging.ClearProviders();
        builder.Services.AddInfrastructure(postgresConnectionString, rabbitMqConnectionString);

        var host = builder.Build();
        Infrastructure = host.Services.GetRequiredService<Infrastructure>();
    }
}

// Tests use custom system
public class DatabaseTests(ITestOutputHelper output)
    : IntegrationTestBase<InfrastructureSystem>(output)
{
    [Fact]
    public async Task GivenDatabaseWhenClearedThenSucceeds()
    {
        // Arrange - containers running, InfrastructureSystem initialized
        // Use System.Infrastructure, System.PostgreSQL, System.RabbitMQ
        var result = await System.Infrastructure.Database.ClearDatabaseAsync(...);

        // Assert
        Assert.True(result);
    }
}
```

### Benefits of This Pattern

**Shared Infrastructure:**
- ✅ No duplication of container management code
- ✅ No duplication of logging configuration
- ✅ Consistent container lifecycle across all test projects
- ✅ Single place to update container versions or configuration
- ✅ Default `System`, `PostgreSQL`, and `RabbitMQ` classes provided for simple scenarios

**Generic Pattern Advantages:**
- ✅ **Convenience:** Default `System` class works for simple tests (`IntegrationTestBase<System>`)
- ✅ **Flexibility:** Extend `System` for domain-specific functionality (`IntegrationTestBase<CustomSystem>`)
- ✅ **Type Safety:** Generic constraint `where TSystem : System` ensures correct usage
- ✅ **No Boilerplate:** Test projects don't need custom base classes unless they want customization
- ✅ **Activator Pattern:** Dynamic instantiation allows parameterless constructors in custom systems

**Developer Ergonomics:**
- ✅ Minimal boilerplate for simple tests (inherit from `IntegrationTestBase<System>`)
- ✅ Clear separation: `System.PostgreSQL`, `System.RabbitMQ` for infrastructure
- ✅ Maximum test isolation: Fresh System instance per test
- ✅ Easy to extend: Add custom properties to System subclasses as needed
- ✅ Supports parallel test execution (no global cleanup, no shared state)
- ✅ Primary constructor syntax supported for concise test classes

### Test Specification

```csharp
namespace PerformanceTester.IntegrationTesting.Tests;

/// <summary>
/// Verifies Phase 0 infrastructure works correctly before Phase 1 implementation.
/// This test project validates the shared integration testing infrastructure.
/// Uses the default System class via generic parameter.
/// </summary>
public class IntegrationTestBaseTests(ITestOutputHelper output) : IntegrationTestBase<System>(output)
{

    [Fact]
    public async Task ContainerManager_StartsPostgreSQLContainer_Successfully()
    {
        // Arrange - already done by base class InitializeAsync

        // Act - attempt to connect to PostgreSQL
        using var connection = new NpgsqlConnection(System.PostgreSQL.ConnectionString);
        await connection.OpenAsync();

        var command = connection.CreateCommand();
        command.CommandText = "SELECT 1";
        var result = await command.ExecuteScalarAsync();

        // Assert - connection successful and can query
        Assert.NotNull(connection);
        Assert.Equal(ConnectionState.Open, connection.State);
        Assert.Equal(1, result);

        Output.WriteLine($"✓ PostgreSQL connection string: {System.PostgreSQL.ConnectionString}");
        Output.WriteLine($"✓ PostgreSQL query result: {result}");
    }

    [Fact]
    public async Task ContainerManager_StartsRabbitMQContainer_Successfully()
    {
        // Arrange - already done by base class

        // Act - attempt to connect to RabbitMQ and publish/consume message
        var factory = new ConnectionFactory
        {
            Uri = new Uri(System.RabbitMQ.ConnectionString)
        };
        using var connection = await factory.CreateConnectionAsync();
        using var channel = await connection.CreateChannelAsync();

        var queueName = "test-queue-verification";
        await channel.QueueDeclareAsync(queue: queueName, durable: false, exclusive: true,
            autoDelete: true, arguments: null);

        var message = "test-message";
        var body = Encoding.UTF8.GetBytes(message);
        await channel.BasicPublishAsync(exchange: "", routingKey: queueName, body: body);

        var result = await channel.BasicGetAsync(queueName, autoAck: true);

        // Assert - connection successful and can publish/consume
        Assert.NotNull(connection);
        Assert.True(connection.IsOpen);
        Assert.NotNull(result);
        Assert.Equal(message, Encoding.UTF8.GetString(result.Body.ToArray()));

        Output.WriteLine($"✓ RabbitMQ connection string: {System.RabbitMQ.ConnectionString}");
        Output.WriteLine($"✓ RabbitMQ message: {message}");
    }

    [Fact]
    public void ContainerManager_IsSingleton_AcrossMultipleCalls()
    {
```

## Architecture Decision Record

### Key Decisions Summary

| Decision | Choice | Rationale |
|----------|--------|-----------|
| **Container Lifecycle** | Singleton (Lazy<T>) | Performance: ~20s startup, reused across all tests |
| **System Lifecycle** | Per-test instance | Test isolation: fresh wrapper per test |
| **Infrastructure (SUT) Lifecycle** | Per-test instance | Test isolation: fresh DI container per test (~100ms overhead) |
| **Test Class Lifecycle** | Per-test instance | xUnit default: new test class per test method |
| **Disposal Strategy** | Disposal chain: Test → System → Infrastructure → IHost | Proper resource cleanup after each test |
| **Health Checks** | Poll until ready (30s timeout) | Robustness: prevent "connection refused" errors |
| **Error Handling** | Clean up partial state on failure | Reliability: failed startup can be retried |
| **Logging Configuration** | Per SystemUnderTest class | Flexibility: each test project configures its own logging |
| **ITestOutputHelper Threading** | Per-test, not shared | xUnit requirement: tied to specific test instance |
| **Container Cleanup** | Manual only (never programmatic) | Test parallelization: containers shared across processes |

### Performance Expectations

- **First test in run**: ~20-25 seconds (container startup + health checks)
- **Subsequent tests**: ~100ms (per-test DI container construction)
- **Health check overhead**: ~2-5 seconds (included in first test)
- **Test isolation overhead**: Acceptable for integration tests

### Why Per-Test Infrastructure?

We chose **per-test Infrastructure instances** (fresh DI container) over **singleton Infrastructure** for these reasons:

1. **Maximum Test Isolation**: No shared state between tests
2. **Parallel Test Safety**: Tests can run in parallel without conflicts
3. **Acceptable Performance**: ~100ms per test is fast for integration tests
4. **Simplified Cleanup**: Each test starts clean, no complex cleanup logic
5. **Easier Debugging**: Failed tests don't pollute state for subsequent tests

**Trade-off**: Slightly slower (~100ms per test) but much more reliable and maintainable.
