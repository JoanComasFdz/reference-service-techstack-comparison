## Overview

This document describes the design and implementation of the `IntegrationTestBase<TSystem>` pattern used throughout the Performance Tester .NET project.

**Important:** This project uses a **shared integration testing infrastructure** (`PerformanceTester.IntegrationTesting`) that provides:
- Container management (PostgreSQL + RabbitMQ)
- Logging capture to test output
- Generic `IntegrationTestBase<TSystem>` base class
- Default `System` class with PostgreSQL and RabbitMQ connection wrappers

Test projects can inherit from `IntegrationTestBase<System>` (simple approach) or create custom System implementations for domain-specific functionality. See `docs/plans/05.PHASE_0_INTEGRATION_TESTING_DESIGN.md` for the complete shared infrastructure design.

### Purpose

The `IntegrationTestBase<TSystem>` generic pattern provides:

1. **Convenience & Flexibility** - Default System for simple tests, extensible for complex scenarios
2. **Automatic Container Management** - Handles Testcontainers lifecycle transparently
3. **Clear Separation** - Test helpers vs production APIs
4. **Developer Ergonomics** - Minimal boilerplate, maximum productivity
5. **Type Safety** - Generic constraint ensures correct System usage

### Philosophy

The integration testing infrastructure balances **convenience** (default implementations) with **flexibility** (extensibility via generics).

**Design Trade-offs:**
- ✅ Simple tests use `IntegrationTestBase<System>` directly (zero boilerplate)
- ✅ Complex tests extend `System` class for domain-specific needs
- ✅ Generic pattern provides type-safe access to system components
- ✅ Shared infrastructure eliminates duplication across test projects
- ✅ Makes tests more readable and maintainable

**Justification:** For testing infrastructure, developer productivity and test clarity are more important than strict adherence to production code patterns. The generic pattern provides the best of both worlds.

## Architecture

### Component Overview

```
Shared Infrastructure (PerformanceTester.IntegrationTesting)
├── IntegrationTestBase<TSystem> (Generic Base Class)
│   ├── Inherits from: IAsyncLifetime
│   ├── Provides: Protected TSystem System property
│   ├── Manages: Container initialization, system initialization, lifecycle hooks
│   └── Generic constraint: where TSystem : System
│
├── ContainerManager (Singleton, Internal)
│   ├── Responsibility: Container lifecycle with health checks
│   ├── Scope: Singleton per test run
│   └── Visibility: Internal (only shared infrastructure accesses directly)
│
├── System (Default Implementation)
│   ├── PostgreSQL - Connection string wrapper
│   ├── RabbitMQ - Connection string wrapper
│   └── Initialize() - Called by IntegrationTestBase after containers start
│
└── Logging Infrastructure
    ├── XunitLogger - ILogger → ITestOutputHelper
    ├── XunitLoggerProvider - ILoggerProvider factory
    └── LoggingTestExtensions - AddXunitOutput() extension

Test Project (Inherits from Shared Infrastructure)
├── Simple Approach
│   └── Tests inherit: IntegrationTestBase<System>
│       └── Use System.PostgreSQL, System.RabbitMQ directly
│
└── Extended Approach (Optional)
    ├── Custom System Implementation
    │   └── class MySystem : System
    │       ├── Override Initialize() for custom setup
    │       └── Add domain-specific properties
    └── Tests inherit: IntegrationTestBase<MySystem>
        └── Use MySystem.PostgreSQL, MySystem.CustomProperty
```

### Design Principles

1. **Generic Pattern** - `IntegrationTestBase<TSystem>` allows both default and custom System implementations
2. **Shared Infrastructure** - Container management, logging, base System class provided by shared project
3. **Private Container Management** - Tests never directly control containers (handled by IntegrationTestBase)
4. **Per-Test System Instances** - Fresh TSystem instance per test (created via Activator, initialized in InitializeAsync)
5. **Automatic Container Initialization** - Containers started once and reused (singleton ContainerManager)
6. **Two-Phase Initialization** - Constructor creates System, InitializeAsync provides connection strings
7. **Automatic Cleanup** - Per-test System instances, data persists in containers for debugging

## Container Lifecycle Management

### Strategy

**Container Reuse:** Containers start once and are reused across all tests in a session.

**Why Reuse?**
- PostgreSQL container startup: ~3-10 seconds
- RabbitMQ container startup: ~10-20 seconds
- 50 test classes × 2 containers = **10-25 minutes** of overhead
- With reuse: **~20 seconds** total startup time

### Lifecycle Phases

```
Test Run Start
    ↓
[ContainerManager Singleton Created]
    ↓
[PostgreSQL Container Started] ← 5 seconds
    ↓
[RabbitMQ Container Started]  ← 15 seconds
    ↓
┌─────────────────────────────────────┐
│  Test Execution Phase               │
│  ┌──────────────────────────────┐   │
│  │ Test Class 1                 │   │
│  │   [Data Cleanup] ← BEFORE    │   │
│  │   Test1() ───────→ Pass      │   │
│  │   [Data Cleanup] ← BEFORE    │   │
│  │   Test2() ───────→ Pass      │   │
│  └──────────────────────────────┘   │
│  ┌──────────────────────────────┐   │
│  │ Test Class 2                 │   │
│  │   [Data Cleanup] ← BEFORE    │   │
│  │   Test1() ───────→ Pass      │   │
│  └──────────────────────────────┘   │
│  ...                                │
└─────────────────────────────────────┘
    ↓
Test Run Complete
    ↓
[Last Test's Data Remains] ← Available for manual inspection
    ↓
[Containers Keep Running] ← For debugging
```

### Cleanup Strategy

**Before Each Test (in InitializeAsync):**
- ✅ Fresh System → Infrastructure → DI container per test
- ✅ Data cleanup logic added when patterns emerge (test-specific, not global)
- ❌ Do NOT restart containers

**After Each Test (in DisposeAsync):**
- ✅ Dispose System → Infrastructure → IHost (cleanup DI container)
- ✅ Data persists in containers for potential manual review
- ❌ Do NOT clean data from containers

**After Test Run Completes:**
- ✅ Last test's data remains in containers for debugging
- ✅ **Containers are NEVER stopped programmatically**
- ✅ Containers remain running for entire test session
- ✅ Enables test parallelization (shared containers across test processes)

**Container Cleanup (Manual Only):**
- **Local development:** Leave containers running indefinitely (fast for repeated test runs)
- **CI/CD:** Manually stop containers AFTER entire test suite completes
  - Example: `docker stop $(docker ps -q --filter ancestor=postgres:16-alpine)`
  - Example: `docker stop $(docker ps -q --filter ancestor=rabbitmq:3.13-management-alpine)`
- **Test isolation:** Achieved via per-test DI containers, not container restarts

### Test Parallelization Support

**Container Lifecycle supports parallel execution** since containers are singletons shared across test processes.

**Important:** Tests must use unique resource identifiers to avoid conflicts when running in parallel.

**How to Achieve Parallelization:**
- ✅ Use unique identifiers per test (GUIDs, timestamps, test names)
- ✅ Generate unique queue names: `$"queue-{Guid.NewGuid():N}"`
- ✅ Generate unique database names: `$"testdb_{Guid.NewGuid():N}"`
- ❌ Never use hardcoded queue names like "test-queue" across multiple tests
- ❌ Never use hardcoded database names like "testdb" across multiple tests

**Example - RabbitMQ Queue Isolation:**

```csharp
public class EventConsumerIntegrationTests : IntegrationTest
{
    // Generate unique queue name per test to enable parallel execution
    private string GenerateQueueName() => $"performancetesterdotnet-{Guid.NewGuid():N}";

    [Fact]
    public async Task StartTrackingEventsAsync_WhenEventsPublished_ShouldCompleteWhenTargetReached()
    {
        // Arrange - Each test gets its own unique queue
        var queueName = GenerateQueueName();
        System.CreateEventConsuming(queueName);

        await System.RabbitMQ.DeclareAndBindQueueAsync(queueName, ExchangeName, RoutingKey);

        // ... test logic uses the unique queue
    }
}
```

**Shared vs. Isolated Resources:**
- **Shared:** Docker containers (reused for performance)
- **Isolated:** Queue names, database table data (must be unique per test)

**Benefits:**
- ✅ Tests can run concurrently without interference
- ✅ Faster test suite execution on multi-core machines
- ✅ Better CI/CD performance
- ✅ Container singleton pattern remains valid

## The System Pattern

### Architecture

**Naming Convention:** The system under test class should be **named after the project being tested**, not generically called "SystemUnderTest" or "System".

**Examples:**
- `Infrastructure` for testing `PerformanceTester.Infrastructure`
- `EventConsuming` for testing `PerformanceTester.EventConsuming`
- `EventPublishing` for testing `PerformanceTester.EventPublishing`
- `Orchestration` for testing `PerformanceTester.Orchestration`

This naming makes it immediately clear what's being tested and provides better IntelliSense/autocomplete in IDEs.

**Example Implementation:**

```csharp
// In PerformanceTester.Infrastructure.IntegrationTests
public sealed class Infrastructure : IDisposable
{
    private readonly IHost _host;
    private readonly IServiceProvider _services;

    public Infrastructure(ITestOutputHelper output)
    {
        // Build DI container using Host.CreateApplicationBuilder()
        var builder = Host.CreateApplicationBuilder();

        // Configure logging to write to test output
        builder.Logging.ClearProviders();
        builder.Logging.AddXunitOutput(output);

        // Register production services using shared container connection strings
        builder.Services.AddInfrastructure(
            ContainerManager.Instance.PostgresConnectionString,
            ContainerManager.Instance.RabbitMqConnectionString);

        _host = builder.Build();
        _services = _host.Services;
    }

    // Production APIs (resolved from DI)
    public IInfrastructure InfrastructureAPI => _services.GetRequiredService<IInfrastructure>();

    // Test Helpers (future - added when patterns emerge)
    // public PostgreSQLHelpers PostgreSQL { get; }
    // public RabbitMQHelpers RabbitMQ { get; }

    public void Dispose()
    {
        _host.Dispose();
    }
}

// System wrapper class
public class System : IDisposable
{
    private readonly Infrastructure _infrastructure;

    public System(ITestOutputHelper output)
    {
        _infrastructure = new Infrastructure(output);
    }

    public Infrastructure Infrastructure => _infrastructure;

    public void Dispose()
    {
        _infrastructure.Dispose();
    }
}

// Usage in tests
public abstract class IntegrationTest : IntegrationTestBase
{
    protected System System { get; }

    protected IntegrationTest(ITestOutputHelper output) : base(output)
    {
        System = new System(output);
    }

    public override async Task DisposeAsync()
    {
        System.Dispose();
        await base.DisposeAsync();
    }
}
```

### Separation of Concerns

| Property | Purpose | Lives In | Example Usage |
|----------|---------|----------|---------------|
| `System.Infrastructure.InfrastructureAPI` | Production API being tested | Production code | `System.Infrastructure.InfrastructureAPI.Database.Clear()` |
| `System.PostgreSQL` | Infrastructure helper methods | Shared infrastructure (`PerformanceTester.IntegrationTesting`) | `System.PostgreSQL.GetTotalRowCountAsync(db, table)` |
| `System.RabbitMQ` | Infrastructure helper methods | Shared infrastructure (`PerformanceTester.IntegrationTesting`) | `System.RabbitMQ.ConnectionString` |
| Custom assertions on `PostgreSQL` | Test-specific validation logic | Test project (`Infrastructure/InfrastructureAssertions.cs`) | `await Asserting.That(System.PostgreSQL).DatabaseTableHasRows(db, table)` |
| Custom assertions on `RabbitMQ` | Test-specific validation logic | Test project (`Infrastructure/InfrastructureAssertions.cs`) | `await Asserting.That(System.RabbitMQ).QueueHasMessages(queue, count)` |

**Key Points:**
- **Infrastructure helpers** are generic and reusable (live in shared `PerformanceTester.IntegrationTesting`)
- **Assertion extensions** are test-specific and operate on infrastructure classes (live in test project)
- Production APIs are what we're actually testing
- Class is named after the project under test for clarity
- Each test project implements its own System and Infrastructure classes tailored to what it needs
- **Lifecycle:** Each test gets a fresh System instance → fresh Infrastructure instance → fresh DI container
- **Disposal chain:** Test → System → Infrastructure → IHost

## Service Logging Capture

### Why Capture Service Logs?

Integration tests should capture all logging output from the service under test. This provides:

1. **Debugging Visibility** - See exactly what the service was doing when a test failed
2. **Behavior Understanding** - Observe service internal behavior during test execution
3. **Issue Diagnosis** - Identify configuration problems, warnings, or errors quickly
4. **Test Documentation** - Logs serve as documentation of what happened during the test

### How It Works

xUnit provides the `ITestOutputHelper` interface for capturing test output:

- **Constructor Injection** - Each test class receives an `ITestOutputHelper` instance
- **Thread-Safe** - Each test gets its own helper instance
- **Visible in Results** - Output appears in test results and during test execution
- **Standard Pattern** - This is the recommended xUnit approach (still current in v3)

### Integration with IntegrationTest Base Class

The `IntegrationTest` base class accepts `ITestOutputHelper` and makes it available to:
1. Wire up service logging (Serilog, Microsoft.Extensions.Logging)
2. Output diagnostic messages from tests
3. Display all service logs in test output

This means **all service logs automatically appear in test results** - no additional configuration needed per test.

## Assertions in Integration Tests

### Why Use JoanComasFdz.AssertingThat?

Integration tests use the `JoanComasFdz.AssertingThat` library for assertions instead of xUnit's built-in `Assert` methods. This provides:

1. **Domain-Specific Language** - Express assertions using business concepts
2. **Better Readability** - `Asserting.That(order).HasBeenShipped()` vs `Assert.Equal(OrderStatus.Shipped, assertingThat.InstanceToAssert.Status);`
1. **Visual Distinction** - IDEs highlight `Asserting` differently, making assertions stand out
2. **Extensibility** - Create custom assertion methods for your domain models
3. **Fluent Chaining** - Chain multiple assertions together

### Basic Usage

```csharp
// Chained assertions
Asserting.That(order)
    .HasBeenShipped()
    .HasTotalAmount(99.99m);
```

### Creating Custom Assertion Extensions

Create domain-specific assertion extensions in your test project's `Infrastructure/` folder:

```csharp
namespace PerformanceTester.Infrastructure.IntegrationTests.Infrastructure;

/// <summary>
/// Custom assertion extensions for Infrastructure domain.
/// </summary>
public static class InfrastructureAssertions
{
   public static AssertingThat<Order> HasBeenShipped(this AssertingThat<Order> assertingThat)
    {
        Assert.Equal(OrderStatus.Shipped, assertingThat.InstanceToAssert.Status);
        Assert.NotNull(assertingThat.InstanceToAssert.ShippedAt);
        return assertingThat;
    }

    public static AssertingThat<Order> HasTotalAmount(this AssertingThat<Order> assertingThat, decimal expected)
    {
        Assert.Equal(expected, assertingThat.InstanceToAssert.TotalAmount);
        return assertingThat;
    }
}
```

**Key Points:**
- Extensions return `AssertingThat<T>` for chaining
- Use xUnit's `Assert` methods internally (or any assertion library)
- Access the actual value via `assertingThat.InstanceToAssert`
- Organize by domain (Infrastructure, EventPublishing, etc.)

### Benefits for Integration Tests

The difference becomes more significant with complex domain objects:

**Before:**
```csharp
Assert.Equal(OrderStatus.Shipped, order.Status);
Assert.NotNull(order.ShippedAt);
Assert.True(order.ShippedAt.Value > DateTime.UtcNow.AddHours(-1));
```

**After:**
```csharp
Asserting.That(order).HasBeenShippedRecently();
```

### Assertion Pattern: Extending Infrastructure vs Extending Values

When creating assertions that involve infrastructure operations (database, message queues, etc.), follow this pattern: **extend the infrastructure class itself, not the values it returns**.

#### The Pattern

✅ **Correct - Extend Infrastructure Class:**
```csharp
// Extension method signature (in test project/Infrastructure/InfrastructureAssertions.cs)
public static async Task DatabaseTableHasRows(
    this AssertingThat<PostgreSQL> assertingThat,
    string dbName,
    string tableName)
{
    var rowCount = await assertingThat.InstanceToAssert.GetTotalRowCountAsync(dbName, tableName);
    Assert.True(rowCount > 0);
}

// Usage in test
await Asserting.That(System.PostgreSQL).DatabaseTableHasRows(testDbName, "test_table");
```

❌ **Anti-Pattern - Extend Return Value:**
```csharp
// Don't do this - creates two-step process
public static AssertingThat<int> HasRows(this AssertingThat<int> assertingThat)
{
    Assert.True(assertingThat.InstanceToAssert > 0);
    return assertingThat;
}

// Forces awkward usage
var count = await System.PostgreSQL.GetTotalRowCountAsync(db, table);
Asserting.That(count).HasRows(); // Wrong tier!
```

#### Why This Pattern?

1. **Encapsulation** - Infrastructure helper methods stay generic and reusable; assertion logic stays in test project
2. **Single Responsibility** - Helpers don't know about test-specific validation; assertions encapsulate domain-specific rules
3. **Discoverability** - All PostgreSQL assertions discovered via `Asserting.That(System.PostgreSQL).` autocomplete
4. **Context Preservation** - Extension method has full access to infrastructure instance (can call multiple helper methods)
5. **Type Safety** - Compiler ensures correct infrastructure usage
6. **Flexibility** - Can combine multiple infrastructure calls in one assertion

#### Where Components Live

| Component | Location | Purpose | Example |
|-----------|----------|---------|---------|
| Helper methods | `PerformanceTester.IntegrationTesting/PostgreSQL.cs` | Generic infrastructure operations | `GetTotalRowCountAsync()`, `CreateTestDatabaseAsync()` |
| Assertion extensions | Test project `/Infrastructure/InfrastructureAssertions.cs` | Test-specific validation logic | `DatabaseTableHasRows()`, `DatabaseTableHasNoRows()` |

#### Complete Example

**Infrastructure Helper (shared project):**
```csharp
// File: PerformanceTester.IntegrationTesting/PostgreSQL.cs
public class PostgreSQL(string ConnectionString)
{
    public string ConnectionString { get; } = ConnectionString;

    public async Task<int> GetTotalRowCountAsync(string dbName, string tableName)
    {
        var builder = new NpgsqlConnectionStringBuilder(ConnectionString)
        {
            Database = dbName
        };
        await using var conn = new NpgsqlConnection(builder.ConnectionString);
        await conn.OpenAsync();

        await using var cmd = new NpgsqlCommand($"SELECT COUNT(*) FROM {tableName}", conn);
        var result = await cmd.ExecuteScalarAsync();
        return Convert.ToInt32(result);
    }
}
```

**Assertion Extension (test project):**
```csharp
// File: PerformanceTester.Infrastructure.IntegrationTests/Infrastructure/InfrastructureAssertions.cs
using JoanComasFdz.AssertingThat;
using PerformanceTester.IntegrationTesting;
using Xunit;

namespace PerformanceTester.Infrastructure.IntegrationTests.Infrastructure;

public static class InfrastructureAssertions
{
    /// <summary>
    /// Asserts that the specified database table has rows.
    /// </summary>
    public static async Task DatabaseTableHasRows(
        this AssertingThat<PostgreSQL> assertingThat,
        string dbName,
        string tableName)
    {
        var rowCount = await assertingThat.InstanceToAssert.GetTotalRowCountAsync(dbName, tableName);
        Assert.True(rowCount > 0, $"Expected table '{tableName}' in database '{dbName}' to have rows, but it was empty");
    }

    /// <summary>
    /// Asserts that the specified database table has no rows.
    /// </summary>
    public static async Task DatabaseTableHasNoRows(
        this AssertingThat<PostgreSQL> assertingThat,
        string dbName,
        string tableName)
    {
        var rowCount = await assertingThat.InstanceToAssert.GetTotalRowCountAsync(dbName, tableName);
        Assert.Equal(0, rowCount);
    }

    /// <summary>
    /// Asserts that the specified database table has exact row count.
    /// </summary>
    public static async Task DatabaseTableHasRowCount(
        this AssertingThat<PostgreSQL> assertingThat,
        string dbName,
        string tableName,
        int expectedCount)
    {
        var rowCount = await assertingThat.InstanceToAssert.GetTotalRowCountAsync(dbName, tableName);
        Assert.Equal(expectedCount, rowCount);
    }
}
```

**Usage in Test:**
```csharp
public async Task ClearDatabaseAsync_WhenDatabaseHasData_ShouldTruncateAllTables()
{
    // Arrange - Setup test data
    var testDbName = $"test_infrastructure_db_{Guid.NewGuid():N}";
    await System.PostgreSQL.CreateTestDatabaseAsync(testDbName);
    await System.PostgreSQL.CreateTestTableWithDataAsync(testDbName, "test_table");

    // Verify initial state using fluent assertion
    await Asserting.That(System.PostgreSQL).DatabaseTableHasRows(testDbName, "test_table");

    // Act - Call production API
    await System.Infrastructure.Database.ClearDatabaseAsync(testDbName);

    // Assert - Verify final state using fluent assertion
    await Asserting.That(System.PostgreSQL).DatabaseTableHasNoRows(testDbName, "test_table");

    // Cleanup
    await System.PostgreSQL.DropTestDatabaseAsync(testDbName);
}
```

#### Design Guidelines

**Naming Conventions:**
- **Helper methods**: Action verbs (`GetTotalRowCountAsync`, `CreateTestDatabaseAsync`, `DropTestDatabaseAsync`)
- **Assertion extensions**: State-focused domain language (`DatabaseTableHasRows`, `DatabaseTableHasNoRows`, `QueueHasMessages`)

**Async Patterns:**
- Helper methods: `async Task<T>` (return values)
- Assertion extensions: `async Task` (no return value needed)
- Both use `Async` suffix

**Error Messages:**
- Include meaningful context in assertion failures
- Specify what was expected vs what was found
- Include relevant identifiers (database name, table name, etc.)

### Exception Assertion Patterns

When testing that infrastructure methods throw exceptions, follow these patterns to maintain consistency and readability.

#### Pattern 2: Asserting on Exceptions with Complex Validation

**❌ INCORRECT - Using raw Assert.ThrowsAsync:**

```csharp
// DON'T: Use raw xUnit assert with manual message validation
var exception = await Assert.ThrowsAsync<TimeoutException>(async () =>
{
    await System.EventConsuming.Consumer.StartTrackingEventsAsync(
        expectedCount: 10,
        inactivityTimeout: TimeSpan.FromSeconds(2));
});
Assert.Contains("Inactivity timeout expired", exception.Message);
Assert.Contains("0/10", exception.Message);
```

**✅ CORRECT - Encapsulate in assertion extension:**

```csharp
// DO: Encapsulate exception validation in custom assertion
await Asserting.That(System.EventConsuming.Consumer)
    .ThrowsTimeoutExceptionAfterStartTrackingEvents(
        expectedCount: 10,
        inactivityTimeout: TimeSpan.FromSeconds(2),
        expectedReceivedCount: 0);
```

**Implementation:**

```csharp
public static class EventConsumingAssertions
{
    /// <summary>
    /// Asserts that StartTrackingEventsAsync throws TimeoutException with expected details.
    /// </summary>
    public static async Task ThrowsTimeoutExceptionAfterStartTrackingEvents(
        this AssertingThat<IEventConsumer> assertingThat,
        int expectedCount,
        TimeSpan inactivityTimeout,
        int expectedReceivedCount)
    {
        // Encapsulate the complex assertion logic
        var exception = await Assert.ThrowsAsync<TimeoutException>(async () =>
        {
            await assertingThat.InstanceToAssert.StartTrackingEventsAsync(
                expectedCount: expectedCount,
                inactivityTimeout: inactivityTimeout);
        });

        Assert.Contains("Inactivity timeout expired", exception.Message);
        Assert.Contains($"{expectedReceivedCount}/{expectedCount}", exception.Message);
    }
}
```

**Key Points:**
- Extension method operates on `AssertingThat<IEventConsumer>` (the infrastructure interface)
- Encapsulates both exception type validation AND message content validation
- Provides clear, domain-specific assertion name
- Reusable across multiple tests

#### Pattern 3: Asserting on Simple Exceptions

**❌ INCORRECT - Using raw Assert.ThrowsAsync:**

```csharp
// DON'T: Use raw xUnit assert even for simple cases
await Assert.ThrowsAsync<ArgumentOutOfRangeException>(async () =>
{
    await System.EventConsuming.Consumer.StartTrackingEventsAsync(
        expectedCount: 0,  // Invalid
        inactivityTimeout: TimeSpan.FromSeconds(30));
});
```

**✅ CORRECT - Encapsulate in assertion extension:**

```csharp
// DO: Create specific assertion even for simple validation
await Asserting.That(System.EventConsuming.Consumer)
    .ThrowsArgumentOutOfRangeExceptionForInvalidCount(invalidCount: 0);
```

**Implementation:**

```csharp
public static class EventConsumingAssertions
{
    /// <summary>
    /// Asserts that StartTrackingEventsAsync throws ArgumentOutOfRangeException for invalid count.
    /// </summary>
    public static async Task ThrowsArgumentOutOfRangeExceptionForInvalidCount(
        this AssertingThat<IEventConsumer> assertingThat,
        int invalidCount)
    {
        await Assert.ThrowsAsync<ArgumentOutOfRangeException>(async () =>
        {
            await assertingThat.InstanceToAssert.StartTrackingEventsAsync(
                expectedCount: invalidCount,
                inactivityTimeout: TimeSpan.FromSeconds(30));
        });
    }
}
```

**Key Points:**
- Even simple exception assertions should be encapsulated
- Provides clear test intent through method name
- Keeps test code clean and readable
- Makes it easy to add message validation later if needed

#### General Guidelines for Assertion Extensions

**When to Create Assertion Extensions:**

1. ✅ **Always** when asserting on values returned by infrastructure methods
2. ✅ **Always** when asserting on exceptions thrown by infrastructure methods
3. ✅ **Always** when validation logic is complex (multiple Assert calls)
4. ✅ **Always** when the same assertion is used in multiple tests

**Assertion Extension Checklist:**

- [ ] Extends `AssertingThat<TInfrastructure>` (not return value types)
- [ ] Returns `Task` (not `Task<TResult>`)
- [ ] Has clear, domain-specific name describing what it validates
- [ ] Has XML documentation explaining what it asserts
- [ ] Located in test project (e.g., `EventConsumingAssertions.cs`)
- [ ] Uses `assertingThat.InstanceToAssert` to access infrastructure
- [ ] Encapsulates all validation logic (caller doesn't see intermediate values)

**Summary of All Three Patterns:**

| Pattern | What to Assert On | Extension Target | Example |
|---------|-------------------|------------------|---------|
| Pattern 1 | Return values from infrastructure methods | `AssertingThat<TInfrastructure>` | `HasThroughputSamples()` |
| Pattern 2 | Exceptions with complex validation | `AssertingThat<TInfrastructure>` | `ThrowsTimeoutExceptionAfterStartTrackingEvents(...)` |
| Pattern 3 | Simple exceptions | `AssertingThat<TInfrastructure>` | `ThrowsArgumentOutOfRangeExceptionForInvalidCount(...)` |

All three patterns share the same principle: **extend the infrastructure class itself, not the values or exceptions it produces**.

## Dependency Injection Architecture

### Why Use DI in Tests?

The integration test infrastructure uses `Microsoft.Extensions.DependencyInjection` and `Microsoft.Extensions.Hosting` to:

1. **Mirror Production Architecture** - Tests use the same DI patterns as the production CLI tool
2. **Service Composition** - Each project exposes `AddXxx()` extension methods (e.g., `AddInfrastructure()`)
3. **Proper Lifetime Management** - Services registered with correct lifetimes (Singleton, Scoped, Transient)
4. **Testability** - Easy to replace services with test doubles when needed
5. **Configuration Integration** - Proper configuration binding and options pattern support

### Extension Method Pattern

Each project exposes a static extension method on `IServiceCollection`:

```csharp
// PerformanceTester.Infrastructure project
namespace PerformanceTester.Infrastructure;

public static class ServiceCollectionExtensions
{
    public static IServiceCollection AddInfrastructure(
        this IServiceCollection services,
        string postgresConnectionString,
        string rabbitMqConnectionString)
    {
        // Register database services
        services.AddSingleton<IPostgreSQLClient>(sp =>
            new PostgreSQLClient(postgresConnectionString));

        // Register message broker services
```

### 2. ContainerManager Singleton

```csharp
using Testcontainers.PostgreSql;
using Testcontainers.RabbitMq;

namespace PerformanceTester.Infrastructure.IntegrationTests;

/// <summary>
/// Manages container lifecycle as a singleton.
/// Ensures containers are started once and reused across all tests.
/// </summary>
internal sealed class ContainerManager
{
    private static readonly SemaphoreSlim s_lock = new(1, 1);
    private static bool s_containersStarted = false;

    // Container instances
    private PostgreSqlContainer? _postgresContainer;
    private RabbitMqContainer? _rabbitMqContainer;

    // Connection information (populated after startup)
    public string PostgresConnectionString { get; private set; } = string.Empty;
    public string RabbitMqConnectionString { get; private set; } = string.Empty;

    /// <summary>
    /// Ensures containers are started (idempotent).
    /// Thread-safe, only starts containers once.
    /// </summary>
    public async Task EnsureStartedAsync()
    {
        if (s_containersStarted)
            return;

        await s_lock.WaitAsync();
        try
        {
            if (s_containersStarted)
                return;

            await StartContainersAsync();
            s_containersStarted = true;
        }
        finally
        {
            s_lock.Release();
        }
    }

    private async Task StartContainersAsync()
    {
        // Build PostgreSQL container
        _postgresContainer = new PostgreSqlBuilder()
            .WithImage("postgres:16-alpine")
            .WithDatabase("testdb")
            .WithUsername("testuser")
            .WithPassword("testpass")
            .WithPortBinding(5432, true) // Random host port
            .Build();

        // Build RabbitMQ container
        _rabbitMqContainer = new RabbitMqBuilder()
            .WithImage("rabbitmq:3.13-management-alpine")
            .WithUsername("testuser")
            .WithPassword("testpass")
            .WithPortBinding(5672, true)  // AMQP port
            .WithPortBinding(15672, true) // Management UI
            .Build();

        // Start both containers in parallel
        await Task.WhenAll(
            _postgresContainer.StartAsync(),
            _rabbitMqContainer.StartAsync()
        );

        // Store connection strings for test helpers
        PostgresConnectionString = _postgresContainer.GetConnectionString();
        RabbitMqConnectionString =
            $"amqp://{_rabbitMqContainer.GetUsername()}:" +
            $"{_rabbitMqContainer.GetPassword()}@" +
            $"{_rabbitMqContainer.Hostname}:" +
            $"{_rabbitMqContainer.GetMappedPublicPort(5672)}";
    }
}
```

**Key Design Decisions:**
- ✅ `internal sealed` - Only visible to test project
- ✅ Double-check locking pattern - Thread-safe initialization
- ✅ Parallel container startup - Faster initialization
- ✅ Random host ports - Enables parallel test runs
- ✅ Connection strings stored - Used by test helpers

```csharp
using Npgsql;

namespace PerformanceTester.Infrastructure.IntegrationTests;

/// <summary>
/// Test helper methods for PostgreSQL container.
/// Provides setup, teardown, and assertion utilities.

    /// Truncates all tables in the database.
    /// Used for cleanup between tests.
    /// </summary>
    public async Task TruncateAllTablesAsync()
    {
        await using var connection = new NpgsqlConnection(_connectionString);
        await connection.OpenAsync();

        // Get all table names
        var tables = new List<string>();
        await using (var cmd = new NpgsqlCommand(
            "SELECT tablename FROM pg_tables WHERE schemaname = 'public'",
            connection))
        await using (var reader = await cmd.ExecuteReaderAsync())
        {
            while (await reader.ReadAsync())
            {
                tables.Add(reader.GetString(0));
            }
        }

        // Truncate all tables
        foreach (var table in tables)
        {
            await using var truncateCmd = new NpgsqlCommand(
                $"TRUNCATE TABLE {table} CASCADE",
                connection);
            await truncateCmd.ExecuteNonQueryAsync();
        }
    }

    /// <summary>
    /// Drops all databases (for specific test scenarios).
    /// </summary>
    public async Task EnsureNoDBExistsAsync()
    {
        await using var connection = new NpgsqlConnection(_connectionString);
        await connection.OpenAsync();

        // Drop all databases except system databases
        await using var cmd = new NpgsqlCommand(@"
            SELECT datname FROM pg_database
            WHERE datistemplate = false
            AND datname NOT IN ('postgres', 'testdb')",
            connection);

        var databases = new List<string>();
        await using (var reader = await cmd.ExecuteReaderAsync())
        {
            while (await reader.ReadAsync())
            {
                databases.Add(reader.GetString(0));
            }
        }

        foreach (var db in databases)
        {
            await using var dropCmd = new NpgsqlCommand(
                $"DROP DATABASE IF EXISTS {db}",
                connection);
            await dropCmd.ExecuteNonQueryAsync();
        }
    }

    /// <summary>
    /// Counts rows in a specific table.
    /// Useful for assertions.

        await using var connection = new NpgsqlConnection(_connectionString);
        await connection.OpenAsync();

        await using var cmd = new NpgsqlCommand(
            $"SELECT COUNT(*) FROM {tableName}",
            connection);

        var result = await cmd.ExecuteScalarAsync();
        return Convert.ToInt32(result);
    }
}
```

```csharp
        using var connection = factory.CreateConnection();

        var queues = new List<string>();

        {

            catch (Exception)
            {
                // Queue might not exist yet, ignore
            }
        }
    }

        using var channel = connection.CreateModel();

            queue: queueName,
            durable: false,
            exclusive: false,
            autoDelete: false,
            arguments: null);

        var body = System.Text.Encoding.UTF8.GetBytes(message);
        channel.BasicPublish(
            exchange: string.Empty,
            routingKey: queueName,
            basicProperties: null,
            body: body);
    }

    /// Gets the message count in a queue.
```

### 7. Wiring Service Logging to Test Output

To capture all service logging in test output, configure your logging framework to write to `ITestOutputHelper`:

```csharp
using Serilog;
using Serilog.Core;
using Serilog.Events;
using Xunit.Abstractions;

namespace PerformanceTester.Infrastructure.IntegrationTests.Infrastructure;

/// <summary>
/// Serilog sink that writes to xUnit ITestOutputHelper.
/// All service logs will appear in test output.
/// </summary>
public class XunitLoggerSink : ILogEventSink
{

    private readonly IFormatProvider? _formatProvider;

        _output.WriteLine($"[{logEvent.Timestamp:HH:mm:ss} {logEvent.Level}] {message}");

        if (logEvent.Exception != null)
        {
            _output.WriteLine($"Exception: {logEvent.Exception}");
        }
    }
}
```

## VSA-Specific Considerations

### Testing Individual Slices

Each slice (EventPublishing, EventConsuming, ProcessMonitoring, etc.) gets its own integration test project:

```
PerformanceTester.EventPublishing/
├── PerformanceTester.EventPublishing.csproj
└── PerformanceTester.EventPublishing.IntegrationTests/
    ├── Infrastructure/
    │   ├── IntegrationTest.cs
    │   ├── ContainerManager.cs  (or shared)
    │   ├── SystemUnderTest.cs
    │   ├── PostgreSQLHelpers.cs
    │   └── RabbitMQHelpers.cs
    └── EventPublishingIntegrationTests.cs
```

**Testing Strategy:**
- Test each slice as a black box
- Each slice has its own Infrastructure class (e.g., `EventPublishing`, `EventConsuming`)
- Use real dependencies (RabbitMQ container, PostgreSQL container)
- Validate the slice's public API
- Each test gets fresh DI container (per-test isolation)

### Testing the Orchestrator

The Orchestrator slice coordinates multiple slices:

```csharp
public class OrchestrationIntegrationTests : IntegrationTest
{
    [Fact]
    public async Task GivenAllSlicesReadyWhenOrchestratingTestThenSucceeds()
    {
        // Arrange - Setup via multiple System properties
        await System.PostgreSQL.TruncateAllTablesAsync();
        await System.RabbitMQ.PurgeAllQueuesAsync();

        // Act - Test orchestrator
        var result = await System.Orchestration.RunPerformanceTest(config);

        // Assert - Verify coordination worked using AssertingThat
        Asserting.That(result).IsSuccess();
        var messageCount = await System.RabbitMQ.GetMessageCountAsync("events");
        Asserting.That(messageCount).IsEqualTo(1000);
    }
}
```

**Key Point:** The Orchestrator test validates slice coordination, not individual slice functionality.

### Sharing ContainerManager Across Projects

**This project uses Option B: Shared Integration Testing Infrastructure**

### Test Project Dependencies (Anti-Pattern)

**CRITICAL PRINCIPLE: Test projects should NEVER reference other test projects.**

This is a common anti-pattern that violates VSA principles and creates unnecessary coupling.

#### The Anti-Pattern

```xml
<!-- ❌ BAD: EventConsuming.IntegrationTests.csproj -->
<ItemGroup>
  <ProjectReference Include="..\PerformanceTester.EventPublishing.IntegrationTests\..." />
</ItemGroup>
```

```csharp
// ❌ BAD: EventConsumingSystem.cs
public EventPublishing.IntegrationTests.Infrastructure.EventPublishing EventPublishing { get; }

// In test:
await System.EventPublishing.Publisher.PublishEventsAsync(count);
```

#### Why This Is Wrong

1. **Creates Test-to-Test Coupling**
   - Test infrastructure is internal implementation detail
   - One slice's tests depend on another slice's test implementation
   - Changes to EventPublishing test infrastructure break EventConsuming tests

2. **Violates VSA Principles**
   - Slices should be independent in production AND testing
   - Test projects should mirror production project independence

3. **Tests Wrong API**
   - Tests use test wrapper, not production API
   - Production consumers will use `IEventPublisher`, not test infrastructure
   - Test coverage doesn't reflect real usage

4. **Maintenance Nightmare**
   - If EventPublishing refactors test infrastructure, EventConsuming tests break
   - Test infrastructure was never designed to be reusable across projects

#### The Correct Pattern

```xml
<!-- ✅ GOOD: EventConsuming.IntegrationTests.csproj -->
<ItemGroup>
  <ProjectReference Include="..\PerformanceTester.EventPublishing\..." />
</ItemGroup>
```

```csharp
// ✅ GOOD: EventConsumingSystem.cs
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using PerformanceTester.EventPublishing;

public sealed class EventConsumingSystem : IntegrationTesting.System
{
    private IHost? _eventPublisherHost;

    /// <summary>
    /// EventPublisher for test setup (publishing CloudEvents to consume).
    /// Uses production API, not test infrastructure.
    /// </summary>
    public IEventPublisher EventPublisher { get; private set; } = null!;

    protected override void InitializeSystem()
    {
        base.InitializeSystem();

        // Create production EventPublisher via DI
        var builder = Host.CreateApplicationBuilder();

        // Wire up logging (optional)
        builder.Logging.ClearProviders();
        if (base.Output != null)
        {
            builder.Logging.AddXunitOutput(base.Output);
        }

        // Register production services using production DI method
        builder.Services.AddEventPublishing(base.RabbitMQ.ConnectionString);

        _eventPublisherHost = builder.Build();

        // Resolve production interface
        this.EventPublisher = _eventPublisherHost.Services.GetRequiredService<IEventPublisher>();

        // Initialize if needed (check production API requirements)
        var publisher = _eventPublisherHost.Services.GetRequiredService<RabbitMqPublisher>();
        publisher.ConnectAsync().GetAwaiter().GetResult();
    }

    public override void Dispose()
    {
        EventConsuming?.Dispose();
        _eventPublisherHost?.Dispose();
        base.Dispose();
    }
}
```

```csharp
// In test:
await System.EventPublisher.PublishEventsAsync(count);  // Uses production IEventPublisher
```

#### Benefits of Correct Pattern

1. ✅ **No Test-to-Test Coupling** - EventConsuming tests depend on EventPublishing production library, not test infrastructure
2. ✅ **Tests Production API** - Uses same `IEventPublisher` interface that production code will use
3. ✅ **Better Integration Testing** - Tests against real production service registration
4. ✅ **Follows VSA** - Slices remain independent at test level
5. ✅ **Maintainable** - EventPublishing can refactor test infrastructure without breaking EventConsuming tests
6. ✅ **Clear Contracts** - Production API is the contract, not test helpers

#### When You Need Services from Another Slice

**Scenario:** Your slice's tests need functionality from another slice (e.g., EventConsuming needs to publish events).

**Steps:**

1. **Reference the production library** (e.g., `PerformanceTester.EventPublishing`)
2. **Create IHost with production DI** - Use the slice's `AddXxx()` extension method
3. **Resolve production interface** - Get `IEventPublisher`, `IDatabase`, etc.
4. **Initialize if required** - Call any required setup methods (e.g., `ConnectAsync()`)
5. **Use production API in tests** - Same interface production code will use

**Key Insight:** If you need another slice's functionality in tests, you're testing integration between slices. Use the production API, not test helpers.

#### Real-World Example: EventConsuming Tests

EventConsuming tests need to publish events to test consumption:

```csharp

// 2. Create IHost with AddEventPublishing()

```

#### Enforcement

**Project References:**
- ✅ Test projects MAY reference: Production projects, `IntegrationTesting` (shared infrastructure)
- ❌ Test projects MUST NOT reference: Other test projects

**Code Review Checklist:**
- [ ] No `ProjectReference` to `*.IntegrationTests.csproj` from other test projects
- [ ] Test System classes use `IHost` + production `AddXxx()` methods for dependencies
- [ ] Production interfaces used in tests, not test infrastructure classes
- [ ] Test projects remain independent (can run without other test projects)

## Summary

The `IntegrationTest` base class pattern provides:

✅ **Single Entry Point** - `System` property for all test interactions
✅ **Automatic Container Management** - Singleton, reused across tests
✅ **DI Container Architecture** - Uses `Host.CreateApplicationBuilder()` with `AddXxx()` extension methods
✅ **Production Parity** - Tests use the same service registration as production CLI tool
✅ **Clear Separation** - Test helpers vs production APIs
✅ **Developer Ergonomics** - Minimal boilerplate in tests
✅ **Fast Execution** - Containers start once, data cleaned before each test
✅ **Easy Debugging** - Last test's data and containers remain for manual inspection
✅ **Clean Organization** - Infrastructure classes in `Infrastructure/` folder, tests in project root
✅ **Service Logging Capture** - All service logs automatically appear in test output via ITestOutputHelper
✅ **Domain-Specific Assertions** - `JoanComasFdz.AssertingThat` library for readable, business-focused test assertions

**Trade-offs:**
- Per-test System and Infrastructure instances (justified for test isolation)
- Requires discipline to keep test helpers separate from production APIs
- Container startup time (20 seconds) before first test runs
- Each production project must expose `AddXxx()` extension methods (additional code, but valuable pattern)
