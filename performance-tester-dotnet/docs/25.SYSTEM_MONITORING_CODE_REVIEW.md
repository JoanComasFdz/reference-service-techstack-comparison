## Detailed Review

### PowerShellHelper.cs

**Purpose:** Helper to locate PowerShell executable across different environments.

**Strengths:**
- Path caching avoids repeated lookups
- Multiple fallback locations for cross-platform support (WSL2, Windows native)
- Clean, focused implementation

**Issues:**

#### 1. PATH Check Doesn't Work As Intended (Line 30)

```csharp
if (File.Exists(candidate))  // "powershell.exe"
```

`File.Exists("powershell.exe")` checks the **current directory**, not the system PATH. To actually verify if PowerShell is in PATH, you would need to:
- Search directories in `Environment.GetEnvironmentVariable("PATH")`
- Or attempt `Process.Start` and catch the exception

**Impact:** Low - the fallback paths cover most scenarios.

**Suggested Fix:**
```csharp
// Option 1: Search PATH explicitly
private static bool IsInPath(string executable)
{
    var pathDirs = Environment.GetEnvironmentVariable("PATH")?.Split(Path.PathSeparator) ?? [];
    return pathDirs.Any(dir => File.Exists(Path.Combine(dir, executable)));
}

// Option 2: Just remove "powershell.exe" from candidates and rely on concrete paths
```

#### 2. Thread Safety (Line 8)

```csharp
private static string? _cachedPath;
```

The `_cachedPath` field is not `volatile` or protected by a lock. In practice, this is unlikely to cause issues since it's convergent (always set to the same value), but it's technically a data race.

**Impact:** Negligible - worst case is redundant path searches.

#### 3. No Logging

When PowerShell is located or when falling back to default, there's no logging to indicate which path was selected. This makes debugging harder.

**Suggested Enhancement:**
```csharp
public static string GetPowerShellPath(ILogger? logger = null)
{
    if (_cachedPath != null)
        return _cachedPath;

    // ... search logic ...

    logger?.LogDebug("PowerShell located at: {Path}", _cachedPath);
    return _cachedPath;
}
```

### SystemMonitoringException.cs

**Purpose:** Custom exception for fatal monitoring failures with rich diagnostic information.

**Strengths:**
- Sealed exception class (good practice - prevents unintended inheritance)
- Rich diagnostic properties (`Platform`, `MetricType`) for troubleshooting
- Factory methods provide consistent, descriptive error messages
- Clear XML documentation

**Issues:**

#### 1. Unnecessary String Interpolation (Lines 53-55, 64-66)

```csharp
message: $"Failed to query Windows host CPU usage via PowerShell. " +
         $"System monitoring cannot continue without CPU metrics. " +
         $"Please verify PowerShell is accessible and Windows host is responsive."
```

The `$` prefix indicates string interpolation, but there are no interpolation placeholders (`{}`). These are just regular string concatenations.

**Impact:** None - just unnecessary syntax.

**Suggested Fix:** Remove `$` prefixes or convert to verbatim strings:
```csharp
message: "Failed to query Windows host CPU usage via PowerShell. " +
         "System monitoring cannot continue without CPU metrics. " +
         "Please verify PowerShell is accessible and Windows host is responsive."
```

#### 2. Missing Parameterless Constructor

While not required for .NET Core, some serialization scenarios (especially cross-process communication) may expect a parameterless constructor.

**Impact:** Low - only matters for specific serialization scenarios.

### WindowsCpuQuery.cs

**Purpose:** Queries Windows host CPU usage via PowerShell Get-CimInstance.

**Strengths:**
- Proper timeout handling with linked `CancellationTokenSource`
- Uses `Get-CimInstance Win32_Processor` (fast, unlike `Get-Counter` which requires ~1s sampling)
- Averages CPU load across multiple processors/sockets
- Comprehensive logging at appropriate levels (Debug for success, Warning for failures)
- Proper process disposal with `using`

**Issues:**

#### 1. Old Array Syntax (Line 68)

```csharp
var lines = output.Split(new[] { '\n', '\r' }, StringSplitOptions.RemoveEmptyEntries);
```

In C# 12+, prefer collection expressions:
```csharp
var lines = output.Split(['\n', '\r'], StringSplitOptions.RemoveEmptyEntries);
```

**Impact:** Style only - no functional difference.

#### 2. Process Start Exception Handling

If `process.Start()` throws (e.g., PowerShell not found), the exception is caught by the general `catch (Exception ex)` block. Consider adding specific handling for `Win32Exception` to provide clearer error messages.

### SystemMonitorService.cs

**Purpose:** BackgroundService that monitors system-wide CPU and memory usage with deferred start pattern.

**Strengths:**
- Deferred start pattern (waits for `StartMonitoringAsync`) is excellent for controlled test orchestration
- `PeriodicTimer` is the correct modern .NET 6+ approach for periodic work
- Parallel Windows queries (lines 227-229) improve performance
- Final sample collection on shutdown ensures complete data capture
- Progress reporting via `IProgress<T>` is comprehensive
- Clear separation between Windows/WSL2 and native Linux code paths
- Proper handling of `SystemMonitoringException` vs general exceptions

**Issues:**

#### 1. Misleading Comment About Linux Reader Initialization (Lines 115-122)

```csharp
// Always initialize Linux readers (needed as fallback even for Windows/WSL2)
if (OperatingSystem.IsLinux())
{
    _cpuReader = new ProcStatReader();
    _memoryReader = new ProcMeminfoReader();
    _cpuReader.Sample(); // Initialize
}
```

The comment says "needed as fallback" but the code **never falls back**. If Windows queries fail, the code throws `SystemMonitoringException` rather than falling back to Linux readers. The readers are only used in the `else` branch (native Linux).

**Suggested Fix:** Update comment to reflect actual behavior:
```csharp
// Initialize Linux readers only for native Linux (not WSL2, which uses Windows queries)
```

#### 2. Null-Forgiving Operators on Nullable Fields (Lines 262, 279)

```csharp
cpuPercent = _cpuReader!.Sample();
var memory = _memoryReader!.Read();
```

These rely on the assumption that reaching this code path means the readers were initialized. This is fragile - if control flow changes, you'll get `NullReferenceException`.

**Suggested Fix:** Add explicit null check with clear exception:
```csharp
if (_cpuReader is null)
    throw new InvalidOperationException("CPU reader not initialized for Linux platform");
cpuPercent = _cpuReader.Sample();
```

Or use `Debug.Assert` if you want to catch issues only in debug builds:
```csharp
Debug.Assert(_cpuReader is not null, "CPU reader should be initialized for Linux");
cpuPercent = _cpuReader.Sample();
```

#### 3. Expensive GetCollectedMetrics Implementation (Lines 88-91) ✅ RESOLVED

**Resolution (2026-01-29):** Replaced `ConcurrentBag<T>` with `List<T>` + lock. Since items are added chronologically by `PeriodicTimer`, the collection is inherently ordered. GetCollectedMetrics now returns in O(1) instead of O(n log n). Same fix applied to ProcessMonitorService for consistency.

**Original Implementation:**
```csharp
public IReadOnlyCollection<SystemMetrics> GetCollectedMetrics() => _collectedMetrics
    .OrderBy(m => m.Timestamp)
    .ToList()
    .AsReadOnly();
```

Every call:
1. Iterates the entire `ConcurrentBag`
2. Sorts all elements
3. Creates a new `List<T>`
4. Wraps it in `ReadOnlyCollection<T>`

If called frequently, this is wasteful.

**Suggested Alternatives:**

Option A - Cache the sorted result:
```csharp
private IReadOnlyCollection<SystemMetrics>? _sortedMetricsCache;
private int _lastKnownCount;

public IReadOnlyCollection<SystemMetrics> GetCollectedMetrics()
{
    var currentCount = _collectedMetrics.Count;
    if (_sortedMetricsCache is null || currentCount != _lastKnownCount)
    {
        _sortedMetricsCache = _collectedMetrics
            .OrderBy(m => m.Timestamp)
            .ToList()
            .AsReadOnly();
        _lastKnownCount = currentCount;
    }
    return _sortedMetricsCache;
}
```

Option B - Use a sorted collection from the start:
```csharp
private readonly SortedSet<SystemMetrics> _collectedMetrics =
    new(Comparer<SystemMetrics>.Create((a, b) => a.Timestamp.CompareTo(b.Timestamp)));
```

**Implemented Solution:**
```csharp
private readonly List<SystemMetrics> _collectedMetrics = [];
private readonly Lock _metricsLock = new();

public IReadOnlyCollection<SystemMetrics> GetCollectedMetrics()
{
    lock (_metricsLock)
    {
        return _collectedMetrics.AsReadOnly();
    }
}
```

#### 4. ConcurrentBag Usage (Line 19)

```csharp
private readonly ConcurrentBag<SystemMetrics> _collectedMetrics = new();
```

`ConcurrentBag<T>` is optimized for scenarios where the same thread that adds items also removes them. Here, there's only one writer (the `ExecuteAsync` loop) and potentially multiple readers (via `GetCollectedMetrics`).

**Impact:** Low - `ConcurrentBag` works correctly, but a `List<T>` with a lock or a `Channel<T>` might be more appropriate for this access pattern.

#### 5. Redundant Await After Task.WhenAll (Lines 229-233)

```csharp
await Task.WhenAll(cpuTask, memoryTask);
var windowsCpu = await cpuTask;
var windowsMemory = await memoryTask;
```

After `Task.WhenAll` completes, both tasks are guaranteed finished. The subsequent `await` calls don't block but add minor overhead.

**Alternatives:**
```csharp
// Option A: Use .Result (safe after WhenAll)
await Task.WhenAll(cpuTask, memoryTask);
var windowsCpu = cpuTask.Result;
var windowsMemory = memoryTask.Result;

// Option B: Capture results directly from WhenAll
var results = await Task.WhenAll(cpuTask, memoryTask);
// But this doesn't work well with different return types
```

**Impact:** Negligible - the current code is correct and clear.

### SystemMonitorPhaseInfo.cs

**Purpose:** Progress information record for system monitor phases.

**Strengths:**
- Immutable record with positional parameters
- Clean factory methods (`Starting`, `Completed`, `Failed`)
- Good XML documentation
- Simple, focused design

**Issues:**

#### 1. State Representation

The three states (Starting, Completed, Failed) are represented via two boolean flags:
- `IsCompleted`
- `IsFailed`

This could lead to invalid states (e.g., `IsCompleted = true && IsFailed = true`).

**Alternative Design:** Consider a discriminated union or enum-based status:
```csharp
public enum PhaseStatus { InProgress, Completed, Failed }

public sealed record SystemMonitorPhaseInfo(
    SystemMonitorPhase Phase,
    PhaseStatus Status,
    int SampleCount = 0,
    string? Message = null);
```

**Impact:** Low - the factory methods prevent invalid states in practice.

## Architecture Observations

### Testability Concern

The static classes (`PowerShellHelper`, `WindowsCpuQuery`, `WindowsMemoryQuery`) are difficult to mock in unit tests.

**Current Design:**
```csharp
// Hard to test in isolation
var cpu = await WindowsCpuQuery.QueryAsync(cancellationToken, logger);
```

**More Testable Alternative:**
```csharp
// Interface-based
public interface IWindowsMetricsQuery
{
    Task<double?> QueryCpuAsync(CancellationToken ct);
    Task<WindowsMemoryInfo?> QueryMemoryAsync(CancellationToken ct);
}

// Inject into SystemMonitorService
public SystemMonitorService(
    TimeSpan samplingInterval,
    IWindowsMetricsQuery windowsMetrics,  // Mockable
    ILogger<SystemMonitorService> logger)
```

### Logging Inconsistency

Different components handle logging differently:
- `PowerShellHelper` - No logging
- `WindowsCpuQuery` - Takes `ILogger?` as method parameter
- `WindowsMemoryQuery` - Takes `ILogger?` as method parameter
- `SystemMonitorService` - Uses constructor-injected `ILogger<T>`

**Recommendation:** Consider consistent dependency injection throughout, or document the intentional differences.
