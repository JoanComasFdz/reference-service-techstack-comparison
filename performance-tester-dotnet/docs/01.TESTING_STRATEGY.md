## Introduction

This document defines the testing strategy for the Performance Tester .NET rewrite. Our approach is influenced by modern critiques of the traditional testing pyramid and focuses on **integration-first testing** with strategic use of unit tests only where they add genuine value.

### Modern Testing Landscape (2024-2025)

Recent industry analysis has challenged the traditional testing pyramid:

- **Qase.io** (March 2024) - The pyramid has become oversimplified and misleading
- **WireMock** (January 2025) - The pyramid is an outdated economic model from an era of slower computers
- **Momentic** (2024) - Questions the pyramid's relevance in modern microservices architectures
- **Code4IT** (2024) - Proposes the Testing Diamond, focusing on integration tests over unit tests

### Key Insights

The universal understanding of "unit testing" has evolved to mean **single-class testing**, which has significant limitations:

- **Unit tests test implementation details, integration tests test functionality**
- Single-class tests don't guarantee full functionality
- They rely on mocks rather than real implementations
- They only validate that a class works against a mock, not against real dependencies
- They don't validate interactions between 2 or more classes (which is what a service/module actually is)
- Even when grouping classes, there's often no clear justification for why certain classes are included while others are mocked
- They provide limited context about overall functionality

**Modern Reality:**
- Integration tests with Docker containers are fast to set up and run
- Integration tests validate the whole service/module functionality, not just individual pieces
- Integration tests provide significantly more context about overall functionality

## Philosophy

### Integration-First Approach

**Primary Strategy:** Focus on integration tests that validate entire projects/slices as black boxes working with real dependencies.

**Unit Tests:** Only when they add genuine value (context, readability, and edge case validation).

### Why This Approach?

1. **Real Validation** - Tests verify actual behavior with real dependencies, not mocked approximations
2. **Better Context** - Integration tests demonstrate how components work together
3. **Faster Feedback** - Modern tooling (Testcontainers) makes integration tests fast enough for regular development
4. **Fewer Mocks** - Less time maintaining mock objects that drift from real implementations
5. **VSA Alignment** - Tests align with Vertical Slice Architecture where meaningful functionality emerges from slice composition

## Unit Testing

### When to Write Unit Tests

Unit tests should be **rare** and signal "this is important!" Write unit tests when:

1. **The test adds context** - It improves code readability, understandability, and maintainability
2. **Large problem space** - The logic has many edge cases that need validation
3. **Necessary complexity** - The logic handles underlying tech limitations, poorly documented dependencies, or unexpected behaviors

### When NOT to Write Unit Tests

**DO NOT unit test:**
- ❌ Repository classes (data access layer)
- ❌ Mapping/transformation classes
- ❌ ASP.NET controllers or API endpoints
- ❌ Simple calculations or business rules (these belong in integration tests)
- ❌ Orchestration logic (coordination between services)

**Key Principle:** If the logic can be validated in a larger integration test context with clear Given-When-Then semantics, prefer integration tests.

### Unit Test Examples

#### Example 1: Simple State Machine ❌ NO Unit Test
```csharp
public class OrderStatus
{
    public Status Current { get; private set; }

    public void MarkAsPaid()
    {
        if (Current != Status.Pending)
            throw new InvalidOperationException();
        Current = Status.Paid;
    }
}
```
**Why not?** Only a few cases, easily reproducible in integration test:
```csharp
// Integration test context
public Task GivenOrderInStatusRequestedWhenMarkedAsPaidThenReturnsError()
```

#### Example 2: Simple Calculation ❌ NO Unit Test
```csharp
public class PricingCalculator
{
    public decimal Calculate(decimal basePrice, CustomerTier tier, bool hasDiscount)
    {
        var price = basePrice;
        if (tier == CustomerTier.Premium) price *= 0.9m;
        if (hasDiscount) price *= 0.95m;
        return price;
    }
}
```
**Why not?** Straightforward logic, easily validated in integration test with real customer scenarios.

#### Example 3: Complex Event Ordering ✅ Unit Test Justified
```csharp
public class EventAggregator
{
    // Handles two events that can arrive in any order
    // Must store intermediate state, handle edge cases
    // Involves in-memory caching and database peculiarities
}
```
**Why yes?**
- Many edge cases (no event, eventA before eventB, eventB before eventA)
- Complex state management
- Tech-specific behavior that needs documentation
- The unit test provides context about the problem space

### How to Write Unit Tests

**Library:** https://github.com/JoanComasFdz/dotnet-scenario-unittesting

This library provides a scenario-based approach that makes unit tests more readable and maintainable.

**Important:** The scenario library is **ONLY for unit tests**. Do NOT use it for integration tests.

## Integration Testing

### Strategy

**Core Principle:** Test each project as a whole, validating that it works correctly with real dependencies.

Integration tests are the **standard way** to verify that a service does what it's supposed to do while working with actual dependencies (PostgreSQL, RabbitMQ, etc.).

### Architecture

Each project that offers functionality should have corresponding test projects:

```
PerformanceTester.sln
├── PerformanceTester.Infrastructure/
│   ├── PerformanceTester.Infrastructure.UnitTests/         # Unit tests (rare)
│   └── PerformanceTester.Infrastructure.IntegrationTests/  # Integration tests
├── PerformanceTester.EventPublishing/
│   ├── PerformanceTester.EventPublishing.UnitTests/        # Unit tests (rare)
│   └── PerformanceTester.EventPublishing.IntegrationTests/ # Integration tests
├── PerformanceTester.Orchestration/
│   ├── PerformanceTester.Orchestration.UnitTests/          # Unit tests (rare)
│   └── PerformanceTester.Orchestration.IntegrationTests/   # Integration tests
└── ...
```

### IntegrationTest Base Class

Each integration test project provides an `IntegrationTest` base class that:

1. **Controls the test lifecycle** - Setup and teardown
2. **Manages dependencies** - PostgreSQL, RabbitMQ containers via Testcontainers
3. **Builds a DI container** - Uses `Host.CreateApplicationBuilder()` with `AddXxx()` extension methods
4. **Provides the System property** - Single entry point for all test interactions
5. **Captures service logging** - All service logs automatically appear in test output via ITestOutputHelper

**Design Philosophy:** The `IntegrationTest` base class is intentionally a "god object" pattern - a single entry point that provides all necessary tools. This is a deliberate trade-off favoring **developer ergonomics** in testing.

**DI Container Architecture:** Tests use the same DI patterns as production code. Each project exposes `AddInfrastructure()`, `AddEventPublishing()`, etc. extension methods that register services with `IServiceCollection`. The test infrastructure builds a host using `Host.CreateApplicationBuilder()`, ensuring tests mirror production service composition.

### The System Pattern

The `System` static class provides clear separation between test helpers and production APIs:

**Test Helpers** (in test project):
- `System.PostgreSQL.*` - Database management methods
- `System.RabbitMQ.*` - Message broker management methods

**Production APIs** (the code under test):
- `System.Infrastructure.*` - Public APIs from the Infrastructure project
- `System.EventPublishing.*` - Public APIs from the EventPublishing project

### Example Integration Test

```csharp
public class DatabaseClearingIntegrationTest : IntegrationTest
{
    [Fact]
    public async Task GivenNoDatabaseWhenClearedThenErrorReturned()
    {
        // Arrange - Using test helper
        System.PostgreSQL.EnsureNoDBExists();

        // Act - Calling production API
        var result = await System.Infrastructure.Database.ClearInstrumentStatusTable();

        // Assert...
    }
}
```

**Key Points:**
- Test name follows BDD style (GivenWhenThen)
- `System.PostgreSQL` = test helper method (lives in test project)
- `System.Infrastructure.Database` = production API being tested
- No test-only methods pollute production code

### System Extension Pattern

When extending the base `System` class, you are **adding modules**, not adding APIs directly:

**Incorrect Pattern (don't do this):**
```csharp
public class InfrastructureSystem : System
{
    // ❌ Don't expose APIs directly on System
    public Task ClearDatabaseAsync(string dbName) { ... }
}
```

**Correct Pattern (do this):**
```csharp
public class InfrastructureSystem : System
{
    // ✅ Add a module that exposes production APIs
    public Infrastructure Infrastructure { get; private set; } = null!;

    // Infrastructure module then exposes: .Database, .ServiceDiscovery, .RabbitMQ
}
```

**Why:** This maintains clear separation:
- `System.PostgreSQL`, `System.RabbitMQ` = Test infrastructure helpers
- `System.Infrastructure` = Functional module
- `System.Infrastructure.Database` = Production API under test

The module itself should encapsulate DI container setup and expose production services retrieved via `IServiceProvider`.

### Container Management

**Strategy:** Container reuse across all tests in a test run (singleton pattern).

**Lifecycle:**
1. Containers (PostgreSQL, RabbitMQ) start once at the beginning of the test run
2. Containers are reused across all test classes
3. Data is cleaned BEFORE each test starts (truncate tables, purge queues)
4. Data from the last test remains in containers after test run completes (enables manual review)
5. Containers remain running after test run completes

**Implementation:** The `IntegrationTest` base class uses a private `ContainerManager` singleton to handle container lifecycle automatically. Tests should NOT micromanage container start/stop.

**Benefits:**
- Fast test execution (no repeated container startup overhead)
- Test isolation through data cleanup before each test
- Enables manual data review from the last test run
- Containers persist for debugging

### Test Independence and Parallelization

**Requirements:**
- ✅ Tests MUST be parallelizable
- ✅ Tests MUST be independent (no shared state between tests)
- ✅ Tests MUST clean up data BEFORE execution (in setup phase)

**Why:** Fast feedback and reliable test execution in CI/CD environments. Cleaning data before (not after) tests enables manual review of the last test's data.

**How to Achieve Parallelization:**
- ✅ Use unique identifiers per test (GUIDs, timestamps, test names)
- ✅ Generate unique queue names: `$"queue-{Guid.NewGuid():N}"`
- ✅ Generate unique database names if testing multi-DB scenarios
- ✅ Avoid hardcoded resource names shared across tests
- ❌ Never use hardcoded queue names like "test-queue" across multiple tests
- ❌ Never share state via static fields or singletons between tests

**Example - RabbitMQ Queue Isolation:**
```csharp
public class EventConsumerIntegrationTests : IntegrationTest
{
    // Generate unique queue name per test to enable parallel execution
    private string GenerateQueueName() => $"performancetesterdotnet-{Guid.NewGuid():N}";

    [Fact]
    public async Task StartTrackingEventsAsync_WhenEventsPublished_ShouldCompleteWhenTargetReached()
    {
        // Arrange - Each test gets its own unique queue
        var queueName = GenerateQueueName();
        System.CreateEventConsuming(queueName);

        await System.RabbitMQ.DeclareAndBindQueueAsync(queueName, ExchangeName, RoutingKey);

        // ... test logic uses the unique queue
    }
}
```

**Shared vs. Isolated Resources:**
- **Shared (by design):** Docker containers (PostgreSQL, RabbitMQ) are reused across all tests for performance
- **Isolated (required):** Queue names, database table data, test-specific resources must be unique per test

### Service Logging

**Strategy:** All service logs are captured and displayed in test output automatically.

**How It Works:**

- The `IntegrationTest` base class wires service logging to test output
- All logs from services under test appear in test results

**Benefits:**

1. **Debugging** - See exactly what the service was doing when a test failed
2. **Visibility** - Understand service internal behavior during test execution
3. **Diagnostics** - Quickly identify configuration problems, warnings, or errors
4. **Documentation** - Logs serve as documentation of what happened during the test

**Implementation Details:** See `INTEGRATION_TEST_DESIGN.md` section 7 "Wiring Service Logging to Test Output" for complete implementation examples.

### Integration Test Assertions

Integration tests use the **`JoanComasFdz.AssertingThat`** library (NuGet package) for assertions instead of xUnit's built-in `Assert` methods.

**Why:**
- Express assertions using business/domain language
- Create custom assertion extensions that encapsulate complex validation logic
- Better readability - tests read like business requirements
- Visual distinction in IDEs

**Example:**

```csharp
// Before (xUnit) - Multiple low-level assertions
Assert.Equal(OrderStatus.Shipped, order.Status);
Assert.NotNull(order.ShippedAt);
Assert.True(order.ShippedAt.Value > DateTime.UtcNow.AddHours(-1));

// After (AssertingThat) - Single domain-focused assertion
Asserting.That(order).HasBeenShippedRecently();
```

The custom `HasBeenShippedRecently()` extension encapsulates the business rule, making the test more readable and maintainable.

**Assertion Architecture Pattern:**

The integration testing infrastructure uses a **two-tier pattern** for separation of concerns:

- **Tier 1: Infrastructure Helpers** - Generic helper methods (database operations, message queue operations) live in the shared infrastructure project (`PerformanceTester.IntegrationTesting`). These are reusable across all test projects.

- **Tier 2: Assertion Extensions** - Test-specific assertion logic lives in each test project's `Infrastructure/InfrastructureAssertions.cs` file. These extensions operate on infrastructure classes (like `PostgreSQL`, `RabbitMQ`), NOT on the values returned by helper methods.

**Key Pattern:** Extend infrastructure classes, not their return values.

```csharp
// ✅ Correct - Extension on infrastructure class
await Asserting.That(System.PostgreSQL).DatabaseTableHasRows(dbName, "test_table");

// ❌ Anti-pattern - Extension on return value
var count = await System.PostgreSQL.GetTotalRowCountAsync(db, table);
Asserting.That(count).HasRows(); // Wrong tier!
```

This pattern provides encapsulation (assertion logic stays in test project), reusability (infrastructure helpers can be used for setup and verification), and clarity (infrastructure being tested is explicit).

**Implementation Details:** See `INTEGRATION_TEST_DESIGN.md` section "Assertions in Integration Tests" for:
- Complete implementation guide for assertion extensions
- Detailed code examples showing both tiers
- Where each component lives and why
- How to create custom assertion extensions

## Test Organization

### Project Structure

```
PerformanceTester.Infrastructure.IntegrationTests/
├── Infrastructure/                    # Test infrastructure (avoids polluting root)
│   ├── IntegrationTest.cs            # Base class for all tests
│   ├── ContainerManager.cs           # Private singleton for container lifecycle
│   ├── SystemUnderTest.cs            # Static class with test/API properties
│   ├── PostgreSQLHelpers.cs          # Test helper methods
│   └── RabbitMQHelpers.cs            # Test helper methods
├── DatabaseIntegrationTests.cs       # Tests for database functionality
└── RabbitMqIntegrationTests.cs       # Tests for RabbitMQ functionality
```

**Organization Principle:** Keep test infrastructure classes in a dedicated `Infrastructure/` folder to maintain a clean project root focused on actual test files.

### Naming Conventions

**Test Classes:** Organized by the API or functionality being tested
- `DatabaseIntegrationTests` - Tests database-related APIs
- `RabbitMqIntegrationTests` - Tests RabbitMQ-related APIs
- `ServiceDiscoveryIntegrationTests` - Tests service discovery functionality

**Test Methods:** BDD-style naming (GivenWhenThen pattern)
```csharp
public async Task GivenValidInstrumentWhenSavedToDatabaseThenSuccessReturned()
public async Task GivenNoConnectionWhenPublishingEventThenErrorReturned()
```

**Scenario Folders (Optional):**
Test classes may be grouped in scenario folders when it improves organization:
```
EventConsuming.Tests/
├── Scenarios/
│   ├── EventPerSecondCalculation/
│   │   └── EventPerSecondCalculationIntegrationTests.cs
│   └── DeltaConsuming/
│       └── DeltaConsumingCalculationIntegrationTests.cs
```

**Note:** Test organization at the class/method level should evolve organically. Write tests first, then refactor organization as patterns emerge.

## Quality Standards

### Test Execution

**Speed and Accessibility:**
- Tests must be **fast** and **easy to run anywhere** (local dev machine, CI/CD, etc.)
- No performance budgets defined yet (optimize as needed)

**Reliability:**
- Tests must NOT be retried on failure
- Failures are signal, not noise
- If a test is flaky, fix the test or the code, don't mask with retries

### Coverage and Validation

**What to Test:**
- ✅ All functionality exposed via public APIs must be validated
- ✅ Both happy paths AND expected error scenarios must be tested
- ❌ Unexpected error scenarios (network failures, timeouts) are optional

**Coverage Metrics:**
- ❌ NO minimum coverage percentage requirements
- ❌ NO arbitrary metrics that force unnecessary tests
- ✅ Success is measured by: tests breaking when code breaks, tests finding bugs, fewer production bugs

**Philosophy:** Coverage as an individual metric says nothing about test quality. Tests must validate actual functionality, not chase numbers.

### Test Quality

**Assertions:**
- No arbitrary "one assertion per test" rule
- Use as many assertions as needed to validate the behavior
- Focus on clarity and completeness

**Test Data:**
- Keep test data inline for now (no complex builders or fixtures)
- As patterns emerge, introduce abstractions when they add value

**Error Handling:**
- Tests should validate both success and failure cases
- Expected errors should be tested explicitly
- Unexpected errors can surface during test execution (don't over-engineer error path tests)

**Logging Visibility:**
- All service logs automatically appear in test output
- Failed tests show complete logging context for debugging
- Test output includes both test-specific diagnostic messages and service logs
- No additional configuration needed per test

### Developer Responsibility

**Core Principle:** It is the developer's responsibility to prove that their code works by writing the necessary tests.

**No Ownership Ambiguity:**
- You write the code → You write the tests
- You break the tests → You fix them
- You introduce bugs → Tests should have caught them

**For This Project:** Currently a one-person project, but the principle scales to teams.

## Tools and Libraries

### Test Framework
- **xUnit 2** - Test framework (de facto standard for .NET)

### Dependency Injection
- **Microsoft.Extensions.Hosting** - Provides `Host.CreateApplicationBuilder()` for building DI container
- **Microsoft.Extensions.DependencyInjection** - DI container implementation
  - Used to register and resolve production services
  - Enables `AddXxx()` extension method pattern
  - Same DI framework used in ASP.NET Core and console applications

### Dependency Management
- **Testcontainers for .NET** - Container lifecycle management
  - Used for PostgreSQL and RabbitMQ containers
  - Handles container startup, configuration, and cleanup

### Mocking (Unit Tests Only)
- **NSubstitute** - Mocking framework for rare unit tests
  - Only use when unit tests are justified
  - Integration tests use real dependencies, not mocks

### Assertions
- **JoanComasFdz.AssertingThat (integration tests)** - Domain-specific, fluent assertions with custom extension methods
  - NuGet package: `JoanComasFdz.AssertingThat`
  - Repository: https://github.com/JoanComasFdz/dotnet-asserting-that
  - Built on top of xUnit's `Assert` methods
- **Scenario library (unit tests)** - Uses custom assertion syntax

### Scenario Testing (Unit Tests Only)
- **dotnet-scenario-unittesting** (https://github.com/JoanComasFdz/dotnet-scenario-unittesting)
  - Provides scenario-based testing for unit tests
  - NOT for integration tests

## Summary

|--------|----------|
| **Primary Strategy** | Integration tests with real dependencies |
