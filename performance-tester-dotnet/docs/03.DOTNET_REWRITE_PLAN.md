## Extension Points for .NET Rewrite

### What to Preserve
1. **Three-phase testing model** (Publish → Consume → API)
2. **Warmup phase** before measurement
3. **Multi-threaded monitoring** with separate threads per metric source
4. **CloudEvent v1.0 compliance** for message format
5. **Sampling intervals** (500ms process/system, 3000ms containers)
6. **Report structure** and statistics (avg, peak, min, std dev, CV%)
7. **Chart layout** (5 subplots with dual y-axes)
8. **Comparison report** with rankings and medal emojis

### What to Modernize
1. **Replace shell scripts** with native .NET process invocation
2. **Use k6** for HTTP load testing (matching Python implementation)
3. **Replace matplotlib** with .NET charting (System.Drawing or SkiaSharp)
4. **Use async/await** instead of daemon threads
5. **Use System.Diagnostics.Process** instead of psutil
6. **Use Docker.DotNet** instead of `docker stats` subprocess
7. **Use RabbitMQ.Client** instead of pika
8. **Use Npgsql** instead of psql subprocess
9. **Use System.Text.Json** for serialization
10. **Use Serilog** for structured logging

### Architecture: Vertical Slice Architecture (VSA)

**Design Principle:** Each slice is self-contained and owns its data structures. No central "Core" project. Producers expose contracts that consumers depend on. Each slice exposes an `AddXxx()` extension method for DI registration.

**Key VSA Principles Applied:**

1. **No "Core" dumping ground** - Each slice owns its models
2. **Producer-owned contracts** - `EventPublishing` owns `CloudEvent`, `ProcessMonitoring` owns `ProcessMetrics`
3. **Public interfaces only** - Orchestrator depends on `IEventPublisher`, not implementation details
4. **Self-contained slices** - Each slice has everything it needs (service, models, logic, API)
5. **Thin orchestration layer** - `TestOrchestrator` just coordinates, doesn't contain business logic
6. **DI container architecture** - Each slice exposes `AddXxx()` extension method for service registration
7. **ASP.NET Core conventions** - Uses `Microsoft.Extensions.DependencyInjection` and `Host.CreateApplicationBuilder()`

## Task Launching & Coordination Patterns

### Overview

The .NET 9 rewrite will use **modern async/await patterns** with the following key components:

1. **`IHost` + `BackgroundService`** - For lifecycle management of long-running monitors
2. **`System.Threading.Channels`** - For efficient producer-consumer pipelines
3. **`PeriodicTimer`** - For interval-based sampling (more efficient than `Task.Delay` loops)
4. **`CancellationToken`** - For cooperative cancellation and graceful shutdown
5. **`Task.WhenAll`/`WhenAny`** - For coordinating multiple async operations

### 1. BackgroundService Pattern for Monitors

**Why BackgroundService?**
- Automatic lifecycle management by `IHost`
- Built-in graceful shutdown via `CancellationToken`
- Clean separation of concerns (each monitor is independent)
- No manual thread management required

**Example: Process Monitor (500ms interval)**

```csharp
public class ProcessMonitorService : BackgroundService
{
    private readonly ILogger<ProcessMonitorService> _logger;
    private readonly Channel<ProcessMetrics> _channel;
    private readonly int _targetProcessId;

    public ProcessMonitorService(
        ILogger<ProcessMonitorService> logger,
        Channel<ProcessMetrics> channel,
        IConfiguration configuration)
    {
        _logger = logger;
        _channel = channel;
        _targetProcessId = configuration.GetValue<int>("TargetProcessId");
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        _logger.LogInformation("Process monitor started (500ms interval)");

        // PeriodicTimer is more efficient than Task.Delay in loops
        using var timer = new PeriodicTimer(TimeSpan.FromMilliseconds(500));

        try
        {
            // WaitForNextTickAsync respects cancellation automatically
            while (await timer.WaitForNextTickAsync(stoppingToken))
            {
                try
                {
                    var metrics = CollectProcessMetrics();

                    // Write to channel (async, non-blocking)
                    await _channel.Writer.WriteAsync(metrics, stoppingToken);
                }
                catch (Exception ex) when (ex is not OperationCanceledException)
                {
                    _logger.LogError(ex, "Error collecting process metrics");
                    // Continue monitoring despite errors
                }
            }
        }
        catch (OperationCanceledException)
        {
            // Expected during shutdown
            _logger.LogInformation("Process monitor shutting down gracefully");
        }
    }

    private ProcessMetrics CollectProcessMetrics()
    {
        using var process = Process.GetProcessById(_targetProcessId);

        return new ProcessMetrics
        {
            Timestamp = DateTime.UtcNow,
            CpuPercent = GetCpuUsage(process),
            RamMb = process.WorkingSet64 / 1024.0 / 1024.0,
            ThreadCount = process.Threads.Count
        };
    }

    private double GetCpuUsage(Process process)
    {

}
```

**Example: Docker Container Monitor (3000ms interval)**

```csharp
public class DockerContainerMonitorService : BackgroundService
{
    private readonly ILogger<DockerContainerMonitorService> _logger;
    private readonly Channel<DockerMetrics> _channel;
    private readonly DockerClient _dockerClient;
    private readonly string _containerId;

    public DockerContainerMonitorService(
        ILogger<DockerContainerMonitorService> logger,
        Channel<DockerMetrics> channel,
        DockerClient dockerClient,
        string containerId)
    {
        _logger = logger;
        _channel = channel;
        _dockerClient = dockerClient;
        _containerId = containerId;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        _logger.LogInformation("Docker monitor started for {ContainerId} (3000ms interval)", _containerId);

        using var timer = new PeriodicTimer(TimeSpan.FromMilliseconds(3000));

        try
        {
            while (await timer.WaitForNextTickAsync(stoppingToken))
            {
                try
                {
                    var metrics = await CollectDockerMetricsAsync(stoppingToken);
                    await _channel.Writer.WriteAsync(metrics, stoppingToken);
                }
                catch (Exception ex) when (ex is not OperationCanceledException)
                {
                    _logger.LogError(ex, "Error collecting Docker metrics");
                }
            }
        }
        catch (OperationCanceledException)
        {
            _logger.LogInformation("Docker monitor shutting down gracefully");
        }
    }

    private async Task<DockerMetrics> CollectDockerMetricsAsync(CancellationToken ct)
    {
        // Use Docker.DotNet instead of subprocess
        var stats = await _dockerClient.Containers.GetContainerStatsAsync(
            _containerId,
            new ContainerStatsParameters { Stream = false },
            ct);

        return new DockerMetrics
        {
            Timestamp = DateTime.UtcNow,
            CpuPercent = CalculateCpuPercent(stats),
            RamMb = stats.MemoryStats.Usage / 1024.0 / 1024.0
        };
    }
}
```

### 2. System.Threading.Channels for Producer-Consumer

**Why Channels over BlockingCollection?**
- ✅ Async-first design (no thread blocking)
- ✅ Better performance (lockless for single-producer/single-consumer)
- ✅ `await foreach` support for clean consumption
- ✅ Backpressure control with bounded channels
- ✅ Modern .NET best practice

**Channel Setup in Dependency Injection:**

```csharp
// In Program.cs or Startup
services.AddSingleton(Channel.CreateUnbounded<ProcessMetrics>(
    new UnboundedChannelOptions
    {
        SingleReader = false,  // Multiple consumers possible
        SingleWriter = false   // Multiple producers (for flexibility)
    }
));

services.AddSingleton(Channel.CreateUnbounded<SystemMetrics>());
services.AddSingleton(Channel.CreateUnbounded<DockerMetrics>());
services.AddSingleton(Channel.CreateUnbounded<RabbitMqMetrics>());

// Or use bounded channels for backpressure:
services.AddSingleton(Channel.CreateBounded<ProcessMetrics>(
    new BoundedChannelOptions(1000)
    {
        FullMode = BoundedChannelFullMode.Wait  // Block producers if full
    }
));
```

**Metrics Collector Service (Consumes from All Channels):**

```csharp
public class MetricsCollectorService : BackgroundService
{
    private readonly ILogger<MetricsCollectorService> _logger;
    private readonly ChannelReader<ProcessMetrics> _processReader;
    private readonly ChannelReader<SystemMetrics> _systemReader;
    private readonly ChannelReader<DockerMetrics> _dockerReader;

    // Thread-safe collections for final results
    private readonly ConcurrentBag<ProcessMetrics> _processMetrics = new();
    private readonly ConcurrentBag<SystemMetrics> _systemMetrics = new();
    private readonly ConcurrentBag<DockerMetrics> _dockerMetrics = new();

    public MetricsCollectorService(
        ILogger<MetricsCollectorService> logger,
        Channel<ProcessMetrics> processChannel,
        Channel<SystemMetrics> systemChannel,
        Channel<DockerMetrics> dockerChannel)
    {
        _logger = logger;
        _processReader = processChannel.Reader;
        _systemReader = systemChannel.Reader;
        _dockerReader = dockerChannel.Reader;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        _logger.LogInformation("Metrics collector started");

        // Launch parallel consumers for each channel
        var processTask = ConsumeProcessMetricsAsync(stoppingToken);
        var systemTask = ConsumeSystemMetricsAsync(stoppingToken);
        var dockerTask = ConsumeDockerMetricsAsync(stoppingToken);

        // Wait for all consumers to complete (when channels complete)
        await Task.WhenAll(processTask, systemTask, dockerTask);

        _logger.LogInformation("Metrics collector stopped. Collected {ProcessCount} process samples, {SystemCount} system samples, {DockerCount} docker samples",
            _processMetrics.Count, _systemMetrics.Count, _dockerMetrics.Count);
    }

    private async Task ConsumeProcessMetricsAsync(CancellationToken ct)
    {
        // await foreach automatically completes when channel is completed
        await foreach (var metric in _processReader.ReadAllAsync(ct))
        {
            _processMetrics.Add(metric);
        }
    }

    private async Task ConsumeSystemMetricsAsync(CancellationToken ct)
    {
        await foreach (var metric in _systemReader.ReadAllAsync(ct))
        {
            _systemMetrics.Add(metric);
        }
    }

    private async Task ConsumeDockerMetricsAsync(CancellationToken ct)
    {
        await foreach (var metric in _dockerReader.ReadAllAsync(ct))
        {
            _dockerMetrics.Add(metric);
        }
    }

    public IReadOnlyCollection<ProcessMetrics> GetProcessMetrics() => _processMetrics;
    public IReadOnlyCollection<SystemMetrics> GetSystemMetrics() => _systemMetrics;
    public IReadOnlyCollection<DockerMetrics> GetDockerMetrics() => _dockerMetrics;
}
```

### 3. Test Orchestration with Concurrent Event Testing

**Key Understanding:** Event publishing and consuming happen **concurrently**, not sequentially. The test consumer subscribes first, then publishing starts, and both run simultaneously until all events are received.

**Solution:** Use `TestOrchestrator` to coordinate test execution while `IHost` manages BackgroundService monitors.

```csharp
public class TestOrchestrator
{
    private readonly IHost _host;
    private readonly ILogger<TestOrchestrator> _logger;

    // VSA: Dependencies via public interfaces only
    private readonly IEventPublisher _publisher;
    private readonly IEventConsumer _consumer;
    private readonly ILoadTester _loadTester;
    private readonly IReportGenerator _reportGenerator;
    private readonly IInfrastructure _infrastructure;
    private readonly IProcessMonitor _processMonitor;
    private readonly ISystemMonitor _systemMonitor;
    private readonly IDockerMonitor _dockerMonitor;

    public TestOrchestrator(
        IHost host,
        ILogger<TestOrchestrator> logger,
        IEventPublisher publisher,
        IEventConsumer consumer,
        ILoadTester loadTester,
        IReportGenerator reportGenerator,
        IInfrastructure infrastructure,
        IProcessMonitor processMonitor,
        ISystemMonitor systemMonitor,
        IDockerMonitor dockerMonitor)
    {
        _host = host;
        _logger = logger;
        _publisher = publisher;
        _consumer = consumer;
        _loadTester = loadTester;
        _reportGenerator = reportGenerator;
        _infrastructure = infrastructure;
        _processMonitor = processMonitor;
        _systemMonitor = systemMonitor;
        _dockerMonitor = dockerMonitor;
    }

    public async Task<TestReport> RunTestAsync(TestConfiguration config, CancellationToken ct)
    {
        _logger.LogInformation("Starting test with {EventCount} events", config.EventCount);

        var stopwatch = Stopwatch.StartNew();

        try
        {
            // 1. Setup
            await SetupPhaseAsync(config, ct);

            // 2. Warmup (not measured)
            await WarmupPhaseAsync(config, ct);

            // 3. Start monitors (BackgroundServices start)
            await _host.StartAsync(ct);
            _logger.LogInformation("Monitors started");

            // 4. Event throughput test (CONCURRENT publishing + consuming)
            var eventTestTime = await EventThroughputTestAsync(config, ct);

            // 5. API load test
            var apiTestTime = await ApiLoadTestAsync(config, ct);

            // 6. Stop monitors
            await _host.StopAsync(ct);
            _logger.LogInformation("Monitors stopped");

            stopwatch.Stop();

            // 7. Generate report
            return await _reportGenerator.GenerateReportAsync(
                eventTestTime,
                apiTestTime,
                stopwatch.Elapsed,
                await GatherMetricsAsync(ct));
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Test failed");
            await _host.StopAsync(CancellationToken.None);
            throw;
        }
    }

    private async Task SetupPhaseAsync(TestConfiguration config, CancellationToken ct)
    {
        _logger.LogInformation("Setup: Waiting for service on port {Port}", config.ServicePort);

        // Discover service process
        var processId = await _infrastructure.FindServiceProcessIdAsync(config.ServicePort, ct);
        _logger.LogInformation("Found service process: {ProcessId}", processId);

        // Clear infrastructure
        await _infrastructure.ClearDatabaseAsync(config.DatabaseName, ct);
        await _infrastructure.ClearRabbitMqQueuesAsync(ct);

        _logger.LogInformation("Setup completed");
    }

    private async Task WarmupPhaseAsync(TestConfiguration config, CancellationToken ct)
    {
        _logger.LogInformation("Warmup: Sending 200 events + 5s API calls");

        // Warmup events
        var warmupConsumerTask = _consumer.SubscribeAndWaitForEventsAsync(200, ct);
        var warmupPublishTask = _publisher.PublishEventsAsync(200, ct);
        await Task.WhenAll(warmupPublishTask, warmupConsumerTask);

        // Warmup API
        var apiUrl = $"http://localhost:{config.ServicePort}/kpi";
        await _loadTester.RunLoadTestAsync(apiUrl, TimeSpan.FromSeconds(5), 1, ct);

        _logger.LogInformation("Warmup completed");
    }

    private async Task<TimeSpan> EventThroughputTestAsync(TestConfiguration config, CancellationToken ct)
    {
        _logger.LogInformation("Event Test: Publishing {EventCount} events (concurrent with consumption)",
            config.EventCount);

        var stopwatch = Stopwatch.StartNew();

        // CONCURRENT: Consumer subscribes, publisher publishes, both run simultaneously
        var consumerTask = _consumer.SubscribeAndWaitForEventsAsync(config.EventCount, ct);
        var publisherTask = _publisher.PublishEventsAsync(config.EventCount, ct);

        // Wait for both to complete
        await Task.WhenAll(publisherTask, consumerTask);

        stopwatch.Stop();

        _logger.LogInformation(
            "Event test completed in {Duration:F2}s ({EventsPerSec:F2} events/sec)",
            stopwatch.Elapsed.TotalSeconds,
            config.EventCount / stopwatch.Elapsed.TotalSeconds);

        return stopwatch.Elapsed;
    }

    private async Task<TimeSpan> ApiLoadTestAsync(TestConfiguration config, CancellationToken ct)
    {
        _logger.LogInformation(
            "API Test: Running k6 load test for {Duration} with {Workers} workers",
            config.ApiDuration,
            config.ApiWorkers);

        var apiUrl = $"http://localhost:{config.ServicePort}/kpi";
        var stopwatch = Stopwatch.StartNew();

        var result = await _loadTester.RunLoadTestAsync(
            apiUrl,
            config.ApiDuration,
            config.ApiWorkers,
            ct);

        stopwatch.Stop();

        _logger.LogInformation(
            "API test completed: {TotalRequests} requests, {RequestsPerSec:F2} req/sec",
            result.TotalRequests,
            result.RequestsPerSecond);

        return stopwatch.Elapsed;
    }

    private async Task<MetricsSnapshot> GatherMetricsAsync(CancellationToken ct)
    {
        // Collect metrics from all monitor slices
        return new MetricsSnapshot
        {
            ProcessMetrics = await _processMonitor.GetCollectedMetricsAsync(),
            SystemMetrics = await _systemMonitor.GetCollectedMetricsAsync(),
            DockerMetrics = await _dockerMonitor.GetCollectedMetricsAsync(),
            EventThroughput = await _consumer.GetThroughputSamplesAsync()
        };
    }
}
```

**Proper Channel Completion:**

```csharp
public class ProcessMonitorService : BackgroundService
{
    private readonly Channel<ProcessMetrics> _channel;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMilliseconds(500));

        try
        {
            while (await timer.WaitForNextTickAsync(stoppingToken))
            {
                var metrics = CollectProcessMetrics();
                await _channel.Writer.WriteAsync(metrics, stoppingToken);
            }
        }
        catch (OperationCanceledException)
        {
            // Expected during shutdown
        }
        finally
        {
            // Signal channel that no more data is coming
            _channel.Writer.Complete();
        }
    }
}
```

## Thread Safety & Data Flow

### Decision Matrix: When to Use Which Pattern

| Pattern | Use Case | Thread Safety | Performance |
|---------|----------|---------------|-------------|
| **Channel<T>** | ✅ Active producer-consumer pipeline | Lock-free | Excellent |
| **ConcurrentBag<T>** | ✅ Final results accumulation | Lock-free | Good |
| **ConcurrentQueue<T>** | FIFO ordering required | Lock-free | Good |
| **Interlocked.Increment** | ✅ Simple counter | Lock-free | Excellent |
| **SemaphoreSlim** | Resource limiting | Lock-based | Good |
| **lock (object)** | ❌ Avoid if possible | Lock-based | Poor |

### For Performance Tester:

1. **Monitors → Channels**: Use `Channel<T>` for all metric pipelines
   - Async-first, non-blocking
   - Automatic batching and buffering
   - Clean shutdown via `Writer.Complete()`

2. **Channel → Collector**: Use `await foreach` with `ReadAllAsync()`
   - Automatically completes when channel completes
   - No manual polling needed

3. **Collector → Storage**: Use `ConcurrentBag<T>` for final accumulation
   - Simple, fast appends
   - No ordering required for final results

4. **Event Counter**: Use `Interlocked.Increment(ref int)`
   - Lock-free atomic operation
   - Minimal overhead

### 2. Error Handling & Resilience

**Async/Await Exception Handling Patterns:**

```csharp
// ✅ GOOD: Proper async exception handling
public async Task PublishEventsAsync(int count, CancellationToken ct)
{
    try
    {
        for (int i = 0; i < count; i++)

            await PublishEventAsync(ct);

    catch (Exception ex)

        _logger.LogError(ex, "Error publishing events after {Count} successful publishes", i);

    try
    {
        await PublishEventAsync(ct);

    catch
    {
        // Silent failure - never do this!
    }
}

// ❌ BAD: Blocking in async code (deadlock risk)
public Task DoWorkAsync()
```

**Exception Filters with `when` Clauses:**

```csharp
public async Task ProcessMetricsAsync(CancellationToken ct)
{
    try
    {
        await CollectMetricsAsync(ct);
    }
    catch (OperationCanceledException) when (ct.IsCancellationRequested)
    {
        // Expected cancellation from our token
        _logger.LogInformation("Metrics collection cancelled");
    }
    catch (OperationCanceledException ex)
    {
        // Unexpected cancellation from nested operation
        _logger.LogWarning(ex, "Unexpected cancellation in metrics collection");
        throw;
    }
    catch (Exception ex) when (ex is IOException || ex is SocketException)
    {
        // Transient I/O errors - could retry
        _logger.LogWarning(ex, "Transient I/O error, retrying...");
        await Task.Delay(1000, ct);
        await ProcessMetricsAsync(ct); // Retry once
    }
}
```

**Common Pitfalls to Avoid:**

1. ❌ **Async void** - Only use for event handlers, never for regular methods
2. ❌ **Swallowing exceptions** - Always log before deciding to suppress
3. ❌ **Not handling OperationCanceledException separately** - It's expected during shutdown
4. ❌ **Blocking on async code** - Never use `.Wait()` or `.Result`
5. ❌ **Catching and not rethrowing** - Hides errors from callers

**Recommendations:**
- Always handle `OperationCanceledException` separately from other exceptions
- Use Polly for retry logic instead of manual try/catch loops
- Log exceptions before re-throwing or suppressing
- Exit with `Environment.Exit(1)` on fatal errors in BackgroundService
- Use exception filters (`when`) for conditional exception handling

**IAsyncDisposable Pattern:**

```csharp
public class TestRunner : IAsyncDisposable
{
    private readonly HttpClient _httpClient;
    private readonly IConnection _rabbitConnection;
    private readonly NpgsqlConnection _dbConnection;

    public TestRunner(
        HttpClient httpClient,
        IConnection rabbitConnection,
        NpgsqlConnection dbConnection)
    {
        _httpClient = httpClient;
        _rabbitConnection = rabbitConnection;
        _dbConnection = dbConnection;
    }

    public async ValueTask DisposeAsync()
    {
        try
        {
            // Async cleanup operations
            if (_rabbitConnection?.IsOpen == true)
            {
                await _rabbitConnection.CloseAsync();
                _rabbitConnection.Dispose();
            }

            if (_dbConnection?.State == ConnectionState.Open)
            {
                await _dbConnection.CloseAsync();
                await _dbConnection.DisposeAsync();
            }

            // Synchronous cleanup
            _httpClient?.Dispose();
        }
        catch (Exception ex)
        {
            // Log but don't throw in Dispose
            // Throwing in Dispose can mask original exceptions
            Console.WriteLine($"Error during disposal: {ex.Message}");
        }
    }
}
```

```csharp
        _channel = channel;

        {
            while (await _timer.WaitForNextTickAsync(stoppingToken))
            {

        }
        finally
        {
```

**Common Pitfalls:**

1. ❌ **Creating connections per operation** - Use connection pooling
2. ❌ **Forgetting to dispose IDisposable** - Always use `using` statements
3. ❌ **Throwing in Dispose methods** - Log errors but don't throw
4. ❌ **Using finalizers unnecessarily** - Only for unmanaged resources
5. ❌ **Not using ArrayPool for temporary buffers** - Causes excessive GC pressure

**Recommendations:**
- Use **`await using`** for all async disposable resources
- **RabbitMQ**: One connection, create channels per operation
- **PostgreSQL**: Let Npgsql handle pooling automatically
- Use **ArrayPool<byte>** for temporary buffers in high-throughput scenarios
- Complete **Channel.Writer** in `finally` blocks of BackgroundServices
- Never throw exceptions in `Dispose` or `DisposeAsync`

**System.Diagnostics.Process Best Practices:**

```csharp
public class K6Runner
{
    private readonly ILogger<K6Runner> _logger;

    public async Task<K6Result> RunLoadTestAsync(
        string apiUrl,
        TimeSpan duration,
        int workers,
        CancellationToken ct)
    {
        var scriptPath = Path.Combine(AppContext.BaseDirectory, "scripts", "api-load-test.js");

        var startInfo = new ProcessStartInfo
        {
            FileName = "k6",
            Arguments = $"run --vus {workers} --duration {duration.TotalSeconds}s " +
                       $"--env API_URL={apiUrl} {scriptPath}",
            UseShellExecute = false,
            RedirectStandardOutput = true,
            RedirectStandardError = true,
            CreateNoWindow = true,
            WorkingDirectory = Path.GetDirectoryName(scriptPath)
        };

        using var process = new Process { StartInfo = startInfo };

        var outputBuilder = new StringBuilder();
        var errorBuilder = new StringBuilder();

        // Async event handlers for real-time output
        process.OutputDataReceived += (sender, args) =>
        {
            if (args.Data != null)
            {
                outputBuilder.AppendLine(args.Data);
                _logger.LogDebug("[k6 STDOUT] {Output}", args.Data);
            }
        };

        process.ErrorDataReceived += (sender, args) =>
        {
            if (args.Data != null)
            {
                errorBuilder.AppendLine(args.Data);
                _logger.LogWarning("[k6 STDERR] {Error}", args.Data);
            }
        };

        _logger.LogInformation("Starting k6 load test: {Duration}, {Workers} workers",
            duration, workers);

        process.Start();

        // Begin async reading (non-blocking)
        process.BeginOutputReadLine();
        process.BeginErrorReadLine();

        // Wait with timeout (duration + 30s buffer)
        using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
        timeoutCts.CancelAfter(duration + TimeSpan.FromSeconds(30));

        try
        {
            await process.WaitForExitAsync(timeoutCts.Token);
        }
        catch (OperationCanceledException)
        {
            _logger.LogWarning("k6 process timed out or cancelled, terminating...");

            try
            {
                // Kill entire process tree
                process.Kill(entireProcessTree: true);
                await process.WaitForExitAsync(CancellationToken.None);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Failed to kill k6 process");
            }

            throw new TimeoutException($"k6 process exceeded timeout: {duration + TimeSpan.FromSeconds(30)}");
        }

        // Check exit code
        if (process.ExitCode != 0)
        {
            _logger.LogError("k6 failed with exit code {ExitCode}", process.ExitCode);
            throw new InvalidOperationException(
                $"k6 failed with exit code {process.ExitCode}. Error: {errorBuilder}");
        }

        _logger.LogInformation("k6 load test completed successfully");

        return ParseK6Output(outputBuilder.ToString());
    }

    private K6Result ParseK6Output(string output)
    {
        // Parse k6 output for metrics
        // Example: "http_reqs....: 3613   722.461133/s"
        var result = new K6Result();

        var lines = output.Split('\n');
        foreach (var line in lines)
        {
            if (line.Contains("http_reqs"))
            {
                var parts = line.Split(new[] { ' ' }, StringSplitOptions.RemoveEmptyEntries);
                if (parts.Length >= 3 && int.TryParse(parts[1], out var totalRequests))
                {
                    result.TotalRequests = totalRequests;
                }
            }
        }

        return result;
    }
}

public class K6Result
{
    public int TotalRequests { get; set; }
    public double RequestsPerSecond { get; set; }
    public double AvgResponseTimeMs { get; set; }
}
```

**Platform Detection for Service Discovery:**

.NET 9 does not provide a native, cross-platform API for discovering which process is listening on a specific TCP port. While `System.Net.NetworkInformation.IPGlobalProperties` can enumerate active TCP listeners and connections, **it does not expose process ID information**.

Therefore, the Performance Tester must detect the operating system and use platform-specific approaches:

| Platform | Method | Tool/API |
|----------|--------|----------|
| **Linux/macOS** | External command | `lsof -ti :port` |
| **Windows** | PowerShell | `Get-NetTCPConnection -LocalPort {port}` |
| **Windows** | P/Invoke (alternative) | `GetExtendedTcpTable` from `iphlpapi.dll` |

**Platform Detection Pattern:**

```csharp

        RuntimeInformation.IsOSPlatform(OSPlatform.OSX))
```

**Why External Commands Over Native APIs?**

- ✅ **Simplicity** - One line vs. complex P/Invoke or /proc parsing
- ✅ **Cross-platform** - Minimal code differences between platforms
- ✅ **Reliability** - Uses well-tested OS utilities (`lsof`, PowerShell)
- ✅ **Maintainability** - No complex native interop code

The only trade-off is a dependency on external utilities (which are typically pre-installed), and slightly slower execution compared to native API calls (negligible for performance testing scenarios where discovery happens once per test run).

**Service Discovery via Process Lookup:**

```csharp
public class ServiceDiscovery
{
    private readonly ILogger<ServiceDiscovery> _logger;

    public async Task<int?> FindServiceProcessIdAsync(int port, CancellationToken ct)
    {
        using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
        timeoutCts.CancelAfter(TimeSpan.FromSeconds(30));

        while (!timeoutCts.Token.IsCancellationRequested)
        {
            // Use lsof on Linux/macOS
            var startInfo = new ProcessStartInfo
            {
                FileName = "lsof",
                Arguments = $"-ti :{port}",
                UseShellExecute = false,
                RedirectStandardOutput = true,
                CreateNoWindow = true
            };

            using var process = Process.Start(startInfo);
            if (process == null)
            {
                _logger.LogWarning("Failed to start lsof");
                await Task.Delay(1000, timeoutCts.Token);
                continue;
            }

            var output = await process.StandardOutput.ReadToEndAsync(timeoutCts.Token);
            await process.WaitForExitAsync(timeoutCts.Token);

            if (process.ExitCode == 0 && int.TryParse(output.Trim(), out var pid))
            {
                _logger.LogInformation("Found service on port {Port} with PID {Pid}", port, pid);
                return pid;
            }

            _logger.LogDebug("Service not found on port {Port}, retrying...", port);
            await Task.Delay(1000, timeoutCts.Token);
        }

        throw new TimeoutException($"Service not found on port {port} after 30 seconds");
    }
}
```

**Key Practices:**

- **Always redirect output/error** for capture and logging
- Use **`BeginOutputReadLine()`** for async, non-blocking reading
- Implement **timeout** with `CancellationToken`
- **Kill process tree** when terminating: `Kill(entireProcessTree: true)`
- Set **WorkingDirectory** appropriately
- Parse **exit code** (0 = success, non-zero = error)
- Add **timeout buffer** for graceful shutdown (e.g., test duration + 30s)

**Recommendations:**
- Use `Process.WaitForExitAsync(CancellationToken)` for async waiting
- Always check exit code and throw if non-zero
- Log stdout to Debug level, stderr to Warning level
- Parse process output for metrics (k6 stats, docker stats, etc.)
- Kill entire process tree on timeout to avoid orphaned processes

```csharp
// Custom TimeSpan converter (e.g., "30s", "5m", "2h")
public class DurationConverter : JsonConverter<TimeSpan>
{
    public override TimeSpan Read(
        ref Utf8JsonReader reader,
        Type typeToConvert,
        JsonSerializerOptions options)
    {
        var value = reader.GetString();
        if (string.IsNullOrEmpty(value))
            return TimeSpan.Zero;

        // Parse "30s", "5m", "2h" format
        var unit = value[^1];
        var number = double.Parse(value[..^1]);

        return unit switch
        {
            's' => TimeSpan.FromSeconds(number),
            'm' => TimeSpan.FromMinutes(number),
            'h' => TimeSpan.FromHours(number),
            _ => throw new JsonException($"Invalid duration format: {value}")
        };
    }

    public override void Write(
        Utf8JsonWriter writer,
        TimeSpan value,
        JsonSerializerOptions options)
    {
        // Write in "Xh Ym Zs" format
        var formatted = value.TotalHours >= 1
            ? $"{value.TotalHours:F2}h"
            : value.TotalMinutes >= 1
                ? $"{value.TotalMinutes:F2}m"
                : $"{value.TotalSeconds:F2}s";

        writer.WriteStringValue(formatted);
    }
}
```

**Dependency Injection Integration:**

The .NET 9 rewrite follows a **Dependency Injection Container architecture** using ASP.NET Core patterns adapted for console applications. This architectural approach ensures production-parity between the CLI tool and its comprehensive integration test suite.

**Key Architectural Differences from Python Version:**

| Aspect | Python Version | .NET 9 Version |
|--------|---------------|----------------|
| **Service Registration** | Manual instantiation (`tester = PerformanceTester(config)`) | DI Container with `AddXxx()` extension methods |
| **Dependency Management** | Direct imports and constructor calls | `Host.CreateApplicationBuilder()` with `IServiceCollection` |
| **Configuration** | Environment variables + argparse | Configuration providers + System.CommandLine |
| **Threading Model** | Python threads + daemon threads | BackgroundService + System.Threading.Channels |
| **Lifecycle Management** | Manual setup/teardown | IHost lifecycle with graceful shutdown |

**DI Container Pattern:**

**Core Principle:** Each vertical slice (Infrastructure, EventPublishing, EventConsuming, Monitoring, Orchestration) exposes an `AddXxx()` extension method that registers its services with `IServiceCollection`.

**Benefits:**
- **Production Parity** - Same service registration used in CLI tool and integration tests
- **Testability** - Integration tests use identical DI setup via `Host.CreateApplicationBuilder()`
- **Maintainability** - Each slice owns its service registration logic
- **ASP.NET Core Conventions** - Familiar patterns for .NET developers

**Example Implementation:**

```csharp
public class Program
{
    public static async Task<int> Main(string[] args)
    {
        // Build service provider using Host
        var builder = Host.CreateApplicationBuilder();

        // Register services using extension methods (each slice owns its registration)
        builder.Services.AddLogging(config => config.AddConsole().AddSerilog());

        builder.Services.AddInfrastructure(
            postgresConnectionString: builder.Configuration.GetConnectionString("Postgres"),
            rabbitMqConnectionString: builder.Configuration.GetConnectionString("RabbitMq"));

        builder.Services.AddOrchestration();

        builder.Services.AddEventPublishing(
            rabbitMqConnectionString: builder.Configuration.GetConnectionString("RabbitMq"));

        builder.Services.AddHttpClient<K6Runner>();

        var host = builder.Build();
        var serviceProvider = host.Services;

        // Define options
        var eventsOption = new Option<int>(
            aliases: new[] { "--events", "-e" },
            description: "Number of events to publish",
            getDefaultValue: () => 10000);

        var durationOption = new Option<string>(
            aliases: new[] { "--duration", "-d" },
            description: "API load test duration",
            getDefaultValue: () => "30s");

        var portOption = new Option<int>(
            aliases: new[] { "--port", "-p" },
            description: "Service port to test",
            getDefaultValue: () => 8080);

        // Create command with simple DI resolution
        var testCommand = new Command("test", "Run performance test")
        {
            eventsOption,
            durationOption,
            portOption
        };

        testCommand.SetHandler(async (int events, string duration, int port) =>
        {
            // Resolve services from DI container
            var orchestrator = serviceProvider.GetRequiredService<ITestOrchestrator>();

            // Build configuration from command options
            var config = new TestConfiguration
            {
                EventCount = events,
                ApiDuration = ParseDuration(duration),
                ServicePort = port
            };

            await orchestrator.RunTestAsync(config, CancellationToken.None);
        }, eventsOption, durationOption, portOption);

        var rootCommand = new RootCommand();
        rootCommand.AddCommand(testCommand);

        return await rootCommand.InvokeAsync(args);
    }

    private static TimeSpan ParseDuration(string duration)
    {
        var unit = duration[^1];
        var value = double.Parse(duration[..^1]);

        return unit switch
        {
            's' => TimeSpan.FromSeconds(value),
            'm' => TimeSpan.FromMinutes(value),
            'h' => TimeSpan.FromHours(value),
            _ => throw new ArgumentException($"Invalid duration: {duration}")
        };
    }
}
```

## Architectural Decision: Layered vs Vertical Slice Architecture

### Why This Section Matters

During the design phase of the .NET 9 rewrite, we evaluated **Vertical Slice Architecture (VSA)** as an alternative to the traditional layered architecture. This section documents the decision-making process and explains why **Vertical Slice Architecture is the right choice** for Performance Tester.

### What is Vertical Slice Architecture?

**Vertical Slice Architecture** organizes code by **features/use cases** rather than technical concerns. Each "slice" contains all the layers needed for that specific feature, cutting vertically through traditional horizontal layers.

**VSA Principles:**
1. **Feature-focused organization** - Code organized by what the user wants to accomplish
2. **High cohesion within slices** - Everything for a feature lives together
3. **Low coupling between slices** - Features are independent
4. **Minimal shared code** - Only truly reusable infrastructure is shared
5. **Easy to understand** - Find all code for a feature in one place
6. **Easy to change** - Changes to one feature don't ripple across layers

**Example VSA Structure:**
```
PerformanceTester/
├── Features/
│   ├── RunTest/                    # Vertical slice for "test" command
│   │   ├── RunTestCommand.cs
│   │   ├── RunTestHandler.cs
│   │   ├── TestOrchestrator.cs
│   │   ├── Monitors/               # Monitoring just for this feature
│   │   ├── Publishers/             # Publishing just for this feature
│   │   └── Reporters/              # Reporting just for this feature
│   └── CompareResults/             # Vertical slice for "compare" command
│       ├── CompareCommand.cs
│       ├── CompareHandler.cs
│       └── ...
└── Shared/                         # Minimal shared infrastructure
```

---

### Analysis: Why Vertical Slice Architecture is the Right Choice

#### 1. Self-Contained Capabilities

Performance Tester's monitoring and testing components are **independent capabilities**, not layers:

- **Process Monitoring** - Samples CPU/RAM/threads every 500ms, produces ProcessMetrics
- **System Monitoring** - Samples system-wide resources every 500ms, produces SystemMetrics
- **Docker Monitoring** - Samples container stats every 3s, produces DockerMetrics
- **Event Publishing** - Publishes CloudEvents to RabbitMQ, owns CloudEvent model
- **Event Consuming** - Consumes events and tracks throughput, owns ThroughputSample
- **API Load Testing** - Runs k6 and parses results, owns K6Result
- **Reporting** - Generates JSON/charts, owns TestReport

Each capability is a **complete unit** with its own:
- Data structures (ProcessMetrics, CloudEvent, K6Result)
- Service logic (BackgroundService, RabbitMQ client, k6 runner)
- Public API (IProcessMonitor, IEventPublisher, ILoadTester)

**Benefit:** "Where's process monitoring code?" → `PerformanceTester.ProcessMonitoring` (everything in one place)

---

#### 2. Producer-Owned Contracts

In VSA, **producers own their data structures**, not a shared model project:

**ProcessMonitoring slice produces ProcessMetrics:**
```csharp
// PerformanceTester.ProcessMonitoring/ProcessMetrics.cs
public record ProcessMetrics
{
    public DateTime Timestamp { get; init; }
    public double CpuPercent { get; init; }
    public double RamMb { get; init; }
}

// PerformanceTester.ProcessMonitoring/IProcessMonitor.cs
public interface IProcessMonitor
{
    Task<IReadOnlyCollection<ProcessMetrics>> GetCollectedMetricsAsync();
}
```

**EventPublishing slice produces CloudEvent:**
```csharp
// PerformanceTester.EventPublishing/CloudEvent.cs
public record CloudEvent { /* ... */ }

// PerformanceTester.EventPublishing/IEventPublisher.cs
public interface IEventPublisher
{
    Task PublishEventsAsync(int count, CancellationToken ct);
}
```

**Orchestrator consumes via interfaces:**
```csharp
// PerformanceTester.Orchestration/TestOrchestrator.cs
public class TestOrchestrator
{
    private readonly IProcessMonitor _processMonitor;
    private readonly IEventPublisher _publisher;

    // Depends on public APIs, not shared models
}
```

**Benefit:** Clear ownership - ProcessMonitoring owns ProcessMetrics, EventPublishing owns CloudEvent. No coupling through shared model projects.

---

#### 3. Better Testability

Each slice can be tested **in isolation** without dependencies on other slices:

**Testing ProcessMonitoring slice:**
```csharp
[Fact]
public async Task ProcessMonitor_CollectsMetrics_Every500ms()
{
    // Arrange: Create slice with test configuration
    var config = new ProcessMonitorConfig { SamplingInterval = TimeSpan.FromMilliseconds(500) };
    var monitor = new ProcessMonitorService(config, channel);

    // Act: Start monitoring
    await monitor.StartAsync(cancellationToken);
    await Task.Delay(2000);
    await monitor.StopAsync(cancellationToken);

    // Assert: Check metrics collected
    var metrics = await monitor.GetCollectedMetricsAsync();
    Assert.InRange(metrics.Count, 3, 5); // ~4 samples in 2 seconds
}
```

**No mocking across slices** - ProcessMonitoring doesn't depend on EventPublishing or Reporting. Each slice has:
- Clear inputs (configuration, cancellation token)
- Clear outputs (metrics collection via public API)
- No hidden dependencies

**Benefit:** Test each capability independently, no complex mock setup across layers.

---

#### 4. Clear Ownership and Boundaries

Each slice has a **single responsibility** and **clear boundaries**:

**ProcessMonitoring responsibilities:**
- ✅ Sample process CPU/RAM/threads
- ✅ Provide IProcessMonitor interface
- ✅ Own ProcessMetrics data structure
- ❌ NOT responsible for reporting (that's Reporting slice)
- ❌ NOT responsible for Docker stats (that's DockerMonitoring slice)

**EventPublishing responsibilities:**
- ✅ Publish events to RabbitMQ
- ✅ Own CloudEvent data structure
- ✅ Provide IEventPublisher interface
- ❌ NOT responsible for consuming (that's EventConsuming slice)
- ❌ NOT responsible for throughput tracking (that's EventConsuming slice)

**Benefit:** Easy to understand what each slice does, and changes to one slice don't affect others.

---

#### 5. Enables Focused Development

When working on a capability, **everything you need is in one place**:

**Scenario:** Need to add thread pool stats to process monitoring

**With VSA:**
1. Open `PerformanceTester.ProcessMonitoring` project
2. Update `ProcessMetrics` record (add ThreadPoolStats property)
3. Update `ProcessMonitorService` sampling logic
4. Update `IProcessMonitor` interface if needed
5. Done - no changes to other slices

**Benefit:** All related code (model, service, interface) lives together. No hunting across multiple layers or shared model projects.

### Comparison Matrix: Layered vs VSA for Performance Tester

| Criterion | Layered Architecture | Vertical Slice Architecture | Winner |
|-----------|----------------------|-----------------------------|--------|
| **Self-Contained Capabilities** | ⚠️ Mixed across layers | ✅ Complete units (model + service + API) | **VSA** |
| **Producer Ownership** | ⚠️ Shared model projects | ✅ Producers own data structures | **VSA** |
| **Testability** | ⚠️ Cross-layer dependencies | ✅ Test slice in isolation | **VSA** |
| **Clear Ownership** | ⚠️ "Where's X?" → Check layer + models | ✅ "Where's X?" → X slice | **VSA** |
| **Change Impact** | ⚠️ Changes ripple across layers | ✅ Changes localized to slices | **VSA** |
| **Focused Development** | ⚠️ Edit across multiple projects | ✅ Everything in one project | **VSA** |
| **Single Responsibility** | ⚠️ Layers have mixed concerns | ✅ Each slice has one job | **VSA** |
| **Coupling** | ⚠️ Coupled through shared models | ✅ Coupled only via interfaces | **VSA** |

**Overall Winner: Vertical Slice Architecture (8 advantages, 1 tie)**

### Trade-offs and How We Address Them

VSA brings clear benefits, but also introduces some challenges. Here's how we address them:

#### Challenge 1: More Projects in Solution

**Trade-off:** VSA creates more projects (9 slices vs 5-6 layers)

**Why it's worth it:**
- **Clear boundaries** - Each project has one job
- **Easier navigation** - "Where's process monitoring?" → One project, not scattered across layers
- **Better testability** - Test one project in isolation
- **Modern IDEs handle this well** - Solution explorer groups, search across projects

**Verdict:** Worth the extra projects for clarity and maintainability

---

#### Challenge 2: Some Infrastructure is Truly Shared

**Trade-off:** Not everything fits cleanly into slices (IHost, Channels, config)

**How we handle it:**

**Infrastructure slice for truly shared utilities:**
```
PerformanceTester.Infrastructure/
├── DatabaseCleaner.cs     # Truly shared: used by setup phase
├── RabbitMqCleaner.cs     # Truly shared: used by setup phase
└── ServiceDiscovery.cs    # Truly shared: used by setup phase
```

**Each monitoring capability still self-contained:**
```
PerformanceTester.ProcessMonitoring/   # Not shared - independent capability
PerformanceTester.SystemMonitoring/    # Not shared - independent capability
PerformanceTester.DockerMonitoring/    # Not shared - independent capability
```

**Guideline:** Infrastructure slice contains **utilities**, not **capabilities**. Capabilities (monitoring, publishing, reporting) are separate slices.

**Verdict:** Fine-grained slicing for capabilities, Infrastructure slice for setup/cleanup utilities

---

#### Challenge 3: Orchestrator Depends on Many Interfaces

**Trade-off:** TestOrchestrator needs to coordinate all slices

**How we handle it:**

This is actually a **benefit**, not a problem:
```csharp
public class TestOrchestrator
{
    // Explicit dependencies - clear what this orchestrator needs
    private readonly IProcessMonitor _processMonitor;
    private readonly ISystemMonitor _systemMonitor;
    private readonly IDockerMonitor _dockerMonitor;
    private readonly IEventPublisher _publisher;
    private readonly IEventConsumer _consumer;
    private readonly ILoadTester _loadTester;
    private readonly IReportGenerator _reportGenerator;
    private readonly IInfrastructure _infrastructure;
}
```

**Benefits:**
- ✅ **Testable** - Mock any interface for unit tests
- ✅ **Clear** - See all dependencies at once
- ✅ **Flexible** - Swap implementations easily
- ✅ **Type-safe** - Compiler checks all dependencies

**Verdict:** Explicit orchestration is clearer than implicit layer dependencies

---

### Final Architectural Decision

**Use Vertical Slice Architecture as proposed in this document.**

**Rationale:**

1. **Self-Contained Capabilities** - Each monitoring type, publishing/consuming, load testing, and reporting is an independent capability with its own data structures
2. **Producer-Owned Contracts** - ProcessMonitoring owns ProcessMetrics, EventPublishing owns CloudEvent - no coupling through shared model projects
3. **Better Testability** - Test each slice in isolation without complex cross-layer mocking
4. **Clear Ownership** - "Where's process monitoring?" → PerformanceTester.ProcessMonitoring (everything in one place)
5. **Localized Changes** - Adding thread pool stats only affects ProcessMonitoring slice
6. **Aligns with .NET patterns** - VSA works perfectly with BackgroundService, IHost, Channels

**Key Insight:**

Performance Tester's monitoring capabilities (Process, System, Docker) are **independent features**, not technical layers. Each capability deserves its own slice with full ownership of its data structures and service logic.
