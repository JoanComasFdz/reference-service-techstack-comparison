# Performance Tester .NET Implementation Order & Responsibilities (VSA)

## Overview

This document defines the **implementation order** and **high-level responsibilities** for each project in the .NET 9 Performance Tester rewrite using **Vertical Slice Architecture (VSA)**. Each slice is self-contained and owns its data structures, following the producer-owned contracts principle.

**Key VSA Principles:**
- ✅ Each slice owns its models (no central Core project)
- ✅ Producers expose interfaces that consumers depend on
- ✅ Maximum independence between slices
- ✅ Higher parallelization potential
- ✅ Clear ownership boundaries

**Abstraction Level:** This document focuses on:
- ✅ Which project to implement first, second, third, etc.
- ✅ What each project is responsible for (features/functionality)
- ✅ Which models each slice owns (producer-owned contracts)
- ❌ NOT detailed code implementation (comes after analyzing Python code)
- ❌ NOT line-by-line Python code translation

---

## Implementation Order with Dependencies

```
0. IntegrationTesting (Testing Foundation - no dependencies)
   ↓
1. Infrastructure (Foundation - no dependencies)
   ↓
2. [Parallel Implementation - 6 Independent Slices]
   ├─ EventPublishing (owns CloudEvent)
   ├─ EventConsuming (owns ThroughputSample)
   ├─ ProcessMonitoring (owns ProcessMetrics)
   ├─ SystemMonitoring (owns SystemMetrics)
   ├─ DockerMonitoring (owns DockerMetrics)
   └─ ApiLoadTesting (owns K6Result)
   ↓
3. Reporting (depends on models from all Phase 2 slices)
   ↓
4. Orchestration (depends on interfaces from all slices)
   ↓
5. CLI (depends on Orchestration)
```

### Why This Implementation Order?

**Phase 0 First (IntegrationTesting):**
- Shared test infrastructure for all integration test projects
- Provides ContainerManager singleton (PostgreSQL + RabbitMQ)
- Provides IntegrationTestBase (lifecycle hooks, logging capture)
- Eliminates duplication across 6+ test projects
- Must exist before any integration tests can be written
- See `docs/plans/05.PHASE_0_INTEGRATION_TESTING_DESIGN.md` for complete design

**Phase 1 Next (Infrastructure):**
- Zero dependencies, needed by orchestrator for setup/cleanup utilities
- First project to have integration tests (validates Phase 0)
- Provides service discovery, database cleaning, queue management

**Phase 2 Parallelizable (All 6 slices independent):**
- **EventPublishing** - Only depends on external NuGet packages (RabbitMQ.Client, CloudNative.CloudEvents)
- **EventConsuming** - Only depends on external NuGet packages (RabbitMQ.Client, CloudNative.CloudEvents)
- **ProcessMonitoring** - Only depends on System.Diagnostics.Process
- **SystemMonitoring** - Only depends on System.Diagnostics.PerformanceCounter
- **DockerMonitoring** - Only depends on Docker.DotNet (NuGet package)
- **ApiLoadTesting** - Only depends on k6 process (no other project)
- **Key:** No project-to-project dependencies, only external packages

**Phase 3 Next (Reporting):**
- Depends on ALL Phase 2 model types (consumer role, not producer)
- Must reference all Phase 2 projects to consume their models
- Generates output from collected data

**Phase 4 Next (Orchestration):**
- Depends on ALL slice interfaces (coordination layer)
- Must reference all projects to coordinate workflow
- Controls BackgroundService lifecycle via IHost

**Phase 5 Last (CLI):**
- Entry point, depends on everything
- Uses `AddXxx()` extension methods from all slices
- Wires up complete DI container

## Phase 0: Testing Foundation

### Project 0: PerformanceTester.IntegrationTesting

**Implementation Priority:** 0th (Before everything else)
**Dependencies:** None (only external NuGet packages)

#### Responsibilities

Singleton managing PostgreSQL and RabbitMQ container lifecycle:

- **EnsureStartedAsync(CancellationToken)**
  - Start PostgreSQL and RabbitMQ containers in parallel
  - Idempotent (subsequent calls are no-ops)
  - Thread-safe using double-check locking pattern
  - Store connection strings for test projects
  - Containers use random host ports (enables parallel test runs)
  - Containers remain running after tests (for debugging)

##### 2. IntegrationTestBase
Abstract base class providing test lifecycle and logging:

- **InitializeAsync()**
  - Ensure containers are started via ContainerManager
  - Virtual method (test projects override to add cleanup logic)
  - Write diagnostic messages to test output

- **DisposeAsync()**
  - Intentionally empty (data persists for debugging)
  - Virtual method (test projects can override if needed)

- **ITestOutputHelper Integration**
  - Accept ITestOutputHelper in constructor

- **XunitLogger** - ILogger implementation writing to ITestOutputHelper

3. Implements System and Infrastructure classes named after the project (e.g., Infrastructure, EventConsuming, etc.)

## Phase 1: Foundation

### Project 1: PerformanceTester.Infrastructure

**Implementation Priority:** 1st
**Dependencies:** None
**Why First:** Zero dependencies, provides utilities needed by orchestrator, self-contained

#### Responsibilities

##### 1. ServiceDiscovery
Find which process is listening on a given port:

- **FindServiceProcessIdAsync(port, timeout, CancellationToken)**
  - Platform detection: `RuntimeInformation.IsOSPlatform(OSPlatform.Linux/Windows)`
  - Linux/macOS: Use `lsof -ti :PORT` via Process
  - Windows: Use `Get-NetTCPConnection -LocalPort {port}` PowerShell
  - Retry every 1s until found or timeout (default: 30s)
  - Return process ID for monitoring
  - Throw TimeoutException if not found

- **WaitForServiceAsync(port, timeout, CancellationToken)**
  - Convenience method that just checks if service is running
  - Returns true/false instead of PID
  - Used by orchestrator in setup phase

##### 2. DatabaseCleaner
Prepare PostgreSQL databases for testing:

- **ClearDatabaseAsync(databaseName, CancellationToken)**
  - Connect to PostgreSQL via Npgsql
  - Query `pg_tables` to discover all tables in 'public' schema
  - Generate `TRUNCATE TABLE {table1}, {table2}, ... CASCADE` command
  - Execute truncation
  - Verify cleanup: Query `pg_stat_user_tables` for row counts
  - Retry logic: 2 attempts with 2s delay for transient connection issues
  - Log table names and row counts before/after

- **ConnectionStringBuilder**
  - Build Npgsql connection strings from configuration
  - Support both password-based and trusted authentication

##### 3. RabbitMqCleaner
Clear RabbitMQ message queues:

- **ClearAllQueuesAsync(CancellationToken)**
  - Connect to RabbitMQ Management HTTP API
  - List all queues in default vhost
  - Purge each queue (DELETE /api/queues/{vhost}/{queue}/contents)
  - Verify queues are empty (message_count == 0)
  - Retry logic: 3 attempts with 1s delay

- **ClearQueueAsync(queueName, CancellationToken)**
  - Purge specific queue by name
  - Verify purge succeeded

- **GetQueueDepthAsync(queueName, CancellationToken)**
  - Query message count for specific queue
  - Used for verification after cleanup

##### 4. Infrastructure Interfaces
Public APIs for orchestrator (3 separate interfaces following Interface Segregation Principle):

- **IDatabase**
  - `Task ClearDatabaseAsync(string dbName, CancellationToken ct)`

- **IRabbitMQ**
  - `Task ClearAllQueuesAsync(CancellationToken ct)`

- **IServiceDiscovery**
  - `Task<int> FindServiceProcessIdAsync(int port, TimeSpan timeout, CancellationToken ct)`

##### 5. Dependency Injection
Expose `AddInfrastructure()` extension method following the patterns defined in `INTEGRATION_TEST_DESIGN.md`.

### Project 2b: PerformanceTester.EventConsuming

**Implementation Priority:** 2nd (parallel with 2a, 2c-2f)
**Dependencies:** RabbitMQ.Client (NuGet), CloudNative.CloudEvents (NuGet)
**Why Independent:** No dependencies on other projects in the solution, only external NuGet packages

#### Responsibilities

##### 1. Models (Owned by this Slice)

- **ThroughputSample**
  - Timestamp (DateTime)
  - Throughput rate (events/s)
  - Cumulative count (int)

##### 2. ThroughputTracker
Calculate throughput rates from event timestamps:

- **RecordEvent()**
  - Record timestamp of event received
  - Calculate events/sec based on time window (500ms)
  - Create ThroughputSample
  - Return sample

- **GetSamples() → IReadOnlyCollection\<ThroughputSample\>**
  - Return all collected samples
  - Called after test completion

##### 3. EventConsumer
Consume processed events from RabbitMQ:

- **Architecture**
  - Single persistent IConnection
  - Long-lived IChannel for consuming
  - Async consumer (IAsyncBasicConsumer pattern)
  - Thread-safe event counting (Interlocked.Increment)
  - Queue name: "performancetesterdotnet" (configurable via environment variable)
  - Exchange: "referenceservice.comparison" (topic exchange)
  - Routing key binding: "instrumentstatus.kpi.updated"
  - **Important:** Queue name ≠ routing key (queue is the consumer's inbox, routing key is the message filter)

##### Inactivity Timeout (Improvement over Python)

**Python Implementation:**
- Absolute timeout (120s from start, regardless of progress)
- Formula: `elapsed = time.time() - consume_start_time`
- Fails slow-but-progressing services
- Problem: Service processing 1 event/sec for 10,000 events will fail after 120s (received only 120/10,000)

**Our Implementation (Better):**
- Inactivity timeout (120s since last event received)
- Timeout resets on EVERY event received
- Formula: `timeSinceLastEvent = DateTime.UtcNow - lastEventReceivedTime`
- Allows slow-but-progressing services to complete
- Detects truly stuck services (no activity for 120s)
- Uses System.Threading.Timer for periodic checks (every 1s)
- More realistic for production scenarios

- **StartTrackingEventsAsync(expectedCount, inactivityTimeout, CancellationToken)**
  - Set internal target count
  - Create TaskCompletionSource for signaling
  - Initialize inactivity timeout tracking (last event received timestamp)
  - Start Timer to check for inactivity (every 1 second)
  - Return awaitable Task that completes when:
    - Target count reached (TaskCompletionSource signaled by OnMessageReceivedAsync)
    - OR inactivity timeout expires - no events received for {inactivityTimeout} seconds (throws TimeoutException)
    - OR cancellation requested (throws OperationCanceledException)
  - **Improvement over Python:** Timeout resets on each event, allowing slow-but-progressing services to complete

- **ExecuteAsync(CancellationToken)** [BackgroundService lifecycle]
  - Create channel
  - Declare exchange: "referenceservice.comparison" (topic, durable)
  - Declare queue: "performancetesterdotnet" (durable, configurable)
  - Bind queue to exchange with routing key: "instrumentstatus.kpi.updated"
  - Set prefetch count: 100 (configurable)
  - Register async callback: OnMessageReceivedAsync
  - Start consuming with manual ACK
  - Run until cancellation
  - Complete throughput channel on exit (in finally block)

- **OnMessageReceivedAsync(BasicDeliverEventArgs)**
  - Deserialize message to CloudEvent using CloudEvents JSON formatter
  - Increment received count (Interlocked.Increment - thread-safe)
  - **Reset inactivity timer** - update last event received timestamp (DateTime.UtcNow)
  - Create throughput sample via ThroughputTracker
  - Write sample to Channel<ThroughputSample> (non-blocking async write)
  - Check if count >= target → signal TaskCompletionSource (TrySetResult)
  - Manual ACK message

- **ReceivedCount Property**
  - Thread-safe read of _receivedEventCount
  - Use Interlocked.CompareExchange for lock-free read
  - Used for diagnostics and timeout error messages only
  - NOT used for orchestrator polling (unlike Python)

- **Graceful Shutdown**
  - Close channel
  - Cancel consumer tag
  - Complete throughput channel on exit (in finally block)

**Note:** Throughput samples are NOT retrieved from IEventConsumer. They are collected by a separate MetricsCollectorService (BackgroundService) that reads from `Channel<ThroughputSample>` and stores samples in a ConcurrentBag. The orchestrator retrieves samples via `IMetricsCollector.GetThroughputSamples()` after test completion.

##### 4. Public Interface

- **IEventConsumer**

Expose `AddEventConsuming()` extension method following the patterns defined in `INTEGRATION_TEST_DESIGN.md`.

  - Unbounded channel
  - Single writer (ProcessMonitorService)

##### 3. ProcessMonitorService
BackgroundService that monitors target service process:

- **Architecture**
  - BackgroundService with PeriodicTimer (500ms interval)
  - Writes ProcessMetrics to Channel\<ProcessMetrics\>
  - Non-blocking CPU sampling

- **ExecuteAsync(CancellationToken)**
  - Get Process by PID (from configuration or ServiceDiscovery)
  - Loop with PeriodicTimer.WaitForNextTickAsync
  - Collect metrics:
    - CPU% using Process.TotalProcessorTime (calculate delta)
    - RAM MB using Process.WorkingSet64 / 1024 / 1024
    - Thread count using Process.Threads.Count
  - Write to channel (non-blocking)
  - Handle process exit gracefully
  - Complete channel on shutdown (in finally block)

- **CPU Calculation**
  - Store previous TotalProcessorTime
  - Calculate delta between samples
  - Divide by elapsed time and core count
  - Result: CPU percentage

## Model Ownership and Cross-Slice Dependencies

### VSA Principle: Producer-Owned Contracts

In Vertical Slice Architecture, **each slice owns the data it produces**. This means:

- **EventConsuming** owns the `ThroughputSample` model (throughput metrics it produces)
- **ProcessMonitoring** owns the `ProcessMetrics` model (process data it produces)
- **SystemMonitoring** owns the `SystemMetrics` model (system data it produces)
- **DockerMonitoring** owns the `DockerMetrics` model (container data it produces)
- **ApiLoadTesting** owns the `K6Result` model (load test results it produces)
- **Reporting** owns the `TestReport` and `SystemInfo` models (report data it produces)
- **Orchestration** owns the `TestConfiguration` model (test parameters it defines)

**Industry-Standard Shared Types:**
- **CloudEvent** - Both EventPublishing and EventConsuming use the official `CloudNative.CloudEvents` NuGet package. This is an industry-standard message format, not a project dependency.

### Acceptable Dependencies

**Consumer Role Dependencies (Acceptable):**
- **Reporting → All Phase 2 models** - Reporting acts as a consumer that aggregates data from all producers. It depends on model types but not on implementations.
- **Orchestration → All slice interfaces** - Orchestration coordinates workflow by calling slice interfaces. It depends on interfaces but not on concrete implementations.
- **ApiLoadTesting → ThroughputSample type** - K6Result includes throughput samples, creating a dependency on EventConsuming's model.

**External Package Dependencies (Acceptable):**
- **EventPublishing → CloudNative.CloudEvents** - Uses official CloudEvents library for event format.
- **EventConsuming → CloudNative.CloudEvents** - Uses same official library to deserialize events.
- Both slices share a NuGet dependency, not a project-to-project dependency.

**Slice-to-Slice Implementation Dependencies (Unacceptable):**
- ❌ Slices in Phase 2 should NOT depend on each other's implementations
- ❌ No circular dependencies between slices
- ❌ No shared "Core" or "Common" project containing models from multiple slices

### Why This Matters

**Benefit 1: Independent Development** - Phase 2 slices can be developed in parallel by different developers without coordination.

**Benefit 2: Clear Ownership** - Each model has exactly one owner responsible for its definition and evolution.

**Benefit 3: Minimal Coupling** - Dependencies flow in one direction (Phase 2 → Phase 3 → Phase 4 → Phase 5).

| **Parallelization** | 4 projects (Messaging, Monitoring, LoadTesting, Reporting) | 6 projects (all Phase 2 slices) |
| **First Project** | Core (models/interfaces) | Infrastructure (utilities) |
| **Model Ownership** | Ambiguous (central dumping ground) | Clear (producer owns) |
| **Testing** | Must wait for Core | Can test each slice immediately |
| **Changes** | Ripple through all projects | Isolated to single slice |
| **Coupling** | High (all depend on Core) | Low (interface-based) |

### Benefits

1. **Higher Parallelization** - 6 independent slices vs 4 in layered approach
2. **Better Isolation** - Changes to ProcessMetrics don't affect EventPublishing
3. **Clearer Ownership** - No "where does this model go?" questions
4. **Easier Testing** - Each slice testable in isolation
5. **Faster Iteration** - No waiting for Core to stabilize
6. **Better Encapsulation** - Internal implementation details stay internal
7. **Natural API Boundaries** - Public interfaces define clear contracts
